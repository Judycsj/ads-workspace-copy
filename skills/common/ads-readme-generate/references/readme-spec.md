# README 生成规范与方法 / README Spec & Playbook

> 本文件是 ads-readme-generate 的内置规范，分两部分：**Part 1 骨架规范**（跨仓库通用、几乎不变）+ **Part 2 写作方法**（各章节"挖什么/怎么委托"，事实每次从代码 + 兄弟 skill 当场生成，永不过期）。业务上下文参考本地 `docs/common/core-knowledge/`。
>
> The complete built-in spec for ads-readme-generate.
> Part 1 = skeleton (cross-repo, rarely changes); Part 2 = per-section methods (facts re-derived from code + sibling skills every run). Business context comes from local `docs/common/core-knowledge/`.

---

# Part 1 — 骨架规范 / Skeleton Spec

## 输出位置与语言 / Output Location & Languages

生成结果统一写入 ads-workspace 的 **`docs/common/readme/<project_name>/`** 目录（对应项目文件夹，不存在则创建）。每个项目固定输出两份：

| code | 文件名 / Filename | 内容 / Content |
| ---- | ---------------- | -------------- |
| `en` | `README.md`         | 英文版（主文件） |
| `zh` | `README.zh-CN.md`   | 中文版，结构与英文版严格一致 |

`zh` 文件中术语（见下）保留英文原名；两份结构完全一致、互为翻译。

## 章节骨架 / TOC Skeleton

所有仓库以下列目录为基准骨架。**子章节按代码分析结果动态扩展**（例如某服务有复杂的存储层、API 定义、核心流程，就在对应位置增设子节），但顶层章节顺序保持一致。

```
- 目录 / Table of Contents
- 项目概述 / Introduction
- 核心功能 / Features
- 项目架构 / Architecture
    - 上下游调用拓扑 / Service Topology      # 见 Part 2 的「拓扑推导配方」
- 目录结构 / Directory Structure
- 开发规范 / Development Guidelines
    - 代码风格 / Code Style
    - 项目结构 / Project Structure
    - 命名规范 / Naming Conventions
    - 错误处理 / Error Handling
    - 单元测试 / Unit Testing Standards
    - Code Review & Git Workflow
- 配置说明 / Configuration
    - 配置文件 / Config Files
    - SPEX 与 spcli 配置 / SPEX and spcli Setup
- 部署 / Deployment
    - 生产构建 / Build for Production
    - 发布流程 / Release Process
- 监控 / Monitoring
- 业务术语表 / Business Terminology Glossary
- 参考资料 / Additional Resources
- 常见问题 / Frequently Asked Questions
```

> 动态扩展示例（不写死，仅供模型参考语感）：C++/BRPC 服务可增设「Spex/BRPC API 定义」「核心流程」「存储层」；FE 仓库可增设「构建与发布」「页面/路由结构」等。是否增设由代码事实决定。

## 生成标记 / Generation Marker

每份文件末尾追加，含两个版本字段：`<HEAD_COMMIT>` = 被分析仓库 HEAD 的完整 40 位哈希（代码版本）；`<SPEC_HASH>` = `sha256(references/readme-spec.md)` 取前 16 位（规范版本）。每次生成/更新都刷新两者（SKILL 第一步据此判断代码 / 规范是否变化）：

```
<!-- Generated by ads-workspace/skills/ads-readme-generate | checked: <HEAD_COMMIT> | spec: <SPEC_HASH> -->
```

## 通用术语 / Common Terminology

以下 Ads 域通用术语在全文保持英文原写法。**项目级术语（类名、proto 类型、服务名、框架名）由代码分析当场抽取**，不在此列举：

```
eCPM  uGSP  GSP  SPEX  spcli  DAG  GAS  BRPC  ROI  CTR  CVR  OCPX  nobid
Config Center  Kafka  Pulsar  Redis  CacheCloud  Prometheus  Grafana  Vespa
```

# Part 2 — 写作方法 / Methodology

## 通用要求 / General Rules

- 每个章节先**从代码/配置静态挖事实**，再视情况**委托兄弟 skill 补全**（见下方「委托补全」）。
- 委托是"尽量委托、追求信息最全"：只要某章节有对应的活数据 skill 且环境可用（本地有 MCP / token，或 CI 已配），就调用它补充最新事实。
- 委托失败或无 token → 退回纯代码推导，并在该处注明数据来源受限，**绝不编造**（细则见 SKILL.md「原则」）。
- 若旧 README 含 repo 特有、且仍能从代码/配置/稳定运维文档验证的内容（命令、脚本、env var、socket、build target、proto 流程、FAQ、缓存 key 约定），**保留**进新 README，不被通用模板覆盖。

## 各章节挖掘要点 / Per-Section Mining Guide

> 以下是"挖什么"的通用方法，非具体事实。每条都要落到**实际的类名/函数名/服务名/repo 名/配置项**上。

### 项目概述 / Introduction
- 一句话定位：服务在 Shopee Ads 链路中的角色与上下游位置。
- 仓库链接：写入 `repository_url`。
- 技术栈：语言、RPC 框架、构建工具、对外暴露的核心 RPC/接口（从 proto/路由读）。
- 核心能力：从入口往下追主链路，概括"输入 → 处理 → 输出"。

### 核心功能 / Features
- 列出对外 RPC/接口及签名（从 `.proto` / 路由定义读真实方法名）。
- 每个核心能力对应到实现它的模块/类，标注真实命名。

### 项目架构 / Architecture
- 外部依赖及交互关系（即下方「上下游调用拓扑 — 推导配方」的产物）。
- 启动流程：从 `main` / 入口往下，列初始化顺序（config → 线程池 → 存储 → MQ → server 等真实步骤）。
- 关键数据流：一次请求从入口到响应经过的真实函数链。
- 中间件实例明细：凡是 README 提到 Redis / Kafka / Pulsar / FSE / Vespa / DB / Hive / S3 / ClickHouse / MQ 等中间件，必须写到**具体实例名**和**读写方向**，不能只写"读取 Redis"、"写 Kafka"、"访问 FSE"这类泛称。无法从代码或委托结果确认具体名称时，只能写"代码中未发现具体实例名"，不得补猜。

### 目录结构 / Directory Structure
- 列顶层目录及职责（跳过 `skip_dirs`），对应到模块。

### 开发规范 / Development Guidelines
- 代码风格：读 `.clang-format` / `.golangci.yml` / `.eslintrc` 等真实配置。
- 命名/项目结构/错误处理：从代码归纳实际约定（单例方式、错误返回模式、日志前缀等）。
- 单元测试：测试框架、入口、运行命令（从 Makefile / CI 读）。
- Code Review & Git Workflow：从 `.gitlab-ci.yml` 读真实 stage；提交前的 build/test 命令。

### 配置说明 / Configuration
- 配置文件：列 `config/` 下真实文件及关键字段。
- SPEX 与 spcli 配置：说明 SPEX 配置方式和 spcli 安装步骤（通用配置）。
- Config Center：优先委托 `sp-config-center` 读取真实 project/namespace/item/key；若环境只提供旧工具，则委托 `ads-config-center-compare-export` 列真实 namespace/key。
- 若旧 README 有稳定的本地运行配置、cache key 约定、socket 映射、proto 生成步骤，优先保留到此或 FAQ。
- 中间件配置：对每个中间件列出代码中可验证的具体配置项，例如 Kafka topic / broker / producer config / consumer group，Redis host:port / cluster name / key pattern / TTL，FSE table / scene / namespace / proxy，DB name / table / DSN，Vespa cluster / schema / document type，Hive table，S3 bucket/path，ClickHouse database/table。

### 部署 / Deployment
- 生产构建：从 Makefile / 构建脚本 / `deploy/*.json` 读真实命令与镜像。
- 发布流程：SPEX 发布流程与灰度策略（通用）；委托 `sp-space` 补全 SDU/部署信息。

### 监控 / Monitoring
- Prometheus 指标：从 exporter/metrics 定义读真实指标前缀、labels、含义。
- 关键监控点：基于指标归纳应关注的延迟/命中率/lag 等。
- 大盘链接：委托 `sp-grafana` 按 service name 搜大盘填入；查不到则注明"内部监控平台"。

### 业务术语表 / Business Terminology Glossary
- 汇总全文用到的业务/技术术语；委托 `sra-glossary` 校准业务术语定义。

### 参考资料 / Additional Resources
- 无专门挖掘项：链接的保留/取舍遵循「通用要求」（见上，旧 README 中稳定可验证的链接保留，敏感/一次性内容不留）；**不收录本地 core-knowledge 文档链接（那是生成时的内部参考，不面向 README 读者）**；全新生成时无可靠来源即留空。

### 常见问题 / Frequently Asked Questions
- 提出 5–10 个帮助新人快速理解项目的关键问题，答案均来自代码事实。
- 把旧 README 里零散但有价值的 repo-specific note（运行 prerequisites、debug command、cronjob flags、cache key format）整理成 FAQ，不因章节重构遗漏。

## 上下游调用拓扑 — 推导配方 / Service Topology Recipe

按以下步骤从代码推导，再委托增强：

### 1. 静态挖掘（必做）/ Static mining

扫描代码识别四类邻居，全部以**代码证据**为准：

- **上游 / Upstream（谁调用本服务）**：SPEX/BRPC/gRPC 的 service 定义与 server 注册（`spex_register`、`cc_generic_services`、`.proto` service）、HTTP handler 路由。
- **下游 / Downstream（本服务调用谁）**：RPC client stub、SDK client 初始化、HTTP client、对外导出端点（如 Prometheus exporter）。
- **依赖 / Dependencies**：
  - 消息队列：Kafka/Pulsar 的 consumer/producer 构造、订阅的 topic 字符串。
  - 存储：Redis/CacheCloud client、DB（MySQL/TiDB）、本地缓存。
  - 配置：Config Center / ConfigCenterManager 的 namespace。
  - 网络/中间件：SPEX Agent socket、ZK 注册等。
  - 库依赖：构建文件里的关键内部库（`MODULE.bazel` / `go.mod` 等）。

### 1.1 中间件实例命名要求（强制）/ Middleware Instance Naming Requirements

README 不能只停留在中间件类型层面。每一项中间件依赖必须尽量落到代码或配置中的**具体名称**：

| 类型 / Type | 必须挖掘并写明的具体名称 / Required concrete names |
| ----------- | -------------------------------------------------- |
| Kafka / Pulsar / MQ | topic 名、producer/consumer 名或配置 key、consumer group、broker/bootstrap 配置（如代码可见） |
| Redis / CacheCloud | cluster name 或 host:port、配置 key、key pattern、value 用途、TTL/过期策略、读/写/读写方向 |
| FSE / Feature Store | table / feature table、scene、namespace/project、proxy/cluster、读取或写入字段（如代码可见） |
| DB / MySQL / TiDB / PostgreSQL | DB 名、table 名、DSN/config key、读/写/事务用途 |
| Vespa / ElasticSearch | cluster/app、schema/document type/index、feed/query 方向 |
| Hive / HDFS / S3 / ClickHouse | table、bucket/path、database/table、读/写方向 |
| Config Center | namespace、key、被哪些模块读取 |

写法要求：

- ✅ 写成：`写入 Kafka topic deep.paidads_recall_<biz>_log_<country>`、`读取 Redis SG 4846bc3b10a5d900.elasticredis:10732，key pattern <userId>::<entryPoint>`、`读取 FSE table paidads_warehouse_dim_shop_info，scene brand_max`。
- ❌ 不要写成：`写 Kafka`、`读 Redis 缓存`、`访问 FSE`、`依赖数据库`。
- 若只能从代码确认中间件类型，不能确认具体实例名，必须在对应表格中写：`具体实例名：未在代码/配置中发现`，并在输出日志提醒该 README 需要人工补充。
- 若项目确实不直接访问某类中间件（常见于 FE / pure library / config repo），必须显式写：`本仓库不直接读写 Redis/Kafka/FSE/DB；通过 <具体 API/service，如可确认> 间接访问`，避免读者误判为漏写。

### 1.1.1 中间件实例检索方法（强制）/ Middleware Instance Discovery Playbook

生成「中间件实例明细 / Middleware Instance Details」时，必须按下面顺序检索。目标是把“用了 Kafka/Redis/Config Center”落到真实实例，而不是按 repo 名或 SDU 名猜。

#### A. 先从代码确认运行入口和真实服务名

1. 找入口文件：`main.go`、`cmd/**/main.*`、`server/**/main.*`、`deploy/*.json`、Makefile build target。
2. 对 Go/Spex 服务，优先搜索并记录：
   - `spex.FastInitSpex(...)`
   - `InitSpex(...)`
   - `serverName`
   - `SpexName`
   - `PROJECT_NAME`
   - `MODULE_NAME`
3. 真实 Config Center namespace 必须从上述服务名推导，例如 `adsbidding.ultravdataprocessor` 对应 project `[sp]adsbidding`、namespace `ultravdataprocessor`。如果代码有 `contentads.ultravdataprocessor`，就必须查询 `[sp]contentads / ultravdataprocessor`。
4. 禁止用 repo 名、目录名、SDU path 或垂类名猜 namespace。尤其是合并进程不能拆错：如果代码只有 `contentads.ultravdataprocessor` 一个 content 入口，就不要写 `adsbidding.shopadsultravdataprocessor`、`adsbidding.liveadsultravdataprocessor` 这类未被代码初始化的 namespace。

#### B. 再从代码确认配置 item/key 和字段

1. 搜索配置初始化：
   - `spex.InitConfig`
   - `ConfigCenter`
   - `ConfigCenterClient`
   - `GetConfig`
   - `SetAppConfig`
   - `SetAgentOperationConfig`
2. 记录每个 item/key，例如 `config`、`agent_operation`、`dynamic`、`op_chain_config`、`shop_ads_config`、`live_ads_config`。
3. 记录配置结构体字段到中间件类型的映射：
   - Kafka: `*_kafka`, `*_producer`, `*_consumer`, `brokers`, `topics`, `group_id`
   - Redis: `*_redis`, `redis`, `conn`, `addr`, `key`, `ttl`
   - FSE: `fse`, `feature_store`, `table`, `scene`, `namespace`
   - DB/Hive/S3/ClickHouse/Vespa: 对应 client/config/table/path/schema 字段
4. 若 `InitConfig` 传入的是当前 Spex 服务名变量（如 `SetAppConfig(serverName)`），按入口服务名分别查询；若传入固定 app key（如 `"ultrav_data_processor"`），在 README 中说明这是额外 item/app key，不要把它误写成 Spex namespace。

#### C. 用 Config Center / Kafka / Redis 委托补全 live 实例

1. 对每个从代码确认的 `(project, namespace, item)`，调用可用的 Config Center 委托（优先 `sp-config-center`；若环境仅提供旧工具则用 `ads-config-center-compare-export`）读取 live 配置。
2. 从 Config Center 返回中只提取中间件实例字段：
   - Kafka: broker/bootstrap、topic、consumer group、producer config key
   - Redis: host:port / cluster domain、配置 key、key pattern、TTL、用途
   - 其他中间件：table / namespace / DB / schema / bucket / path
3. Config Center 返回的 `password`、`secret`、`token`、SASL user/password、Redis password 等敏感字段不得写入 README 或输出日志。若某个 config 对象（如 `post_data_spex`）包含 secret，只写 project/group/namespace/item 等非敏感定位信息。
4. 若 Config Center 能读到实例但代码中没有使用该 namespace/key，不能写入 README。先回到 A/B 重新验证代码是否真的会读取它。
5. 若 Config Center 返回多条 rule（按 region/env/az/country），README 里应保留能区分实例的条件摘要，例如 global/BR/liveish、country list、az/region；但不要展开敏感字段。

#### D. 渲染前做一致性检查

1. 每一行中间件实例都要有方向：Consume / Produce / Read / Write / ReadWrite / Read。
2. 每一行都要有 evidence：入口文件、config 初始化文件、配置字段名。
3. 对合并进程，README 要写清楚“一个 Spex namespace + 多个 item/key/field”的关系，例如 content binary 读取 `[sp]contentads / ultravdataaggregator` 下的 `shop_ads_config`、`live_ads_config`、`video_ads_config`、`brand_max_config`。
4. 对未发现的类型，写 `未在代码/配置中发现`；对整体未发现任何中间件，使用下面 1.2 的固定标识。
5. 中英文 README 的实例表必须同步，不能英文有具体 topic 而中文缺失。

### 1.2 未检出与人工确认标识（强制）/ Not-Detected and Manual-Confirmation Markers

当静态扫描代码、配置和可用委托结果后，**没有发现任何 Redis / Kafka / Pulsar / FSE / Vespa / DB / Hive / S3 / ClickHouse / MQ 等中间件实例信息**时，README 仍必须保留「中间件实例明细 / Middleware Instance Details」小节，并写入固定标识：

```
未能自动化检出中间件信息
```

人工 owner 确认该 repo 确实没有直接中间件依赖后，只允许把上述标识改为：

```
已人工确认没有中间件信息
```

生成器后续处理规则：

- 若现有 README 的「中间件实例明细 / Middleware Instance Details」小节中已经包含 `已人工确认没有中间件信息`，增量更新时**不再对该 repo 执行中间件实例检索**，也不得把该标识改回 `未能自动化检出中间件信息`。
- 若相关依赖代码或配置文件发生变化，且人工确认标识仍存在，生成器只在输出日志提醒“存在人工确认标识，已跳过中间件实例检索；如依赖状态已变化，请人工删除该标识后重新生成”，不自动覆盖。
- 若现有 README 中包含 `未能自动化检出中间件信息`，后续生成时应重新尝试自动检索；一旦检出具体实例，替换该标识为实例表。
- 中英文 README 必须保持一致：英文 README 也使用上述中文固定标识，便于机器稳定检测。

### 2. 委托增强（尽量做）/ Delegated enrichment

对静态挖到的每类依赖，调用下方「委托补全」里对应 skill 补全活数据（如 Kafka topic 的真实 consumer group、Redis 集群名、Config Center namespace 全量）。

### 3. 渲染 / Render

在「项目架构 / Architecture」下生成「上下游调用拓扑 / Service Topology」子章节：

1. **Mermaid 流程图**：以本服务为中心，上游在左、下游在右、存储/中间件在下，每条边标注协议类型（BRPC / Spex RPC / HTTP / Kafka 等）。
2. **拓扑表格**：分「上游」「下游」「依赖」三类，每项列服务名、协议/类型、描述。
3. 若委托数据与代码矛盾，**以代码为准**并在日志标注差异。

依赖表必须包含中间件实例列，推荐格式如下：

| 类型 / Type | 方向 / Direction | 具体实例名 / Concrete Instance | 用途 / Purpose | 代码或配置证据 / Evidence |
| ----------- | ---------------- | ------------------------------- | --------------- | -------------------------- |
| Kafka | Produce / Consume | `<topic / producer config / consumer group>` | `<event purpose>` | `<file path / config key>` |
| Redis | Read / Write / ReadWrite | `<cluster/host:port + key pattern>` | `<cache purpose>` | `<file path / config key>` |
| FSE | Read / Write | `<table + scene/namespace/proxy>` | `<feature purpose>` | `<file path / config key>` |
| DB | Read / Write / ReadWrite | `<db/table/DSN config key>` | `<entity purpose>` | `<file path / config key>` |

**更新规则**：增量更新时，只要变更触及依赖相关代码（RPC/MQ/存储/配置/构建文件），本章节**整段重挖**（重跑步骤 1–3、不在旧拓扑上打补丁）；无相关变更则原样保留。

> 因此拓扑无需手工维护清单：依赖一旦从代码移除，下次重挖即消失（探测到才记录、扫不到就不出现）。

## 读码跳过目录 / skip_dirs

通读代码前先确定跳过目录——下列多为**自动生成 / 依赖 / 产物**目录，读取无意义，当作不存在。按探测到的构建工具自动合并 + 通用兜底：

| 探测信号 / Detected | 追加跳过 / Skip |
| ------------------ | -------------- |
| 通用兜底（始终） | `vendor/`, `.git/`, `node_modules/`, `dist/`, `build/`, `output/`, `bin/`, `logs/`, `testdata/`, `mock/`, `tmp/` |
| `MODULE.bazel` / `WORKSPACE` (Bazel) | `bazel-*/`, `external/`, `proto/spex/gen/`, `proto/spex/sp_proto/` |
| `go.mod` (Go)       | `vendor/`, `third_party/` |
| `package.json` (Node/FE) | `node_modules/`, `dist/`, `.next/`, `coverage/` |

## 委托补全 / Skill Delegation Map

生成各章节时，按依赖/内容类型调用对应 skill 取**当下真实**的数据：

| 内容类型 / Content | 委托 skill | 用途 |
| ----------------- | --------- | ---- |
| Kafka / Pulsar topic、consumer group、lag | `ads-kafka-info` | 补全消息队列依赖明细 |
| Redis / 缓存集群信息 | `ads-cachecloud-info` | 补全存储依赖、集群名/分片 |
| Config Center namespace / key | `sp-config-center`（优先）或 `ads-config-center-compare-export` | 补全配置依赖、namespace、item/key、live 配置中的中间件实例 |
| 部署拓扑 / SDU / service tree / CMDB | `sp-space` | 补全部署与服务树信息 |
| 监控大盘链接 | `sp-grafana` | 按 service name 搜大盘，填监控章节 |
| 业务术语解释 | `sra-glossary` | 业务术语表章节、术语准确性 |
| 第三方依赖源码 | `sra-code-search` | 核对外部依赖的真实接口 |

> 调用前先判断环境：CI 中某些平台 token 可能缺失，缺失即跳过该委托并降级，不要因此报错中断。
