# spec mode 逐章节引导

> 供 spec mode Step 5 使用的交互式填充引导。

## 编号分配规则

- 01, 02 是 foundation 文件（固定）
- 如果 02 不是 `02-core-concepts.md` 且不存在 `03-core-concepts.md`，03 保留给 core-concepts
- component spec 从第一个可用编号开始
- contract（--contract）编号放在所有 component spec 之后
- 编号统一使用两位数字格式（03, 04, ...）

## 逐章节引导问题

### N.1 组件目标

- 这个组件的核心职责是什么？（一段话描述做什么、不做什么）
- 预填信息来源：01 接口表中该组件的行（阶段/输入/输出/上下游）
- 引导问题：
  - 必须执行什么？（mandatory checks, validation, rules）
  - 必须避免什么？（anti-patterns, out-of-scope behavior）

### N.2 输入契约

- 引导问题：
  - 这个组件接收哪些输入？
  - 输入有哪些组合方式？（A only, A+B, A+B+C）
  - 每种组合下组件的重点行为是什么？
  - 输入的解析规则是什么？（格式校验、默认值、异常处理）

### N.3 输出契约

- 引导问题：
  - 组件产出什么？（文件、stdout、数据结构）
  - 必需字段有哪些？类型和含义？
  - 有没有输出格式示例？

### N.4 执行流程

- 引导问题：
  - 从输入到输出，组件按什么步骤工作？
  - 每个步骤的名称和描述？
  - 步骤之间有没有条件分支或循环？
  - 哪些步骤可能失败？失败后怎么处理？

### N.5 规则执行

- 引导问题：
  - 有哪些必须检查的规则/约束？
  - 每条规则在什么时机检查？（哪个 Step）
  - 检查失败时怎么处理？（报错/警告/跳过）
  - 能否提供正例和反例？

### N.6 上下游契约（可选）

- 引导问题：
  - 对上游组件有什么要求？（上游必须提供什么）
  - 对下游组件做什么承诺？（下游可以依赖什么）

### N.7 变更护栏（可选）

- 引导问题：
  - 如果修改了这个 spec，哪些文件/组件需要同步更新？
  - 有没有跨 spec 的字段依赖？
