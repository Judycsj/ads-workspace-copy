# 问题分类规则/Question Classification Rules

本文件定义 `ads-kb-eval` 技能的问题分类判定规则。分类在路由和评分之前执行，决定问题的后续处理方式。

---

## 分类总览/Classification Overview

| 类别/Type | 定义 | 后续处理 | 评分 |
|-----------|------|---------|------|
| **kb** | 概念、原理、架构、流程、配置等可从 KB 静态文档回答的知识型问题 | → Step 2 路由 + 评分 | 1-5 分 |
| **指标查询** | 问动态变化的指标数值或统计数据，KB 应提供指标定义 + 查询方式 | → Step 2 路由 + 指标查询标准评分 | 1-5 分（双维度） |
| **task** | 需要执行操作（生成 SQL/报告/代码、跑实验）或属于操作性 SOP/Runbook | → 匹配执行技能，跳过评分 | N/A |
| **无效问题** | 表述不清、超出 KB 范畴、或本质上是研究/分析任务而非知识查询 | → 标记原因，跳过评分 | N/A |

---

## 判定流程/Classification Decision Flow

按以下顺序依次判定，**命中即停**：

```
问题文本
  │
  ├─ [1] 动词信号检测 → 是否为研究/分析任务？ → 是 → 无效问题
  │
  ├─ [2] 数据时效性检测 → 是否问动态/实时数据？ → 是 → 指标查询
  │
  ├─ [3] 操作性检测 → 是否要求执行操作或诊断排查？ → 是 → task
  │
  ├─ [4] KB 范畴检测 → 是否超出当前 KB 覆盖范畴？ → 是 → 无效问题
  │
  └─ [5] 默认 → kb
```

---

## 详细判定规则/Detailed Classification Rules

### 规则 1: 研究/分析任务检测（→ 无效问题）

**核心原则**：如果回答问题需要**独立推理、实验设计、方案探索或创造性分析**，而非从文档中查找事实，则不是 KB 知识查询。

**动词信号**（问题中出现以下动词模式时高度怀疑为研究任务）：

| 信号类型 | 动词/短语模式 | 说明 |
|---------|-------------|------|
| **评估/判断** | "评估是否最优"、"判断是否应该"、"评估 X 是否合理" | 需要对比实验或专家判断 |
| **识别/发现** | "识别冗余特征"、"识别缺少的信息"、"发现问题" | 需要 gap 分析或探索性研究 |
| **分析影响** | "分析 X 对 Y 的影响"、"分析 gap"、"分析缺陷" | 需要因果推理或定量分析 |
| **方案设计** | "提出解决方案"、"有哪些可行策略"、"如何改进" | 需要研究设计和创新思考 |
| **梯度/数学推导** | "梯度分析"、"反向传播分析"、"抽象为公式" | 需要数学推导 |

**注意区分**：

| 问题 | 分类 | 原因 |
|------|------|------|
| "当前校准架构是什么？" | **kb** | 问事实/现状 |
| "分析当前校准的缺陷，提出解决方案" | **无效问题** | 需要分析判断 + 方案设计 |
| "pGMV 的计算公式是什么？" | **kb** | 问具体公式 |
| "评估 pGMV 与实际 GMV 的差异" | **无效问题** | 需要数据分析对比 |
| "模型有哪些预估目标？" | **kb** | 问事实 |
| "识别预估目标与业务目标的 gap" | **无效问题** | 需要系统分析推理 |
| "UniCR 的特征体系有哪些？" | **kb** | 问事实列表 |
| "识别当前特征对业务目标缺少哪些信息" | **无效问题** | 需要 gap 分析 |
| "pricing_type 在特征体系中吗？" | **kb** | 问事实 |
| "评估 pricing_type 是否应该加入特征" | **无效问题** | 需要实验评估 |

**混合问题处理**：如果问题前半是事实查询、后半是分析评估（如"列出特征并评估是否完整"），按以下规则：
- 如果事实部分是问题的主体 → 保留为 **kb**，在 Reason 列标注"后半为研究分析"
- 如果分析部分是问题的主体 → 标为 **无效问题**

### 规则 2: 动态数据/实时指标检测（→ 指标查询）

**核心原则**：如果答案随时间变化、需要查询实时系统才能获得具体值，则为指标查询。KB 应提供指标定义和查询方式，而非具体数值。

**信号词**：

| 信号类型 | 关键词/模式 | 示例 |
|---------|-----------|------|
| **时间限定** | "最近一周"、"当前"、"今天"、"每天" | "统计最近一周 PCoC" |
| **统计动词** | "统计 X 数量"、"X 占比是多少"、"X 分布" | "样本场景占比、region 占比" |
| **运维数据** | "资源数"、"利用率"、"QPS"、"延迟"、"耗时" | "serving 所需资源数" |
| **表现数据** | "模型表现"、"效果数据"、"达标率" | "模型在各分组上的表现" |

**注意区分**：

| 问题 | 分类 | 原因 |
|------|------|------|
| "PCoC 的定义是什么？" | **kb** | 问概念定义（静态） |
| "统计最近一周 PCoC 数据" | **指标查询** | 问实时数值（动态） |
| "模型更新频次是多少？" | **kb** | 问配置/策略（静态） |
| "统计训练资源利用率" | **指标查询** | 问运维数据（动态） |
| "模型有哪些评估指标？" | **kb** | 问指标体系（静态） |
| "模型 params 和 FLOPs 是多少？" | **kb** | 问模型属性（静态，虽然 KB 可能缺失） |

**边界情况**：问题同时涉及静态知识和动态数据时（如"梳理样本生产链路，以及资源消耗情况"），按主体判断：
- 主体是链路/架构 → **kb**，在 Reason 列标注"部分涉及动态数据"
- 主体是数据/统计 → **指标查询**

### 规则 3: 操作性/SOP 检测（→ task）

**核心原则**：如果问题要求执行具体操作、提供诊断排查步骤、或属于 troubleshooting runbook 内容，则为 task。

**信号词**：

| 信号类型 | 关键词/模式 | 示例 |
|---------|-----------|------|
| **诊断排查** | "诊断方法"、"排查步骤"、"troubleshoot"、"如何排查" | "loss 突增时的诊断方法" |
| **操作执行** | "如何生成"、"如何自动化"、"如何修改配置"、"给出...SQL/代码" | "如何自动生成 AB 实验指标" |
| **代码修改** | "应如何修改"、"需要改哪些配置" | "设置不同学习率应如何修改" |
| **SOP 流程** | "操作步骤"、"执行流程"、"部署流程" | "从部署到推理的完整流程" |

**注意区分**：

| 问题 | 分类 | 原因 |
|------|------|------|
| "校准系统的架构是什么？" | **kb** | 问架构知识 |
| "PCoC 高估时的诊断方法是什么？" | **task** | 问排查操作步骤 |
| "训练 pipeline 的关键配置有哪些？" | **kb** | 问配置知识 |
| "如何修改 embedding 学习率？" | **task** | 问具体操作方法 |
| "模型部署后的在线推理链路是什么？" | **kb** | 问系统流程知识 |
| "如何自动生成 AB 实验指标数据？" | **task** | 问工具使用/自动化 |

**与 kb 的灰色地带**：一些"怎么做"的问题可能是 kb（问系统如何工作）也可能是 task（问用户如何操作）。判断标准：
- **系统怎么做** → kb（如"pGMV 校准系统怎么运行的？"）
- **用户怎么做** → task（如"loss 异常时用户应该怎么排查？"）

### 规则 4: KB 范畴检测（→ 无效问题）

**核心原则**：问题所问的知识完全不在当前 KB doc 的覆盖范畴内。

**信号词**（问题中出现以下关键词时高度怀疑超出 KB 范畴）：

| 信号类型 | 关键词/模式 | 示例 |
|---------|-----------|------|
| **论文/学术** | "论文"、"paper"、"一致性校验"、"与 X 方法的差异" | "校验模型实现与论文方法一致" |
| **训练平台/EGO** | "slot"、"sparse embedding"、"dense weight"、"过拟合"、"欠拟合"、"学习率配置"、"EGO" | "判断 slot 的 embedding 是否过拟合" |
| **项目产出物** | "推全效果"、"实验效果"、"TD 设计"、"历史 TD"、"上线报告" | "获取模型推全时的实验效果和 TD 设计" |
| **代码/SQL 生成** | "给出...SQL"、"写出...代码"、"生成...脚本" | "给出 merge_bucket op 的模拟 SQL" |

**常见超范畴场景**：

| 场景 | 示例 | 原因 |
|------|------|------|
| **训练平台/EGO** | "slot 过拟合如何判断"、"embedding 学习率配置" | 属于 EGO 训练平台知识库 |
| **论文对比** | "实现与论文的差异"、"与论文方法一致性校验" | KB 不涉及学术论文 |
| **项目历史** | "推全实验效果"、"历史 TD 设计" | 属于项目文档，不在 core-knowledge |
| **表述不清** | 缺少主语、无法判断具体指向 | 无法分类和路由 |

## 模式 B 重分类/Mode B Reclassification

模式 B（模块评测）重新评分时，除了更新评分外，**应同时审查分类合理性**：

1. 已有问题中 Type 为 `kb` 但评分持续为 1/5 的问题 → 检查是否应重分类为**无效问题**
2. 备注列标有"问题不合理"但 Type 仍为 `kb` 的问题 → 确认是否需要改 Type
3. 新增的审计模式：用户可显式要求"审计问题质量"（如本次 §2.2 审计案例），此时按以上规则逐题检查分类

## 分类理由模板/Classification Reason Templates

分类完成后，Reason 列应填写判定理由。以下为各类别的理由模板：

| 类别 | Reason 格式 | 示例 |
|------|-----------|------|
| **kb** | `—`（默认不填）或具体路由说明 | `—` |
| **指标查询** | `<信号描述>：<具体说明>` | `动态统计数据：样本占比/region占比 随时间变化` |
| **task** | `<操作类型>：<具体说明>` | `操作性 SOP：loss 突增诊断属于 troubleshooting runbook` |
| **无效问题** | `<不合理原因>：<具体说明>` | `研究分析任务：需数学推导和实验验证，非 KB 知识查询` |
