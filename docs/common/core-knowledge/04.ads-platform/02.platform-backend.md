## 4.2 Ads Platform Backend Overview

Ads Platform Backend is the advertiser-facing backend layer of Paid Ads. It standardizes campaign creation and management, turns Seller Center operations into ad supply, and connects productized workflows with ads-DB, status sync, wallet, budget, reporting, and delivery systems.

The platform backend is the engineering layer that delivers the **2026 Platform Product OKR** (see [2026 Q1/Q2 Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit)). It powers three OKR-aligned workstreams:

1. **Ad creation & full-funnel experience** — PC creation success rate 86% → 90%, APP 40% → 50%. `ads-marketing`, `ads_service`, and `ultimate_ads_service` provide stable creation/management APIs and a predictable campaign-level state machine, backing PC/APP differentiated flows (GMS / Multi-Product / Single-Product) and bulk operations.
2. **Adoption of key projects (GMS, Escrow Top-up, New Product Ads)** — `ads-marketing` hosts the GMS campaign lifecycle and Rapid Boost; `topup` / `auto-topup` / `ads-account-balance` drive the Escrow Top-up Budget / Platform GMV ratio; the New Product Ads API embeds ad creation into the product upload workflow to lift the new-entry adoption rate.
3. **AI-powered diagnosis & seller guidance** — `ads-derived-data-service`, Report, and the Diagnosis backend supply the data foundation for the AI Assistant (GMS reports, daily automated inspection, weekly data digests) and recommendation-card adoption on PC/APP homepages.

> Business reference: [2026 Q1/Q2 Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit) — the deck defines creation success rate, recommendation adoption, and Escrow / GMS / New Product Ads as the headline business outcomes this backend supports.

> **Per-layer responsibilities** (read top to bottom as "user → business orchestration → state / funds plane → data base"):
>
> - **1. Entrance** — Expose seller and operator workflows.
> - **2. Business API** — Upper row orchestrates seller-facing flows; lower row owns the unified ads CRUD/write contracts.
> - **3. State Sync & Funds** — Two co-equal sub-domains: state propagation (CDC / derived caches / resharding) and funds (credit, top-up, balance, rebates).
> - **4. Core Data Store** — Persistent data base shared by all upper layers: ads-DB sharded write model plus low-latency Redis cache.

### 4.2.3 Main Frontend Entry Points

Seller Center is the primary advertiser entry point, but the **five frontend entries differ sharply by target seller tier and product positioning**. The table below contrasts each entry's audience, representative pages, and owning backend; business background lives in the [Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit).

| Entry | Target seller / scenario | Representative pages / modules | Primary backend |
| --- | --- | --- | --- |
| Seller Center · PC | Top / mid-tier sellers — heavy data analysis, complex workflows | Home Intelligent Insights module · Ads List (Shop-Ads + other products) · creation page (Single / Multi-Product / Shop-Ads differentiation) · diagnosis report · campaign pop-ups | `ads-marketing` |
| Seller Center · APP | Long-tail / micro sellers — one-tap operations, smart guidance | Rebuilt homepage · Ads List entry (CTR ~52%) · creation page with default product selection · Performance module · Ads Detail (budget-up / ROAS-down hints) · GMS-style recommendation card | `ads-marketing` |
| Listing Page | All active sellers — high-traffic touchpoint, new-feature reach | "Publish to Advertise" via New Product Ads API · Listing-side feature introduction cards | `ads-marketing` (New Product Ads API) |
| Biz Advice / AI Assistant | Cross-tier sellers — AI-driven business advice | GMS reports · daily automated inspection · weekly data digests · Balance / Bid / Budget recommendations | `ads-derived-data-service`, Diagnosis backend |
| Backend Admin / CRM / SRM / Debug Bot | Internal — BD, platform ops, QA, SRE | Approval flows · whitelist / fee-rate config · Quick Debug · debugging tools | `ultimate_ads_service` |

> PC and APP differ at the **seller-tier** level: PC serves top/mid-tier merchants who drive most platform revenue and need advanced analytics, while APP serves long-tail / micro merchants who need simplified one-tap flows. Listing is the cross-tier high-traffic touchpoint, Biz Advice / AI Assistant is the AI-driven advisory surface, and Backend Admin covers internal operations.

> **Legend** — symbol decoding:
>
> - Filled lavender = **Aggregate Root**.
> - Solid white = **Entity**.
> - Dashed border = **Value Object**.
> - Yellow = **Domain Service**.
> - Pink parallelogram = **Domain Event**.
> - Dashed light lavender = **External Context**, reaching the core only through the Lifecycle Service's **Anti-Corruption Layer (ACL)**.
> - Solid lines = aggregation.
> - Dotted lines = composition / VO reference / ACL flow.
> - Thick arrows `==>` = event publication.

> **Note** — five core invariants are pinned to the diagram's node annotations: data model, placement/pricing immutability, lifecycle drivers, paid vs. free credit, plus three Budget storage conventions worth memorizing:
>
> - `daily_quota=0` is a **sentinel meaning "unlimited"** — not a literal zero daily budget; eligibility checks must short-circuit on this value.
> - All monetary amounts are stored as integers with a `×10⁵` magnification (e.g. `$1.23` → `123000`) to avoid float precision; readers and writers must pair the multiply / divide.
> - Selected placements support `quota_splitting` — splitting one campaign's daily quota across hourly / sub-placement / experiment buckets for pacing or holdouts.

### 4.2.7 ads_service vs UAS Division of Responsibility

The platform core write gateway is split into two layers: `ads_service` (legacy) and `ultimate_ads_service / UAS` (new unified entry). They co-exist, but **UAS is now the authoritative entry for all set/update across every ad type**, while `ads_service` retreats to long-tail business gateway duty (accounts, reporting, keyword, Display Ads, fraud, whitelist).

#### Responsibility Comparison

| Dimension | `ads_service` (legacy gateway) | `ultimate_ads_service` (UAS, new gateway) |
|-----------|-------------------------------|-----------------------------------------|
| SPEX namespace | `paidads.ads_service.*` (~110 active RPCs, proto ~4100 lines) | `paidads.ultimate_ads_service.*` (65+ active RPCs) |
| Error code range | `ERROR_*` (custom per business domain) | `Constant.Error` (`496000000–496100000`) |
| Write scope | Banner Ads CRUD, Campaign Day CRUD, keyword black/white-list, full Display Ads pipeline, Item Boost, fraud users, whitelist type management | All mainstream ad-type `SetAdvertiseBatch*` / `MassUpdate*`, account set/get, target audience groups, Brand Consideration / Search Brand Ads / Product GMS / Background ROI-3 GMS, Voucher, Audit/Operation Log queries |
| Ad types written | Banner Ads; other mainstream types are deprecated (see "Deprecated RPCs" below) | Product / Shop / LiveStream / Video / Search Brand / Brand Consideration / Product GMS / Background ROI-3 GMS / Auto Product Ads |
| Write entries | `set_advertise_batch` (deprecated → UAS); `create_banner_ads` etc. still active | `SetAdvertiseBatchProductV2`, `SetAdvertiseBatchShopV2`, `SetAdvertiseBatchLiveStream`, `SetAdvertiseBatchVideo`, `SetAdvertiseBatchSearchBrand`, `SetAdvertiseBatchBrandConsiderationAds`, ... |

### 4.2.8 CRUD API Design (UAS Perspective)

Once `ads_service` retreats to long-tail business gateway duty (see §4.2.7), all ad-type writes converge on UAS. This section captures how UAS structures those writes so service owners and reviewers know which package to touch and what the write pipeline guarantees.

UAS organizes its API along three dimensions: **Entity × Action × Product Type**.

| Dimension | Values |
|-----------|--------|
| **Entity** | Campaign, Ad / Advertisement, Keyword, Item, Creative, AdsAccount, TargetAudienceGroup, Voucher, Package, WhitelistMeta |
| **Action** | `SetAdvertiseBatch*` (create/edit batch), `MassUpdate*` (batch update), `BatchDeleteHide` (soft delete / hide), `Get*`/`Query*`, `Check*`, `Refresh*`, `Add*`, `Approve*` / `Qc*` (QC approval) |
| **Product Type** | Product (Search Product Ads), Shop, LiveStream, Video, SearchBrand, BrandConsideration, ProductGms, BackgroundRoiThreeGms, AutoProductAds, Brand Group Keyword |

Each Action is registered uniformly in `setup/controller.go` and dispatched to its `internal/set_*` or `internal/mass_update_*` package:

| Package | Ad Type | Primary Write Tables |
|---------|---------|----------------------|
| `set_product_ads` | Search Product Ads | `advertisement_tab`, `ad_keyword_tab`, `campaign_tab` |
| `set_shop_ads` | Shop Ads | `advertisement_tab`, `campaign_tab` |
| `set_live_stream_ads` | Live Ads | `advertisement_tab`, `live_stream_ads_index_tab` |
| `set_video_ads` | Video Ads | `advertisement_tab`, `video_ads_index_tab` |
| `set_product_gms_ads` | Product GMS | `product_ad_tab`, `product_campaign_tab`, `product_gms_item_tab` |
| `set_background_roi_three_gms_ads` | Background ROI-3 GMS (pt=29) | `background_roi_three_gms_ads_index_tab` |
| `brand_consideration_ads` | Brand Consideration Ads | `brand_consideration_ads_index_tab` |
| `search_brand_ads` | Search Brand Ads | `searchbrand_ads_index_tab`, `searchbrand_package_tab` |
| `auto_product_ads` | Auto Product Ads | `item_ads_index_v2_tab` |
| `automated_ads_solution` | Automated Ads Solution | `campaign_tab` |

Every write goes through: (1) `internal/locker` (Redis distributed lock) for concurrency safety; (2) `db_manager` (wraps ads-db-lib) for primary table writes; (3) `internal/ads_audit/` + `internal/ads_audit_info/` for audit logging; (4) Kafka publish for downstream consumers (sycner / indexer); (5) `internal/cache` invalidation for related Redis keys.

### 4.2.9 Ad Lifecycle and State Machine

Ad status in the platform backend is modeled in **three layers**, driven by five categories of triggers: user actions, audit, item state, inventory, and external sync (policy / compliance).

#### Three-Layer Status Model

| Layer | Field Location | Description |
|-------|----------------|-------------|
| **CampaignStatus** | `campaign_tab.status` | Campaign-level seller-visible control state: `ACTIVE` / `PAUSED` / `DELETED` / `SCHEDULED` / `ENDED` |
| **AdStatus** | `advertisement_tab.status` (per-product extensions: `product_ad_tab.status`, `live_stream_ads_index_tab.status`, etc.) | Ad-item level state: `ACTIVE` / `PAUSED` / `REJECTED` / `BANNED` / `DELETED` / `DRAFT` |
| **DeliveryStatus** (servable state) | Indexer writes `is_active`; ads-engine computes at runtime | Composite of Campaign × Ad × Item × Account: `SERVING` / `OUT_OF_BUDGET` / `OUT_OF_BALANCE` / `OUT_OF_STOCK` / `OUT_OF_SCHEDULE` / `BANNED` |

#### State Transition Triggers (5 categories)

#### Dual Sync Mechanism: Real-time + Periodic Reconciliation

```mermaid
flowchart LR
    DB[(ads-DB)] -->|binlog| RESHARDER[ads-resharder] -->|sharded| KAFKA[(Kafka: gds/iis/ips/ils/abs/mcn/due/algo_*)]
```

### 4.2.11 GMS (Shop GMV Max) Full Picture

#### Definition

**GMS** = **Shop GMV Max**, an intelligent ad strategy maximizing shop-level GMV—the seller only needs to enable GMS, and the platform handles selection, bidding, budget, and voucher automatically. Inside Shopee Paid Ads, GMS and "traditional GMV Max (Discovery / Search GMV Max etc., the oCPC family)" are **two different systems**:

| Form | pt | Billing | Item Source | bid-sense API | Voucher | UAS Handler |
|------|----|---------|-------------|---------------|---------|-------------|
| **GMS (Shop GMV Max)** | 24 / 27 | Normal billing | Algo `gms_pool` (offline Redis) → `add_missing_item` | `GetItemSelectionGMS` | Normal bidding | `product_gms` package |
| **Package Non-Ads** (GMS Package byproduct) | 29 + `is_nominated_package` | ❌ no billing | Algo `roi3_pool` → `refresh_item` | `GetItemSelectionROI3` | Package voucher | `background_roi_three_gms` package |
| **Organic Non-Ads** | 29 + `is_organic` | ❌ no billing | DE Hive 30D1O | — | Organic voucher | `background_roi_three_gms` package |

GMS vs traditional GMV Max:
- Traditional GMV Max is an **intra-Campaign** intelligent bidding mode (based on Simple Mode / oCPC; does not change Campaign form)
- GMS is a **shop-level** automation product (selection + bidding + auto voucher) with its own pt (24/27/29) and its own selection pool

#### Escrow (Cost Management) Integration

Escrow is a "fixed-rate auto-management" mode for large / KA sellers (vs. real-time per-consumption billing):

| Component | Responsibility |
|-----------|---------------|
| `auto-topup.auto-escrow-order-scanner` cron | Drives escrow order state machine `pending → processing → completed` (30 min buffer) |
| `auto-topup.auto-escrow-aggregate-scanner` cron | Updates escrow aggregate cache |
| UAS `auto-escrow-fixed-program-whitelister` cron | Imports escrow fixed-rate whitelist from CSV (`--force-aas`, `--skip-existing`, `--only-existing`, `--parallelism`) |
| UAS `batch-set-escrow-fixed-program-whitelister-admin` cron | Batch-set escrow whitelist from admin DB (`--fetch-batch-size`, default 200) |
| ads-status-syncer `auto-escrow-whitelist-sync` cron | Syncs auto-escrow whitelist |
| UAS `campaign-accelerator-sync` cron | Pushes Campaign Accelerator package config to advertiser account and GMS Campaign (incl. sign-up/live/post-live escrow ratio) |
| topup `service/permission/` | Escrow permission check (GMV Max / Livestream / Search Brand) |

#### Credit Type / Applicability

Each Credit record's usability is jointly determined by 4 fields:

| Field | Values | Effect |
|-------|--------|--------|
| `credit_type` | Paid (seller purchase) / Free (platform voucher, incentive) | Routes to `ads_credit_tab` or `display_ads_credit_tab` |
| `effective_type` | `0` (general) or specific placement enum | Controls eligible ad placement types (search, discovery, display) |
| `consumption_type` | Ad product type | Controls eligible ad product types |
| `expire_at` | Expiry timestamp | Scanned by `paidads.topup.list_unexpired_free_ads_credit` |

Deduction strictly enforces `effective_type` + `consumption_type`; non-matching credits are not consumed.

#### Operational Notes

- **Overdue Balance**: High-concurrency deduction → overcharge → record in `campaign_overdue_balance_tab` → `offset_overdue_balance` worker offsets periodically; query via `paidads.topup.get_campaign_overdue_balance`
- **PENDING recovery**: `paidads.topup.trigger_unfinish_topup` replays stuck translog; worker also calls `ProcessPending` at startup and 15 min after startup
- **Translog Kafka emission**: every deduction / top-up writes to `deduction_translog` Kafka topic (per region) for downstream billing / reporting / reconciliation
- **CMDB**: `shopee.paidads.advertiser_platform.platform.advertiser_platform.topupsvs`
- **Grafana**: [Topup Services Dashboard](https://monitoring.infra.sz.shopee.io/grafana/d/Us9zKo5Vz/topup-services-copy?orgId=39)

### 4.2.16 Source Update Mechanism

This chapter contains two kinds of content:
1. **Hand-written**: business concepts, architecture diagrams, positioning, cross-repo narrative (4.2, 4.2.1–4.2.4, 4.2.6–4.2.15 prose)
2. **Code-scanned**: per-repo facts that change when code lands — cron-task lists, SPEX handler-package buckets, deploy module names, CDC topic / JobType lists, ads-db-lib table dict

Two scripts in the [`ads-platform-be-overview-generate`](../../../../skills/team/01.ads-engineering/ads-platform-be-overview-generate/) skill cover the two halves:

**(a) Document generator** — rebuilds the bilingual overview from profiles + READMEs (hand-curated cross-repo prose). Layered Architecture rendering is controlled by `--layered-arch-format` (`table` / `diagram` / `both`).

```bash
uv run skills/team/01.ads-engineering/ads-platform-be-overview-generate/scripts/generate_ads_platform_be_overview.py \
  --use-local-sources \
  --scan-projects projects/gitlab/ads-platform \
  --layered-arch-format diagram \
  --output docs/common/core-knowledge/04.ads-platform/02.platform-backend.md \
  --language en
```

**(b) Enrich script** — walks each repo under `projects/gitlab/ads-platform/`, runs the scanners listed below, and writes a single source-of-truth side document `02.platform-backend.scanned-facts.md` that contributors can diff against this overview.

```bash
uv run skills/team/01.ads-engineering/ads-platform-be-overview-generate/scripts/enrich_platform_be.py
# Output: docs/common/core-knowledge/04.ads-platform/02.platform-backend.scanned-facts.md
# Use --print-json to get a machine-readable summary instead.
```

**Implemented scanners** (`scripts/scanners.py`):

| Info | Source | Extraction |
|------|--------|-----------|
| `cmd/` binaries | `<repo>/cmd/<binary>/` | directory list |
| Cron task list (Strategy A) | `<repo>/cmd/<cron-binary>/*.go` excluding boilerplate | filename scan + Go doc-comment |
| Cron task list (Strategy B) | `<repo>/cmd/<cron-binary>/command.go` with `[]commandConfig{...}` | brace-tracked regex on `Name:` + `Usage:` + `Run:` |
| SDU deploy modules | `<repo>/deploy/*.json` | JSON parse → `project_name.module_name`, `run.command`, `base_image` |
| Internal layering | `<repo>/internal/<subdir>/` | directory list |
| SPEX handler packages | `<repo>/internal/(set_\|get_\|mass_update_\|query\|job_...)*` | directory list bucketed by prefix |
| Proto signature | `<repo>/sp_proto/paidads/<repo>.proto` | line count + `package` + `rpc` regex |
| CDC topic / handler | `ads-status-syncer/cmd/ads_status_syncer/handler_*.go` | filename scan |
| JobType enum | `ads-status-syncer/internal/consumer/consts_enum.go` | `const(...)` block walk for `JobType\w+` identifiers |
| README ## Monitoring / ## Deployment | `docs/common/readme/<repo>/README.md` | level-2 heading extraction |
| ads-db-lib table dict | `ads-db-lib/<group>/*_tab.go` | regex on `TableName = "..."` + `type *Tab struct` |
| Wire DI symbols | `<repo>/internal/setup/wire.go` | regex on `*Client` / `*Repository` / `*DSN` identifiers |

> **What if code changes**: Run (b) from ads-workspace root and compare the regenerated `02.platform-backend.scanned-facts.md` against the per-section claims in this overview. The enrich script is read-only — it never edits the main overview — so you stay in control of when to backfill scanned numbers into the prose. The hand-written narrative still owns the *why* (business logic, design decisions, cross-repo flow); the side doc owns the *what* (counts, names, paths derivable from code).
