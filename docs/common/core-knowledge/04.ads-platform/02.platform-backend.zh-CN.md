## 4.2 平台后端架构总览/Platform Backend Overview

平台后端是 Paid Ads 面向广告主的后端能力层。它把 Seller Center 等前端入口的创建、管理、充值、报表和诊断操作，标准化为广告供给，并连接 ads-DB、状态同步、钱包、预算、报表和投放链路。

平台后端是 **2026 Platform 产品 OKR**（参见 [2026 Q1/Q2 Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit)）落地的工程层，承载三条 OKR 对齐的工作主线：

1. **创编与全链路体验**——PC 创编成功率 86% → 90%、APP 40% → 50%。通过 `ads-marketing`、`ads_service`、`ultimate_ads_service` 提供稳定的创编/管理 API 和可预测的活动级状态机，支撑 PC/APP 差异化投放（全店 / 多品 / 单品）与 Bulk 操作。
2. **重点项目 Adoption（GMS、Escrow 货款打通、新品广告）**——`ads-marketing` 承载 GMS lifecycle 与 Rapid Boost；`topup` / `auto-topup` / `ads-account-balance` 支撑 Escrow Top-up Budget / Platform GMV 占比目标；新品广告 API 把创编能力嵌入商品上传流程，拉升新入口采纳率。
3. **AI 驱动的诊断与经营建议**——`ads-derived-data-service`、Report 与诊断后端为 AI Agent（GMS 投放报告、每日自动巡检、周度数据解读）和 PC/APP 首页推荐卡采纳率提供数据底座。

> 业务参考：[2026 Q1/Q2 Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit) —— Slides 把创编成功率、推荐卡采纳率以及 Escrow / GMS / 新品广告作为本后端要支撑的关键业务结果。

> **每层职责**（自上而下读为"用户 → 业务编排 → 状态/资金平面 → 数据底座"）：
>
> - **1. 入口层** —— 承载卖家和运营工作流。
> - **2. 业务 API 层** —— 上排承接卖家侧业务编排，下排是统一的广告 CRUD/写入契约。
> - **3. 状态同步 & 资金预算** —— 两个并列子域：状态传播（CDC / 衍生缓存 / 重分片）与资金（credit、充值、余额、返利）。
> - **4. 核心数据底座** —— 所有上层共享的持久化数据底座：ads-DB 分片写模型 + 低延迟 Redis 缓存。

### 4.2.3 主要前端入口/Main Frontend Entry Points

Seller Center 是广告主的主入口，但**五个前端入口按目标商家分层和产品定位差异显著**——下表对比每个入口的目标商家、代表页面和主要后端，业务背景可参考 [Platform OKR Review](https://docs.google.com/presentation/d/1hRuJf5QR0GQAs67h9yO6reV77fq7s56j8tmB0fDX-JQ/edit)。

| 入口 | 目标商家 / 场景 | 代表页面 / 模块 | 主要后端 |
| --- | --- | --- | --- |
| Seller Center · PC | Top / Mid-tier seller，重数据分析、复杂工作流 | 首页智能推荐模块、Ads List（全店 + 其他产品）、创建页（单品 / 多品 / 全店差异化）、诊断报告、大促弹窗 | `ads-marketing` |
| Seller Center · APP | Long-tail / micro seller，重一键操作和智能引导 | 重排版首页、Ads List 入口（CTR ~52%）、创建页（默认选品）、Performance、Ads Detail 提预算/降 ROAS 引导、GMS 特殊样式推荐卡 | `ads-marketing` |
| Listing Page | 全量 active seller，高流量触点、新功能触达 | "Publish to Advertise"（新品广告 API）、Listing 触点引导卡 | `ads-marketing`（新品广告 API） |
| Biz Advice / AI Assistant | 跨 tier 商家，AI 经营建议入口 | GMS 投放报告、每日自动巡检、周度数据解读、余额 / 出价 / 预算智能建议 | `ads-derived-data-service`、诊断后端 |
| Backend Admin / CRM / SRM / Debug Bot | BD、平台运营、QA、SRE 内部入口 | 审批流、白名单/费率配置、Quick Debug、调试工具 | `ultimate_ads_service` |

> PC 与 APP 入口的根本差异在于 **seller tier 定位**——PC 服务于贡献主营收的 top/mid 商家、强调高级数据分析；APP 服务于长尾 / micro 商家、强调简化一键操作和智能引导。Listing 是跨 tier 的高流量触点，Biz Advice / AI Assistant 是 AI 驱动的经营入口，Backend Admin 覆盖内部运营。

>
> - `daily_quota=0` 是「不限预算」的**哨兵值**，不是日预算 0 块；预算判定逻辑必须先短路这个特殊值。

> - 部分 placement 支持 `quota_splitting`——把单条 campaign 日预算切到「按小时 / 按子版位 / 按实验桶」分桶，用于 pacing 或实验 holdout。

### 4.2.8 CRUD API 设计/CRUD API Design (UAS Perspective)

在 `ads_service` 退守为长尾业务网关之后（参见 §4.2.7），所有广告类型的写入收敛到 UAS。本节梳理 UAS 如何组织这些写入接口，让服务 owner 和 reviewer 清楚应该改哪个包，以及写入流水线提供哪些保证。

UAS 用 **Entity × Action × Product Type** 三维度组织接口：

| 维度 | 取值 |
|------|------|
| **Entity** | Campaign（活动）、Ad / Advertisement、Keyword、Item、Creative、AdsAccount、TargetAudienceGroup、Voucher、Package、WhitelistMeta |
| **Action** | `SetAdvertiseBatch*`（创建/编辑批量）、`MassUpdate*`（批量更新）、`BatchDeleteHide`（软删/隐藏）、`Get*`/`Query*`（查询）、`Check*`（校验）、`Refresh*`（重算/拉取）、`Add*`（补齐）、`Approve*` / `Qc*`（QC 审批） |
| **Product Type** | Product（搜索商品广告）、Shop（店铺广告）、LiveStream、Video、SearchBrand、BrandConsideration、ProductGms、BackgroundRoiThreeGms、AutoProductAds、Brand Group Keyword |

每个 Action 走 `setup/controller.go` 统一注册，再 dispatch 到对应 `internal/set_*` 或 `internal/mass_update_*` 包：

| 包 | 广告类型 | 主要写入表 |
|----|---------|------------|
| `set_product_ads` | 搜索商品广告 | `advertisement_tab`、`ad_keyword_tab`、`campaign_tab` |
| `set_shop_ads` | 店铺广告 | `advertisement_tab`、`campaign_tab` |
| `set_live_stream_ads` | 直播广告 | `advertisement_tab`、`live_stream_ads_index_tab` |
| `set_video_ads` | 视频广告 | `advertisement_tab`、`video_ads_index_tab` |
| `set_product_gms_ads` | 产品 GMS 广告 | `product_ad_tab`、`product_campaign_tab`、`product_gms_item_tab` |
| `set_background_roi_three_gms_ads` | 后台 ROI-3 GMS 广告（pt=29） | `background_roi_three_gms_ads_index_tab` |
| `brand_consideration_ads` | Brand Consideration Ads | `brand_consideration_ads_index_tab` |
| `search_brand_ads` | Search Brand Ads | `searchbrand_ads_index_tab`、`searchbrand_package_tab` |
| `auto_product_ads` | 自动选品广告 | `item_ads_index_v2_tab` |
| `automated_ads_solution` | Automated Ads Solution（系统驱动 Campaign） | `campaign_tab` |

每次写入会：1）经 `internal/locker`（Redis 分布式锁）防并发；2）调用 `db_manager`（封装 ads-db-lib）写主表；3）通过 `internal/ads_audit/`、`internal/ads_audit_info/` 落 audit；4）必要时 publish Kafka 变更事件（被下游 syncer / indexer 消费）；5）经 `internal/cache` 失效相关 Redis key。

### 4.2.9 广告生命周期与状态机/Ad Lifecycle and State Machine

广告状态在平台后端用 **三层模型**表示，由用户操作、审核、商品状态、库存、政策合规和外部状态同步五类触发源共同驱动。

#### 三层状态模型

| 层级 | 字段位置 | 描述 |
|-----|---------|------|
| **CampaignStatus** | `campaign_tab.status` | Campaign 配置层状态（卖家可见控制态）：`ACTIVE` / `PAUSED` / `DELETED` / `SCHEDULED` / `ENDED` |
| **AdStatus** | `advertisement_tab.status`（按广告产品扩展：`product_ad_tab.status`、`live_stream_ads_index_tab.status` 等） | 广告条目层状态：`ACTIVE` / `PAUSED` / `REJECTED` / `BANNED` / `DELETED` / `DRAFT` |
| **DeliveryStatus**（投放可投态） | Indexer 写入 `is_active`、ads-engine 运行时计算 | 由 Campaign × Ad × Item × Account 四方面综合判定：`SERVING` / `OUT_OF_BUDGET` / `OUT_OF_BALANCE` / `OUT_OF_STOCK` / `OUT_OF_SCHEDULE` / `BANNED` |

#### 状态转换触发器（5 类）

| 触发源 | 路径 | 典型动作 |
|--------|------|---------|
| **卖家操作** | Seller Center → ads-marketing → UAS `SetAdvertiseBatch*` / `MassUpdateCampaignV2` | 创建/暂停/恢复/编辑预算/编辑出价 |
| **审核/政策** | 审核系统 CDC → ads-status-syncer → UAS | `REJECTED` / `BANNED` / `RESTORED` |
| **商品/库存** | item.item_info CDC → ads-resharder → Kafka `IIS` / `IPS` topic → ads-status-syncer | item 下架 → 暂停关联 Ad；库存为 0 → 标记 `OUT_OF_STOCK` |
| **预算/余额** | ads-account-balance 计算 + status-syncer `ads-status` cron | 余额耗尽 → `OUT_OF_BALANCE`；日预算耗尽 → `OUT_OF_BUDGET` |
| **MCN / Campaign 系列** | MCN CDC → status-syncer `MCN` handler | MCN partnership 失效 → 暂停 MCN 关联 Campaign；NPB phase 推进 → UAS `npa-phase-sync` |

#### 状态同步双机制：实时 + 周期对账

```mermaid
flowchart LR
    DB[(ads-DB)] -->|binlog| RESHARDER[ads-resharder] -->|分片| KAFKA[(Kafka: gds/iis/ips/ils/abs/mcn/due/algo_*)]
    KAFKA --> SYNCER[ads-status-syncer<br/>consumer]
    SYNCER -->|JobType 派发| WORKER[28 类 JobType]
    WORKER -->|SPEX| UAS[ultimate_ads_service]
    UAS -->|写回| DB

    CRON["ads_status_sync_job<br/>23 个 cron"] -.周期全量对账.-> DB
    CRON -.填充缓存.-> REDIS[(Redis: existence/item/FDT/...)]
```

- **实时侧**：CDC 事件秒级触发状态变更（卖家"暂停"操作 1~3 秒可达投放层）。
- **离线侧**：`ads-status-syncer` 的 23 个 cron 做**周期全量对账**（如每日 `ads-status` 检查所有广告余额/预算状态，每周 `system-gms-weekly-budget` 重算 GMS 周预算，每 60min `balance-noti` 扫低余额账户触发通知）。

#### 各广告产品状态特殊性

| 广告产品 | 关键差异 |
|---------|---------|
| Product Ads（pt=2） | 完整状态机，最复杂 |
| Shop Ads（pt=4） | 走 graph-indexer + shop-indexer 双索引；状态由 SPS 和 KW 维度细化 |
| Live Ads | 由直播会话（LSS）状态联动；MCN 关联强校验 |

| Product GMS / Background ROI-3 GMS（pt=24/27/29） | item 优先级互斥（GMS > Product/MPD > pt=29），详见 §4.2.11 |

### 4.2.11 GMS（Shop GMV Max）全景/GMS Full Picture

#### 概念定义

**GMS** = **Shop GMV Max**，是一种以"店铺整体 GMV 最大化"为目标的智能广告策略——卖家只需开启 GMS，平台自动选品、自动出价、自动调预算、自动发券。它在 Shopee Paid Ads 内部和"传统 GMV Max（Discovery / Search GMV Max 等 oCPC 形态）"是**两套不同体系**：

| 形态 | pt | 计费 | item 来源 | bid-sense 接口 | 发券 | UAS handler |
|------|----|------|----------|----------------|------|-------------|
| **GMS（Shop GMV Max）** | 24 / 27 | 正常计费 | algo `gms_pool`（Redis 离线）→ `add_missing_item` | `GetItemSelectionGMS` | 正常 bidding | `product_gms` 包 |
| **Package Non-Ads**（GMS Package 副产物） | 29 + `is_nominated_package` | ❌ 不计费 | algo `roi3_pool` → `refresh_item` | `GetItemSelectionROI3` | package voucher | `background_roi_three_gms` 包 |
| **Organic Non-Ads** | 29 + `is_organic` | ❌ 不计费 | DE Hive 30D1O 数据 | — | organic voucher | `background_roi_three_gms` 包 |

GMS 与"传统 GMV Max"差异：
- 传统 GMV Max 是**单 Campaign 内**的智能出价模式（基于 Simple Mode / oCPC，不改变 Campaign 形态）
- GMS 是**店铺级别**的自动化产品（包含选品 + 出价 + 自动 voucher），有专属 pt（24/27/29）和专属选品 pool

Escrow 是平台为大型 / KA 卖家提供的"固定费率自动托管"模式（区别于按消耗实时计费）：

#### Credit 类型 / 适用范围

每条 Credit 记录由 4 个字段共同决定可用性：

| 字段 | 取值 | 作用 |

| `expire_at` | 过期时间戳 | 由 `paidads.topup.list_unexpired_free_ads_credit` 扫描 |

#### SDU 部署模型

平台后端服务统一在 **Shopee Mesos / SP Mesos** 上以 SDU（Service Deployment Unit）粒度部署，每个二进制对应一个独立 module。CMDB 路径：`shopee.mp_search_recommendation_ads.paidads.advertiser_platform.platform`。

|  | `paidads.adsservicecronjob` | cron 二进制 |

|  | `paidads.adsmarketingconsumer` | Kafka consumer |

部署描述文件统一格式：每个 repo `deploy/*.json`，定义：
- `build.docker_image.base_image`：`harbor.shopeemobile.com/paidads/base/platform:1.21`（Go 1.21）

### 4.2.16 数据源更新机制/Source Update Mechanism

本章节包含两类内容：

```bash
uv run skills/team/01.ads-engineering/ads-platform-be-overview-generate/scripts/generate_ads_platform_be_overview.py \
```

**（b）扫描脚本 (Enrich script)** —— 遍历 `projects/gitlab/ads-platform/` 下所有 repo，运行下表中的 scanner，输出唯一的 source-of-truth 旁文档 `02.platform-backend.scanned-facts.md`，contributors 可与本 Overview 做 diff。

```bash
uv run skills/team/01.ads-engineering/ads-platform-be-overview-generate/scripts/enrich_platform_be.py

# 加 --print-json 可改为输出机器可读 JSON。
```

**已实现 Scanner (`scripts/scanners.py`)**:

| 信息 | 源 | 抽取方式 |
|------|---|---------|
| `cmd/` 二进制 | `<repo>/cmd/<binary>/` | 目录列表 |
| Cron 任务清单（策略 A） | `<repo>/cmd/<cron-binary>/*.go` 去掉 boilerplate | 文件名扫描 + Go 文档注释 |
| Cron 任务清单（策略 B） | `<repo>/cmd/<cron-binary>/command.go` 中的 `[]commandConfig{...}` | 大括号深度跟踪 + `Name:` / `Usage:` / `Run:` 正则 |
| SDU 部署 module | `<repo>/deploy/*.json` | JSON 解析 → `project_name.module_name`、`run.command`、`base_image` |
| Internal 分层 | `<repo>/internal/<subdir>/` | 目录列表 |
| SPEX handler 包 | `<repo>/internal/(set_\|get_\|mass_update_\|query\|job_...)*` | 按前缀分桶的目录列表 |
| Proto signature | `<repo>/sp_proto/paidads/<repo>.proto` | 行数 + `package` + `rpc` 正则 |
| CDC topic / handler | `ads-status-syncer/cmd/ads_status_syncer/handler_*.go` | 文件名扫描 |
| JobType 枚举 | `ads-status-syncer/internal/consumer/consts_enum.go` | 在 `const(...)` 块中匹配 `JobType\w+` 标识符 |
| README ## Monitoring / ## Deployment | `docs/common/readme/<repo>/README.md` | 二级标题块抽取 |
| ads-db-lib 表字典 | `ads-db-lib/<group>/*_tab.go` | 正则匹配 `TableName = "..."` + `type *Tab struct` |
| Wire DI 符号 | `<repo>/internal/setup/wire.go` | 正则匹配 `*Client` / `*Repository` / `*DSN` 标识符 |

> **如果代码更新了怎么办**：在 ads-workspace 根目录运行 (b)，把重新生成的 `02.platform-backend.scanned-facts.md` 与本 Overview 各 section 的事实做 diff。Enrich 脚本只读，不会修改主文档 —— 你可以自行决定何时把扫描出来的数字回填到 prose 中。手写叙事仍然掌控「为什么」（业务逻辑、设计决策、跨 repo flow），旁文档掌控「是什么」（从代码可推导的数量、名称、路径）。
