## 1.3 广告系统链路模块 / Advertising System Pipeline Modules

### 1.3.1 系统链路全景 / System Pipeline Overview

#### 1.3.1.1 广告链路架构图 / Ad Pipeline Architecture Diagram






广告请求的一般完整处理链路如下：

```
                                            广告请求的一般完整处理链路

  ┌─ org ──────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │                                                                                                            │
  │  req ──────────▶ recall ──────────────▶ prerank ──▶ ranking ──────────▶ mix rank ──────▶ dispatch to app   │
  │                                                                         ^                                  │
  └─────────────────────────────────────────────────────────────────────────|──────────────────────────────────┘
                                                                            |
  ┌─ ads ───────────────────────────────────────────────────────────────────|──────────────────────────────────┐
  │                                                                         |                                  │
  │  req ──────▶recall ──────▶ prerank ──▶ bidding ──▶ ranking ─────────────┘                                  │
  └────────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

以上示意图中，广告和原生链路是独立链路，只在最后混排阶段融合。

对于电商广告 GMV MAX 而言，广告和原生链路深度融合，广告通过 API0-API3 为原生流量链路提供所需的广告信息。

#### 1.3.1.2 广告链路模块简介 / Ad Pipeline Module Overview





| 阶段              | 职责                   | 输入                                              | 核心处理                                                                               | 输出                                             |
| --------------- | -------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------- |
| **Recall 召回**   | 从全量广告库中检索用户可能感兴趣的候选集 | 全量广告库（百万级）+ 用户/查询/上下文特征                         | 多路并行：双塔 KNN、协同过滤 I2I、倒排文本匹配、U2U2I 等；经 AdsInfoFilter 过滤 + Zigzag 合并截断               | ~千级候选，附带召回队列来源和业务标签                            |
| **Prerank 粗排**  | 用轻量模型快速筛选，缩小精排计算范围   | 召回结果集（千级）+ 基础特征                                 | 轻量 DNN / MMoE 多任务打分（复杂度介于双塔与精排之间）；支持配额保留（reserveQuota）强插扶持候选                       | ~百级候选，附带粗排分数                                   |
| **Rank 精排**     | 精确预估用户行为概率，为出价提供价值信号 | 粗排结果集（百级）+ 完整特征（行为序列、上下文、价格等）                   | UniCR（MMOE-STAR 多任务多域）精排模型；pGMV = item_price × sold_cnt × CR，经 SIR + ItemCali 校准   | pCTR、pCVR、pGMV 等多任务分数，~几十条候选                   |
| **Bidding 出价**  | 根据广告主出价策略计算广告价值 eCPM | 精排分数（pCTR/pCVR/pGMV）+ 广告主出价设置 + lambda/ratio 系数 | 按出价类型计算 eCPM（手动 CPC / oCPX / tROAS）；lambda PID 控成本、ratio 校准模型偏差；Pacing 控预算消耗节奏     | eCPM / bidPrice，排序分 rank_score = α×eCPM + porg |
| **Mix Rank 混排** | 融合广告与原生结果，生成最终展示列表   | 广告候选（含 eCPM）+ 原生结果（含 OrgScore）+ 体验约束配置          | RankScore = α×eCPM + β×OrgScore 竞价排序；执行广告密度上限、最小间距、同店限频等体验硬约束                      | 最终展示序列（广告 + 原生混合），每条广告附带扣费参数                   |
| **Billing 计费**  | 按拍卖机制扣费，确保计费公平可信     | 计费触发事件（点击/曝光）+ 当前与下一位 RankScore + 反作弊信号         | GSP 扣费：deduction = next_RankScore 推导的第二价格；上下界裁剪（min_cap, max_cap）；实时反作弊过滤 + 离线纠偏退款 | 实际扣费金额，计费日志（供归因和反馈系统）                          |

> 各阶段的详细策略和模型实现分别见：召回 [§2.1](../02.ads-strategy/01.recall-and-supply-strategy.zh-CN.md#21-召回通路和供给策略)、排序模型 [§2.2](../02.ads-strategy/02.cxr-pgmv-models-and-calibration.zh-CN.md#22-cxr--pgmv-模型和校准)、出价算法 [§2.3](../02.ads-strategy/03.bidding-products-and-algorithms.zh-CN.md#23-出价产品和算法)、流量策略与计费 [§2.4](../02.ads-strategy/04.traffic-strategy-and-billing.zh-CN.md#24-流量策略和计费)。

### 1.3.2 核心策略模块 / Core Strategy Modules

#### 1.3.2.1 流量定向 / Traffic Targeting






- 从流量视角：召回用户感兴趣的广告集合
- 从广告视角：为广告定向潜在感兴趣的用户流量
- 定向方式包括：关键词定向、人群定向、上下文定向、重定向等
- 核心挑战：在定向精度与流量规模之间取得平衡

> 流量定向的详细策略和模型实现见 [§2.1](../02.ads-strategy/01.recall-and-supply-strategy.zh-CN.md#21-召回通路和供给策略)（广告召回策略）

#### 1.3.2.2 价值预估 / Value Estimation






预估流量×广告的价值点，价值点包括用户对广告的各种行为概率分（点击/转化/付费等）。核心模型：


| 模型   | 含义    | 说明          |
| ---- | ----- | ----------- |
| pCTR | 预估点击率 | 用户点击广告的概率   |
| pCVR | 预估转化率 | 点击后产生转化的概率  |
| pGMV | 预估成交额 | 转化带来的交易金额期望 |


> 价值预估的详细策略和模型实现见 [§2.2](../02.ads-strategy/02.cxr-pgmv-models-and-calibration.zh-CN.md#22-cxr--pgmv-模型和校准)（CxR & PGMV 模型和校准）

#### 1.3.2.3 出价策略 / Bidding Strategy






基于价值预估分，根据广告主的出价表达，计算流量×广告的广告价值 eCPM。

- 基础出价：广告主手动设定出价， eCPM 由出价 × 预估概率转换
- 智能出价（oCPX）：广告主设定目标成本，平台通过 pCTR/pCVR/λ 自动计算 eCPM
- 核心目标：在广告主预算约束下，最大化投放效果（点击/转化/GMV）

> 出价公式和策略详解见 [§1.4.2](04.strategy-mechanisms.zh-CN.md#142-广告出价和售卖的核心概念)-[§1.4.5](04.strategy-mechanisms.zh-CN.md#145-双出价)

#### 1.3.2.4 售卖机制 / Selling Mechanism






基于广告价值（eCPM）和平台原生价值（OrgScore），通过竞价排序机制决策流量售卖给哪个广告，以及对应的扣费规则：

- 竞价排序： `RankScore = α × eCPM + β × OrgScore`
- 主流机制： GSP（广义第二价格拍卖）— 按下一位出价扣费，激励真实出价
- 扣费公式（以 CPC 为例）：  `实际 CPC = (next_RankScore - β × OrgScore) / (α × pCTR) + 0.01`
- 核心权衡：平台收入、广告主 ROI、用户体验的三方均衡

> 混排机制和计费公式详解见 [§1.4.6](04.strategy-mechanisms.zh-CN.md#146-广告混排)-[§1.4.7](04.strategy-mechanisms.zh-CN.md#147-广告计费)。
