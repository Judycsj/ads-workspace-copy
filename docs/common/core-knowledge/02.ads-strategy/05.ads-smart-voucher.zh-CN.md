## 2.5 广告智能优惠券/Ads Smart Voucher

### 2.5.1 广告优惠券概览/Ads Voucher Overview

广告智能优惠券是 Product Ads 的 ROI3 / ROI4(cofund) 发券层。它不是单纯改 bid，而是在常规广告竞价之外增加“是否发券、发多大券、谁承担券成本”的决策层。本次同步来源为 `docs/common/sub-kb/2.5-voucher/strategy.md`（ROI3 策略、在线链路、分析契约；last verified 2026-04-22，confidence medium）和 `docs/common/sub-kb/2.5-voucher/model.md`（Uplift ROI3 模型、样本、特征、策略、SQL 和 playbook 统一入口；last verified 2026-04-30，confidence medium）。

ROI3 知识库需要同时保留两层定义：

- 历史/产品命名背景：`ROI3 = GMV / (ad cost + coupon cost)`。这个表述仍适合解释为什么券成本进入优化目标。
- 当前分析契约：ROI3 要通过 `base / voucher / uplift / cost` 理解；只有当发券相对不发券带来的增量价值能覆盖券成本时，发券才是有价值的。

当前保护规则应被理解为线上运营 guardrail，而不是 ROI3 唯一产品定义：

```text
Guardrail = gmv_uplift / 4 + advv_uplift - cost_uplift > 0
```

这组写法用于协调旧版“比例式 ROI3”定义与新版 Uplift 分析契约。源文档的一致性审计已经将新版契约标记为 owner 确认的本地分析契约，同时保留比例式定义作为背景。

**核心语义锁定。**

1. `uplift_*` 表示 `voucher - base`。
2. `pcoc` 表示 `预测值 / 实际值`。
3. `pcr`、`pctr`、`pgmv`、`pc2`、`advv` 和券成本属于不同指标族，不能混成一个“价值”字段。
4. `voucher_price` 是发出去的券面额，不是最终核销券成本。
5. `reward_discount -> Metric_VOUCHER_PRICE` 更接近订单/核销侧券成本链路。
6. 实验平台 `ads_voucher_cost` 是当前 ROI3 预算使用率分析的 truth 分子。
7. `DailyVoucherPrice` 等 HyperX trace 字段只能解释 controller 观测，不是最终 truth cost。
8. AB 平台 group bucket、在线实验 bucket 和运行时 `roi3_traffic_bucket` 是不同概念。
9. 模型校准和 pacing 控制是两件事：校准修正预测值，控制调节执行强度和预算节奏。

#### 2.5.1.1 Ads Smart Voucher-ROI3(QCPX)/Ads Smart Voucher-ROI3 (QCPX)

ROI3 通常指平台单边承担券成本。平台承担券成本，并判断“发券”相比“不发券”是否能让平台价值更优。

**业务目标：**

- 平台 rev 增收（用券撬动的广告消耗 > 发券成本）
- 带动平台总 GMV 增长（广告流量效率提升 → 广告 GMV 提升 → 大盘 GMV 增长）
- 商家营销效率和效果的提升（用券提升用户下单意愿和规模）

在当前 Uplift 视角下，核心问题不是“发券后的最终值是多少”，而是“发券相对不发券带来多少增量价值，以及这部分增量价值要付出多少券成本”。

#### 2.5.1.2 Ads Smart Voucher-ROI4(cofund)/Ads Smart Voucher-ROI4 (cofund)

ROI4 / cofund 通常指平台和广告主共同承担券成本。相比 ROI3，它会在价值函数和控制链路里更显式地加入 platform spend / ROI 约束。

ROI3 / ROI4 边界相关的重要代码和 trace 概念包括 `enableCofund`、`targetPlatformSpendImps`、`getPlatformGmvRoi()` 和 `voucher_pacing_control`。

### 2.5.2 发券工程链路和策略模块/Voucher Issuance Engineering Pipeline and Strategy Modules

#### 2.5.2.1 端到端发券链路/End-to-End Voucher Issuance Pipeline

发券链路横跨 ads 离线、API0-3、org rank/mixrank、online bidding、posterior 聚合和 controller 回流：

| 阶段 | 模块 | 稳定职责 |
|---|---|---|
| 离线 | ads offline / index | 为每个 item 创建可用券，并将 voucher ID / 券面额写入 ads 正排索引。 |
| API0 / API1 | ads → org | 为每个 ad item 返回可用券候选。 |
| Rank | org rank | 预估每个 item × voucher 候选的 `ctrUpliftRatio` 和 `cvrUpliftRatio`，并通过 API2 回传给 ads。 |
| API2 | ads voucher decision | 结合 bidding 模型值和 uplift 值，决策 voucher ID、面额、折扣比例、uplift 和 eCPM。 |
| MixRank | org mixrank | 使用券面额、折扣比例、uplift ratio、eCPM 等发券信息参与混排。 |
| API3 | ads billing | 通过 `additionDeduction` 执行增量计费。 |
| Posterior | order / click / imp 聚合 | 聚合真实曝光、点击、下单和核销信号。 |
| Control | `voucher_pacing_control` | 平滑 spend、对齐预算节奏，并输出 `PidCoef` 等执行系数。 |

#### 2.5.2.2 在线主链路/Online Main Path

在线链路可以按下面的顺序理解：

```text
request
  -> 模型层读取 raw head
  -> 校准层做 cali / ratio / cap / monotonicity
  -> 写公共字段
  -> 策略层准备候选券并计算 value / cost
  -> selector 选择最终券并写策略 trace
  -> posterior 聚合真实 imp / click / order / redeem
  -> 控制层平滑 spend，输出 PID / budget coef
```

`rerank_uni_pgmv.go` 是模型/校准侧桥接层。它读取 `direct_pgmv_7d`、`shop_pgmv_7d`、`pcr_0`、`uplift_ratio_*`、`uplift_pctr0`、`uplift_pctr_ratio*` 等 raw head，执行 fallback / calibration / ratio / cap / monotonicity 逻辑，并写出 `ModelPgmv`、`ModelPgpm`、`VoucherPcr0`、`VoucherCrUpRatio1..7`、`VoucherPctr0`、`VoucherPctrRatio1..7` 等公共字段。

**预估值校准手段**（当预估值出现系统性高估/低估时）：

- **临时方案（人工校准系数）**：通过配置人工校准系数，直接调节 `pcr0` 和各档位 `uplift_ratio` 的输出值，不需要重训模型。适用于 PCOC 出现明显偏离时的快速介入。
- **长期方案（Uplift PCOC 优化 Epic）**：KP13 推进 uplift 预估值校准性改进，方向是直接建模 platform_gmv，不再依赖 CR uplift 后处理构造。**KP1 GMV 校准头（2026-07-01 全量，expId=226383）已实现大幅改善：PCOC error 降低 62.2%，VPR abs +44.13%。** 参考：`docs/team/00.paid-ads-dev/10.trd-prd-td-list/2026q2/o1/kr4-kp13-202605121057/epic-file.md`

当前应在总知识库里锁定的 Uplift 模型事实：

1. 主抽象是两阶段结构：**CR uplift 头**（`uplift_pcr0 + 7 个 uplift_ratio head`）+ **GMV 校准头**（`VoucherPlatformGmvUpliftRatio1..7`，KP1 全量）。
2. 方法族是 DragonNet + IPW + TMLE，不是普通单塔 CVR 模型。
3. CR 头训练依赖 `placed_order_1d`；GMV 校准头训练依赖 `platform_gmv`（omni 口径，仅 RCT 样本，backbone 冻结后独立训练）。
4. Treatment / Control 根定义是 `voucher_price > 0` 与 `voucher_price == 0`。
5. RCT 分析仍主要依赖 reason `17 / 18 / 99`；reason `19` 是否纳入需要按具体脚本确认。
6. 七档主折扣语义是 `2% / 5% / 8% / 12% / 15% / 20% / 30%`（KP1，2026-06-08 协议上线，2026-07-01 模型全量）。
7. CTR uplift 分数可能被加载和处理，但当 `Roi3EnableCtrUpliftRatio=false` 时，线上发券主链路仍以 CVR uplift 为主。

#### 2.5.2.3 策略模块和后处理/Strategy Modules and Post-Processing

`rerank_voucher_rule.go` 和 voucher package 可按下面的函数级顺序理解：

1. `abTestConfigPrepare()`。
2. 通过 `dynamicVoucherPrepare`、`voucherListPrepare` 和 `voucherListPrepareNew` 准备候选券。
3. 候选公共过滤：max CPA cap、`DynamicVoucherCap`、`voucherPrice >= VoucherThresholdPrice`、`MaxDiscountThresholdNoVoucher`。
4. `modelPrepare()` 将模型公共字段包装成策略可消费结构。
5. request / item gating：`isUserValid`、`isItemRoi3Valid`、`isRoi3VoucherLimit`、`isBudgetAvailable`。
6. 候选打分：`calcUpliftCTR()`、`calcUpliftCR()`、`calcUpliftProfitAndROI()`。
7. `voucherSelector()` 选择最终券，算法桶还会受 cofund send flag、only seller adjust、seller voucher threshold、`voucherDiscountDisableList` 等约束。
8. 回写结果与 trace：`BestVoucherID`、`BestVoucherPrice`、`DynamicVoucherPrice`、`DynamicVoucherDiscount`、`VoucherPgpm`、`VoucherPcr`、`VoucherDeduction`、`VirtualVoucherPrice`、`VoucherUnpickedReason`、`VoucherUnpickedReasonBase`、`BidRerankTrace.PgmvV`、`BidRerankTrace.Pctr_0`、`BidRerankTrace.PctrV`、`BidRerankTrace.Pcr_0`、`BidRerankTrace.PcrV`。

`RerankVoucherRulesNew` 位于 `rerank_bidding` 之后、`rerank_subsidy` / `rerank_deduction` 之前。关键后处理规则包括 `RerankVoucherRuleNewV2`、`VoucherBidBoostRule`、`VoucherDeboostRule`、`VoucherAdsAddDedRule`。也就是说，voucher 主策略先产出 `VoucherPgpm`、`VoucherPcr`、`VoucherDeduction`，后续规则再把这些量转成 boost、deboost 和 deduction 通道里的执行量。

#### 2.5.2.4 控制层/Control Layer

`voucher_pacing_control` 是 pacing controller，不是模型预测器。稳定流程如下：

1. 拉取 order / click / impression 三套 posterior 指标。
2. 用 `CaliCoef` 做 click-side spend 到 order-side spend 的校正。
3. 对 order / click / impression 信号做平滑混合。
4. 基于 budget、CDF 和 smoothed spend 计算 PID error。
5. 输出 `PidCoef`、`Roi3BudgetCoefArray`、`CofundBudgetCoefArray`。

关键边界：controller 只调节节奏和执行强度，不生成 `pcr`、`pctr`、`pgmv`。

### 2.5.3 发券模型预估/Voucher Issuance Model Estimation

#### 2.5.3.1 模型目标和因果定义/Model Objective and Causal Definition

Uplift CR 模型服务于 ROI3 选券、出价、计费和评估。它不是只预测最终转化概率，而是预测发券相对不发券的增量转化影响。

当前 base 模型是以 `DragonNet + IPW + TMLE` 为核心的因果推断式增量转化模型：

- `control tower` 预估不发券 baseline 转化，通常对外表现为 `pCVR_0` / `pcr_0`。
- `treatment tower` 预估不同券折扣档位的 uplift ratio。
- `propensity head` 预估 `pi(t|x)`，用于通过 IPW 修正 treatment 选择偏差。
- TMLE 式修正用于进一步降低观测样本 treatment 数据中的偏差。

线上关键输出是：

```text
# CR uplift 头（placed_order_1d 训练）
uplift_pcr0
uplift_ratio1 ~ uplift_ratio7

pCVR_i = uplift_pcr0 * uplift_ratio_i
uplift_i = pCVR_i - uplift_pcr0

# GMV 校准头（platform_gmv 训练，KP1 全量，开关 useVoucherPlatformGmvModel=true）
VoucherPlatformGmvUpliftRatio1..7  # 各档 GMV uplift ratio，直接对齐 omni platform_gmv
```

这些输出会继续进入 Profit、ROI、eCPMV、选券、bid boost、deboost 和 deduction 计算。

#### 2.5.3.2 样本链路和 Label/Sample Pipeline and Labels

Uplift CR 样本链路复用 UniCR CR 基础设施：Rank FeatureDump 与 UB 行为流拼接、RawSample 落盘、FP 场景处理、CR TrainData 路径和 LabelJoin。真正差异集中在 Uplift convertor 和评估样本筛选。

`convertor_uplift_cr_1h_auuc.py` 是关键 Uplift convertor，稳定职责包括：

- 识别是否发券并生成 `is_treatment`；
- 识别是否属于 RCT 样本并生成 `is_rct`；
- 补齐 uplift portrait 默认值；
- 生成 1h 训练 label；
- 重组 multitask 字段，供 Uplift 训练和 AUUC 评估使用。

样本语义：

| 概念 | 稳定含义 |
|---|---|
| Treatment | 发了券，根定义是 `voucher_price > 0`。 |
| Control | 未发券，根定义是 `voucher_price == 0`。 |
| RCT | 随机分组样本，可视为偏差更小。 |
| 非 RCT | 由策略决定是否发券的样本，存在选择偏差。 |
| 训练 label | CR 头：`placed_order_1d`；GMV 校准头：`platform_gmv`（omni 口径，30d ATC→24h first click，仅 RCT 样本，backbone 冻结后独立训练）。 |
| 折扣档位 | 七档，对应 `2% / 5% / 8% / 12% / 15% / 20% / 30%`（KP1 全量，30% 为新增高折扣档）。 |

模型仍有 `direct_label_1d` 等兼容输出，但当前 Uplift 训练解释应锚定 1h direct-order label 和 multitask `[18:19]` 字段。

**Label 收集工程链路**（各 label 口径和归因窗口）：

| Label | 归因方式 | 原始数据 | 归因窗口 | 说明 |
|-------|---------|---------|---------|------|
| `direct_order_1h`（主训练 label）/ `advv` | ads last click 归因 | order mart | **1h** | 与广告券有效期对齐；V3（2026-04）前训练 label 为 `direct_order_1d`，V3 切换为 1h |
| `platform_gmv` | omni 口径，atc 拆分订单 | order mart（atc 维度） | **30 天 atc + atc 前 1 天 click** | 与 AB 实验看板 platform GMV 口径对齐；atc 拆分订单方式归因 |
| `redeem_platform_gmv` / `voucher_cost` | 券 click 归因 | order mart（券核销维度） | **1h**（与 AB 实验 platform GMV 对齐） | 用于评估实际券撬动的 GMV 和实际券成本；归因到发券时的广告 click |

**关键设计注意**：`direct_order_1h` 训练 label 的 1h 窗口来自对 7 天原始数据的截断，不是原始归因窗口为 1h。`platform_gmv` 使用 30 天 + 1 天 atc 口径，与训练 label 窗口不一致，是离线指标和线上业务目标之间已知 gap 的来源之一。

#### 2.5.3.3 模型特征/Model Features

Uplift 特征体系有三层：

| 特征层 | 与 PGMV 关系 | 状态 | 说明 |
|---|---|---|---|
| Sparse 特征（29个 uplift 专用） | 大量共用（同一 EGO 样本基础设施） | base 在用 | 覆盖用户行为、商品属性、品类偏好、店铺信号、用户画像和入口上下文 |
| Dense / treatment 特征（7个） | **uplift 独有** | base 在用 | baseline pCR、`item_price`、`platform_discount`、`shop_discount`、平台/店铺 voucher ID、训练期 `voucher_price` |
| User voucher portrait（18个） | **uplift 独有** | **KP5 全量（2026-06-12）** | 用户 30d 券行为画像：核销计数（3361/3363）、金额分布（3367/3369/3371）、折扣比率（3373/3375/3377）、核销比率/份额（3365/3379/3381/3385/3387/3395）、敏感度（3389/3393/3397）、券类型计数（3383） |
| Item/Shop 折扣订单响应（20个） | **uplift 独有** | **KP5 全量（2026-06-12）** | 8 个 direct/broad order（3d/14d，item+shop，slot 6586-6615 系列）+ 12 个 discount order 分档（big/mid/small，3d/14d，item+shop，slot 6573-6612 系列） |
| Query/Item 文本 Embedding（2个） | **uplift 独有**（LLM 产出） | **KP5 全量（2026-06-12）** | slot_31889（query emb，dim=256）+ slot_11（item emb，dim=256）；KA5 离线 AUUC +0.019、PCOC error -0.060 |

特征示例和约束：

- Base sparse 特征覆盖用户长短期价格行为、user-item 交互命中、品类与店铺偏好、商品类目/CR/新鲜度/价格波动属性、店铺转化信号，以及少量用户画像/上下文特征。
- Dense / treatment 特征让模型显式感知“券长什么样、折扣多大”。`voucher_price` slot `65160` 只在训练时用于 treatment 分组，推理前尚未完成发券决策，因此不可用。
- User voucher portrait（KP5 全量）18 slots 均使用 30d 窗口：核销计数类（`log1p` 处理）、金额类（log 归一化）、比率类（clip 后归一化）、敏感度类（有符号 clip）、券类型计数（低基数 embedding）。显式引入”用户历史上如何响应券”的信号。
- 画像特征按语义分组处理：比率类裁剪归一化、长尾计数 `log1p`、金额 log 归一化、可正可负的 sensitivity 特征做有符号裁剪、低基数离散特征走 embedding。
- 已做数据质量保护：异常折扣率、异常金额占比、小样本放大的 sensitivity、跨 region 金额量纲差异。

Sparse 特征按维度分布（29 个 uplift 专用 slot）：

| 维度 | 数量 | 代表特征 |
|------|------|---------|
| 纯 user | 8 | 长短期价格桶、性别年龄、地址、全局子品类偏好 |
| user × item 交叉 | 6 | 点击/加购/购买命中时间衰减、长期 session 品类/店铺偏好 |
| 纯 item | 12 | 商品 ID、三级品类、7/30 天 CR 桶、CTCVR 桶、新鲜度、价格波动、店铺转化 |
| 店铺 ID (4 hash) | 4 | shop_id 多路 hash |
| context | 1 | entrance（入口） |

已知特征缺口：

- KP5（2026-06-12）已补充 18 个 user voucher portrait slots 和 20 个 item/shop 折扣订单响应 slots，用户券行为画像和商品信号显著增强。
- 部分特征覆盖率天然偏低，”无历史 = 默认值”是可预期建模状态。

#### 2.5.3.4 模型结构、训练和 Serving/Model Architecture, Training, and Serving

Uplift 模型网络结构（两阶段）：

**阶段一：CR uplift 头**（placed_order_1d 训练）

```text
feature input (~250 sparse slot + 7 dense/treatment + KP5 新增 40 slots)
  -> SceneFiLM: entrance_emb(table_size=256, dim=16) → scale, shift
                → x*(1+scale)+shift 应用于 backbone（scale clip ±0.5）  [KP5]
  -> shared backbone: Dense(input → 256) → Dense(256 → 128)
                      + Discount Embedding Concat (~528 维)
  -> propensity head: Dense(8) → softmax → π(t|x)    [8分类：1 control + 7 treatment]
  -> control tower:   Dense(64) → Dense(32) → sigmoid → pCVR_0
  -> treatment tower × 3:
       Tower1 (02/05档): Dense(64) → Dense(32) → [k, b] → ratio_1, ratio_2
       Tower2 (08/12档): Dense(64) → Dense(32) → [k, b] → ratio_3, ratio_4
       Tower3 (15/20/30档): Dense(64) → Dense(32) → [k, b] → ratio_5, ratio_6, ratio_7
```

**阶段二：GMV 校准头**（platform_gmv 训练，KP1 全量，backbone 冻结）

```text
[冻结 backbone 输出]
  -> GMV 校准头（仅 RCT 样本，label = platform_gmv，omni 口径）
       trainable: calib_c（control 端）+ g[i]（各档 i=1..7）
       输出: VoucherPlatformGmvUpliftRatio_i = calib_c × g[i] × platform_gmv_0
       保序: cumulative_max 约束（单调递增）
       损失: arithmetic mean-matching loss（GMV PCOC → 1.0）
       开关: useVoucherPlatformGmvModel=true（已全量）
```

线性剂量-响应公式（LDR）：

```
LDR_i   = k_i × d_i + b_i        -- 每档折扣的线性响应，保证 tower 内单调性
logit_i = LDR_i + logit_0
ratio_i = sigmoid(logit_i) / pCVR_0   -- clip [0.1, 5.0]
```

**3 个 Treatment Tower 分段设计原因**：6 个独立 Tower 会导致高折扣档（15%/20%）样本不足；1 个共享 Tower 无法区分低/中/高折扣的异质激励模式（VCNet 实验验证了共享失败导致高折扣低估）。3 段设计在样本充足和模式可区分之间取得平衡。

**Isotonic Regularization 实现（两层）**：训练时通过 `softplus(delta)` 约束 Tower 内相邻档位单调递增；Serving 时额外增加保序 clip（`ratio1 ≤ ... ≤ ratio7`）兜底跨 Tower 的单调性。

**选择 DragonNet 而非 VCNet 的原因**：实验验证结论——VCNet 所有折扣共享单一 Tower，导致高折扣档位（15%/20%）系统性低估 uplift；此外 VCNet 不含 propensity 修正机制，无法处理策略分配带来的选择偏差。DragonNet 采用"3 个 Treatment Tower 分别覆盖低/中/高折扣段"的拆塔设计，同时通过 propensity head + IPW + TMLE 三层纠偏处理选择偏差。详见 `sub-kb/2.5-voucher/model.md §5.3.1`。

**当前模型限制**：

- treatment tower 内 uplift-discount 关系为线性（LDR），无法捕捉阈值效应；
- item price × discount 交互刻画不足；

**折扣档位扩展**：在线协议已于 **2026-06-08 上线**（TRD：`kr4-kp1/trd/platform-gmv-online-protocol-trd.md`），档位从原 6 档（2%/5%/8%/12%/15%/20%）扩展至 **7 档（98/95/92/88/85/80/70 折）**，对应新接口字段 `VoucherPlatformGmvUpliftRatio1..7` / `VoucherAdvvUpliftRatio1..7` / `VoucherRedeemRate1..7`。策略侧是否实际使用新预估值由三组独立 bool 开关（`useVoucherPlatformGmvModel` / `useVoucherAdvvModel` / `useVoucherRedeemRateModel`）控制。
- 跨 Tower 单调性（如 05% vs 08%）仅由 Serving 侧 clip 保障，训练时无约束；
- `layers/BST.py` 等行为序列模块在 uplift 模型中**未使用，线上不生效**。

#### 2.5.3.5 评估体系/Evaluation System

Uplift 评估不能只看模型 AUC，因为模型最终服务于增量价值。离线评估重点看：

- `pcr0` AUC / pCoC；
- 各 uplift 档位 AUUC；
- 各 uplift 档位 pCoC。

这些指标与线上业务目标的系统映射：

| 离线指标 | 衡量能力 | 对应线上业务目标 | 异常时的线上风险 |
|---------|---------|----------------|----------------|
| **pcr0 AUC** | Control Tower 无券 CR 排序能力 | ecpm0 / Profit 基础计算正确性 | AUC 差 → 发券选品偏差 |
| **pcr0 pCoC** | 无券 CR 数值校准度（预估/实际） | Profit 绝对值可靠性；pacing controller 基准 | pCoC 偏高 → Profit 高估 → 发券过激进，预算超消耗 |
| **Uplift AUUC** | 各折扣档 uplift 排序能力（识别真正受券影响的用户） | Guardrail `gmv_uplift`、增量 ADVV | AUUC 低 → 券发给不敏感用户 → Guardrail 难达标 |
| **Uplift pCoC** | 各折扣档 uplift 数值校准度 | 档位选择准确性；Profit 中 uplift 项可靠性 | pCoC 偏高 → uplift 高估 → 倾向高折扣券，cost/benefit 恶化 |

主要评估风险是训练和业务评估没有完全相同的目标和窗口。RCT 实证显示 1h direct-order uplift 比 7d broad GMV 系统性高 10%~15%（折扣越大差距越明显）。如果不显式标记上下文，1h direct-order 训练 label、7d 业务指标、click-space 模型值和实验页指标混用，会系统性高估线上 Profit。

无偏性保证机制（三层）：RCT 样本（reason 17/18/99）weight=1 提供无偏基准；IPW 对非 RCT 策略样本一阶纠偏；TMLE L_targeted_reg 学习残差修正参数 `ε(x)` 做二阶纠偏，具备"双重稳健"性质。

### 2.5.4 发券出价策略/Voucher Issuance Bidding Strategy

#### 2.5.4.1 Profit、ROI 和选券/Profit, ROI, and Voucher Selection

选券本质上比较 voucher benefit 和 voucher cost。本章旧有公式仍可作为策略侧抽象保留，但必须和上面的 Uplift 语义一起理解。

```
voucher_benefit = Rev_Coef × ctcvr_0 × ctcvr_uplift × cpa_bid / Rev_Troi
                + GMV_Coef × ctcvr_0 × ctcvr_uplift × (item_price / GMV_Troi - voucher_price)
                + PC2

voucher_cost    = Cost_Coef × ctcvr_0 × (1 + ctcvr_uplift) × q

voucher_profit  = voucher_benefit - voucher_cost
                = ctcvr_0 × { ctcvr_uplift × cpabid × Rev_Coef / Rev_Troi
                            + ctcvr_uplift × item_price × GMV_Coef / GMV_Troi
                            - (1 + ctcvr_uplift) × q × Cost_Coef }
```

稳定理解：

- `voucher_benefit` 聚合 revenue / GMV / PC2 风格的预期价值；
- `voucher_cost` 估算预期券成本；
- `voucher_profit = voucher_benefit - voucher_cost`；
- 最终选券需要在 gating、budget、blacklist、cofund、seller threshold、discount disable 等约束下最大化平台预期价值；
- 面向业务分析时，不要把某个临时 Profit 公式提升成 ROI3 唯一定义；当前总叙事是 `base / voucher / uplift / cost`。

**v-profit 三项的模型来源（来源：KP1/KP2/KP3 §1.1）**

最终业务目标 v-profit 的三个分子项分别由不同模型/链路产出：

```
v-profit =
  (platform_gmv_uplift / 4 + advv_uplift - voucher_cost_uplift)
  / voucher_cost
```

| 打分项 | 旧链路表达式（2026-06-08 前） | 新协议表达式（2026-06-08 起） |
|---|---|---|
| `advv_uplift` | `PREDICT_ADVV = ModelPgmv × crRatioUp × tCir × coef` | `VoucherAdvv0`（base）× `VoucherAdvvUpliftRatioN`（各档 uplift ratio），开关 `useVoucherAdvvModel` |
| `platform_gmv_uplift` | `upliftGmvImp = (ctrV × crV − ctr0 × cr0) × itemPrice × avgSoldCnt` | `VoucherPlatformGmv0`（base）× `VoucherPlatformGmvUpliftRatioN`，开关 `useVoucherPlatformGmvModel` |
| `voucher_cost_uplift` | `VoucherPcr × VoucherPrice × order2Pay`（`order2Pay` 固定 0.66） | `VoucherRedeemRateN`（各档核销概率），开关 `useVoucherRedeemRateModel` |

新协议三组字段各有独立 bool 开关，关闭时回退旧链路，兼容存量实验。TRD：`kr4-kp1/trd/platform-gmv-online-protocol-trd.md`（2026-06-08 上线）。

**旧链路已知 Gap**（新协议上线前的系统性偏差，详见 §2.5.3.6）：

- `ModelPgmv` 污染 uplift base：`ModelPgmv` 混入发券信号，非纯粹 `pgmv_0`，导致 `PREDICT_ADVV` base value 被污染（KP2 §1.2）
- `crRatioUp` 口径不对齐：训练目标 `direct_order_1h` vs 业务验收 `ads broad_gmv_7d`（KP2 §1.1）
- `upliftGmvImp` 是构造量而非结果量：CTR/CR 变化 × 价格，非 platform_gmv 真实增益（KP1 §1.2.4）

> **在线时序**：Uplift 模型与 PGMV 模型**并行请求**，同时调用，无先后依赖。
> **Fallback**：Uplift 模型打分失败时，`pcr0` 降级使用 organic 分，`crRatioUp`（uplift ratio）默认取 1.0。

#### 2.5.4.2 排序、出价和计费/Ranking, Bidding, and Billing

发券决策通过两个增量项分别影响排序和计费：

```
addition_boost      = voucher_profit
                    = ctcvr_0 × { ctcvr_uplift × cpabid × Rev_Coef / Rev_Troi
                                + ctcvr_uplift × item_price × GMV_Coef / GMV_Troi
                                - (1 + ctcvr_uplift) × q × Cost_Coef }

addition_deduction  = uplift_advv
                    = ctcvr_0 × ctcvr_uplift × cpabid
```

- `addition_boost`：作用于混排排序，提升有发券 item 在排序中的优势
- `addition_deduction`：作用于计费，对广告主额外扣取发券带来的增量 advv

`voucher_bid_boost_rule.go` 的表达也可以理解成 click-space value/cost 对比：

- 非 cofund：`adjustBid = VoucherPgpm / pctr * tCir * coef - VoucherPcr * VoucherPrice * order2Pay`
- cofund：`adjustBid = VoucherPgpm / pctr * tCir * coef - VoucherPcr * VoucherPrice * order2Pay + targetPlatformSpendImps / pctr`

`VoucherPgpm / pctr` 更接近 click-space voucher value；`VoucherPcr * VoucherPrice * order2Pay` 更接近每 click 预期券成本。因此 `VoucherPgpm` 不能直接解释成严格的 impression-space voucher GMV。

### 2.5.5 预算分配与激励兼容 Pacing/Budget Allocation & Incentive-Compatible Pacing

#### 2.5.5.1 双池预算分配/Dual-Pool Budget Allocation

平台每日券预算 `B_total` 拆分为**广告池** `B_ads` 和**非广告池** `B_non_ads`：

- 分配目标：在 `pc2_cpigmv_overall ≤ guardrail` 且 `B_ads + B_non_ads = B_total` 的约束下，最大化 `total_rev_uplift(B_ads, B_non_ads)`。
- 广告池设有最低保障比例 `α_min`。

设计理由：广告 item 通常具有更高的单位券成本产出（券驱动广告转化 → 广告花费 → 平台收入），因此向广告 item 倾斜预算是激励兼容的。

#### 2.5.5.2 广告池内 Shop 级分配/Shop-Level Allocation Within Ads Pool

在 `B_ads` 内部，按 shop 投广贡献分配子预算：

```text
B_shop_i = B_ads × w_i / Σw_j
w_i = f(shop_ads_rev_contribution)    // f 为单调递增凹函数
```

- 使用凹函数（如 `sqrt(rev)`）保证边际递减，防止头部 shop 垄断券预算。
- 投广贡献 rev 越高的 shop 分配到的券预算越多，形成激励兼容机制。

#### 2.5.5.3 Shop 级 Pacing 系数/Per-Shop Pacing Coefficient

现有的 `voucher_pacing_control`（§2.5.2.4）在全局层面运作。预算分配将其扩展为 shop 级 pacing 系数：

- 广告池内每个 shop 独立维护 `pacing_coef`，按时间窗口（如每小时）更新。
- 非广告池维护一个全局 `pacing_coef`。
- pacing 系数通过对 `voucher_cost` 乘系数来改造 `addition_boost` 公式：

```text
addition_boost = rev_uplift
               + platform_gmv_uplift × pc2_cpigmv
               + pc2_uplift
               - pacing_coef × voucher_cost
```

- `pacing_coef > 1` 收紧发券；`pacing_coef < 1` 放松发券。
- 广告池的 `coef_min` 低于非广告池（如 0.5 vs 0.8），使广告 item 天然更容易获得发券。

#### 2.5.5.4 激励兼容飞轮/Incentive-Compatible Flywheel

双池分配 + shop 级 pacing 形成正向反馈循环：

1. **投广更多** → shop 投广贡献 rev 更高 → 分配到更多券预算
2. **预算充裕** → pacing 系数更低 → 发券更多
3. **发券更多** → 商品竞争力更强 → 转化和 GMV 提升
4. **GMV 提升** → 激励广告主继续加投 → 回到步骤 1

Guardrail 采用分层约束：全局硬约束 `pc2_cpigmv ≤ threshold`，分池设软上限，超过时触发 pacing 加速收紧。

> 来源：`docs/personal/luka.yang/voucher_budget_allocation.md` — 预算分配和 pacing 设计技术讨论稿。

这个实验证明了 per-hour 系数能单调重塑花费分布，且不会被现有 PID 完全拉回去。

| Bucket | 配置夜间小时均值 coef | 实际夜间花费份额，0-5 点 | corr(实际偏移, 配置意图) |

| 1.5x | 0.81 | 17.5% | +0.46 |
| 2.0x | 0.75 | 20.1% | +0.49 |

干净 treatment 的真实效果是降本和提效率，不是 value uplift。

| Bucket | ADVV/order vs control | 券成本/order vs control | Guardrail/order vs control | ADVV / 券成本效率 |
|---|---:|---:|---:|---:|
| A-A 桶 | -0.48% ~ +0.12% | -1.6% ~ -0.2% | -0.37% ~ +0.41% | 约 `3.07~3.12` |
| 1.5x | -0.72% | -3.50% | -0.26% | `3.166`（+2.9%） |
| 2.0x | -0.74% | -5.59% | -0.26% | `3.236`（+5.1%） |

长期结论：`pacing_control_coef[region][hour]` 是可用的线上控制杠杆。它能把花费挪到配置想要的小时，且配置倾斜越强，实际花费重塑越强。但这个非锁预算实验只证明了券成本下降、guardrail 基本持平；不能证明“同等花费下 guardrail 更高”。这个问题需要固定预算 / 锁预算 treatment 才能回答。

##### 2.5.5.5.3 口径与设计结论/Metric and Design Conclusions

| 结论 | 数据依据 | 设计含义 |
|---|---|---|
| 发券强度系数对成本有可靠单调性。 | KP4 `ROI3Coef` 曲线在 ID / TH / VN 上都显示 voucher cost 单调响应；KP6 pacingByHour 中，配置强度增加时夜间花费份额 `13.3% → 15.9% → 17.5% → 20.1%`。 | 系数可以作为预算控制旋钮，用于 throttle 成本和重塑花费分布。 |

#### 2.5.6.1 预算分配与 Pacing

**天级预算闭环与拉格朗日选券。** ROI3 当前在天级预算等式约束 `sum(voucher_cost) = voucher_budget_day` 下，以逐请求拉格朗日打分分配预算：

```text

```

其中 `budget_coef` 是天级预算等式约束对应的影子价格，由 BCB（Budget Control Block）按花费进度调控。等式约束下 `budget_coef` 数学上不限制区间。（来源：KP10 epic-file.md §1.2）

**RCT 随机不发券概率。** RCT 实验组的随机不发券由 AB 参数 `Roi3NoVoucherProp`（float64）控制，不是硬编码。逻辑位于 `voucher_rct_selector.go`：

- 以概率 `p = Roi3NoVoucherProp` 随机不发券（reason = 17 randomNoVoucher）。
- 以概率 `1 - p` 从折扣分布中随机选一个档位发定折券（reason = 18 randomVoucher）。
- 折扣分布有两种模式：
  - 默认模式：2% (40%)、5% (40%)、8% (20%)。

- `Roi3NoVoucherProp` 的具体值在 AB 实验平台 [feature 2408](https://abtest.shopee.io/feature/42/detail/2408?featureDetailTab=values&tab=1) 中配置。

**Shopee 券体系与 ROI3 券型定位。** 回答"全场域有多少种券 / ROI3 是否有天然优势"时先锁语境，不要直接报单一数字：

- **平台券体系（三层）**：`PV = platform voucher`（平台券）、`SV = seller voucher`（商家券）、`FSV = free shipping voucher`（免邮券）。ROI3 广告券属于 **SV** 体系——它不是另一套独立的 voucher universe，而是 SV 在广告请求阶段的一条在线发券能力。
- **ROI3 在线候选券型**：`static / threshold / dynamic`，其中 `dynamic` 再分 `dynamic_discount / dynamic_price`。（2026-04-21 sample：impression 几乎全是 dynamic，`dynamic_price ≈ 90%` / `dynamic_discount ≈ 10%`，threshold/static 可忽略）
- **机制优势（可写死）**：广告请求阶段按 `user × item × voucher` 实时选券；与 `bid / boost / deduction / budget pacing` 同链路联动；曝光前即把发券收益和成本纳入排序/出价。
- **业务优势（不能写死）**：不能断言 ROI3 的 CTR/CVR/GMV/ROI/PC2 一定优于其他券型——需在统一对比口径（imp share / click / auto-claim / redeem / cost / ROI / pc2）下做数据比较。
- **出资视角独立**："谁出钱"（资助方）和 SV 券型分类是两件事，不能用 SV 分类替代出资方判断。
- **券类型维表**：`mp_voucher.dim_voucher__reg_live`（判断 `ADS-ROI`、统一 voucher type）。

> **边界**：ROI3 KB 能回答"ROI3 属于哪类券体系、在线候选怎么分"，但**全站券类型总数**需补上游 voucher / settlement 文档，不能仅靠 ROI3 卡片回答。

（来源：sub-kb `2.5-voucher/strategy.md` §3.1、`roi3_knowledge_template.md`）

> **仍缺（需 owner 补充）**：完整 unpicked reason 字典（非 RCT reason values）；engine 下游 API/协议字段。

| --- | --- |

比例数据可通过 tracking 表按上述口径统计。

**用户视角发券漏斗口径。** ROI3 更接近“系统在竞价阶段决定给哪张券”，不是用户先进入券中心手动领券。稳定的用户侧漏斗可先按以下节点解释：

```text
BestVoucherID / VoucherId 下发 -> impression -> click / auto-claim -> order -> redeem
```

如果产品口径必须显式拆“领取”，则写成：

```text
下发 -> 曝光 -> 点击 -> claim / auto-claim -> 成交 -> 核销
```

节点取证入口：

| 节点 | 取证字段/表 |
| --- | --- |
| 下发 | `BestVoucherID`、`VoucherId`、`bid_voucher_id` |
| 曝光 | tracking `operation = 1` 或 performance `impression_cnt` |
| 点击 | tracking `operation = 2` 或 performance `click_cnt` |
| claim / auto-claim | `is_auto_claimed_just_now`、`ads_voucher_auto_claimed` |
| order | tracking `operation = 5` 或 performance `order_cnt` |
| redeem | `mp_paidads.ads_order_voucher_1d__reg_s0_live` |

仍需注意：同一口径、全链路、精确漏斗率不适合作为静态 KB 真值写死，应按指定日期、region、entrance 重新跑数。

> **仍缺（需 owner/数据补充）**：用户视角各节点量化漏斗率。
