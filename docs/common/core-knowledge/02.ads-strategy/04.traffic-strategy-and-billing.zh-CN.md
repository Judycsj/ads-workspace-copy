## 2.4 流量策略和广告计费/Traffic Strategy and Ad Billing

### 2.4.1 Pacing/预算分配/Pacing/Budget Allocation

#### 2.4.1.1 定义与定位/Definition and Positioning

Pacing（预算平滑）是**平台层面**控制广告预算消耗速度的机制，确保每个广告的预算在投放周期内按合理节奏分配，从而最大化平台整体收入和广告主价值。LinkedIn、Meta、Google、eBay 等主流广告平台均将 Pacing 作为广告投放系统的核心组件。

**与出价调控（[§2.3.3](03.bidding-products-and-algorithms.zh-CN.md#233-出价调控技术)）的关系：**


| 维度       | 出价调控（λ 调控）          | Pacing（预算平滑）                                          |
| -------- | ------------------- | ----------------------------------------------------- |
| **视角**   | 单个广告主/广告计划          | 平台全局                                                  |
| **目标**   | 成本达成（CPA/ROAS）或预算花完 | 预算在时间维度上平滑消耗，全局竞价效率最优                                 |
| **调控对象** | 出价系数 λ              | 消耗速度（pass-through rate / pacing multiplier / deboost） |
| **协同关系** | λ 决定"出多少价"          | Pacing 决定"何时出价"或"以多大力度参与竞拍"                           |


两者协同工作： Pacing 在宏观层面控制广告的流量获取节奏，出价调控在微观层面优化每次竞价的出价水平。

#### 2.4.1.2 核心问题：预算撞线（Budget Hitting）/Core Problem: Budget Hitting

- **现象**：凌晨时段高预算消耗率（大小预算广告均存在）
- **后果**：优质广告过早耗尽预算，导致广告候选池规模从凌晨开始递减，竞价激烈程度持续减弱，广告错过晚高峰高价值流量

**双重负面影响：**


| 影响层面     | 具体问题                                |
| -------- | ----------------------------------- |
| **广告主侧** | 晚高峰（多数广告核心转化时段）无法触达，实际 advv 低于潜在最优值 |
| **平台侧**  | 晚高峰竞价深度不足导致 CPC 下滑，整体收入未达最优水平       |


**撞线的连锁反应：** 当大量广告在凌晨和上午阶段耗尽预算后，下午和晚高峰时段的竞价池急剧缩小。竞价深度下降直接压低 CPC（二价拍卖机制下，竞争者减少意味着次高价更低），即使剩余广告赢得了更多曝光，单次点击收入也大幅降低。对广告主而言，"撞线"意味着错失了一天中转化率最高的时段，等价于用低价值流量消耗了本可用于高价值流量的预算。

#### 2.4.1.3 业内 Pacing 方法分类/Industry Pacing Method Classification

业内 Pacing 方案可分为四种主要方法，核心差异在于**调控系数的定义**以及**对排序和计费的影响方式**：


| 方法                  | 调控系数                                           | 对排序的影响                                      | 对计费的影响                            | 代表系统                                                    |
| ------------------- | ---------------------------------------------- | ------------------------------------------- | --------------------------------- | ------------------------------------------------------- |
| **Hard Throttling** | 参竞概率 `p`（pass-through rate, PTR）， `p ∈ [0, 1]` | 未参竞的请求排序分 = 0（直接移除候选）                       | 无影响（未参竞则无计费）                      | LinkedIn Pacing (KDD 2014)                              |
| **Rank Deboost**    | 排序 pacing coef `α`，作用于 eCPM 排序分                | `rank_score = α × ecpm + porg`，α < 1 时排序分下降 | **不影响计费**（扣费公式仍按原始 ecpm 计算）       | 当前方案                                                    |
| **Bid Shading**     | 出价 pacing coef `β`，直接乘以出价                      | `rank_score ∝ β × bid × pCTR`，排序分随 β 下降     | **影响计费**（扣费基于调整后的出价，广告主实际 CPC 降低） | Meta Mystique (WWW 2024)、eBay AdaptivePacing (WWW 2024) |
| **Lambda 融合**       | 将 pacing 信号融入出价调控因子 λ                          | 通过 λ 统一影响排序（λ 本身就是出价乘数）                     | **影响计费**（λ 调整出价后的扣费按调整后计算）        | 与 [§2.3.3](03.bidding-products-and-algorithms.zh-CN.md#233-出价调控技术) 出价调控统一                          |


**四种方法详细说明：**

**1) Hard Throttling（概率过滤）**

对每次竞拍以概率 `p`（PTR）决定广告是否参与。消耗过快时降低 PTR，消耗过慢时提高 PTR。

- **调控系数**： `p ∈ [0, 1]`，实现为 Bernoulli 采样 `participate = Bernoulli(p)`
- **排序**：未参竞请求直接从候选池移除，不进入排序
- **计费**：与计费完全解耦——参竞时按正常出价和 GSP/GFP 规则扣费，不参竞则无计费
- **优点**：实现最简单，与出价和排序系统完全解耦
- **缺点**：对高价值请求和低价值请求一视同仁，可能过滤掉本可高效转化的竞拍机会

**2) Rank Deboost（排序打压）**

Pacing 系数仅作用于排序分，不改变出价和扣费逻辑。

- **调控系数**：排序 pacing coef `α`，作用于粗排和混排的 eCPM 排序分
- **排序**： `rank_score = α × ecpm_weight × ecpm + porg`， `α < 1` 时降低广告排序竞争力，减少赢拍概率
- **计费**：**不影响**——扣费公式中使用的是原始 ecpm（不含 α），广告主实际 CPC 不受 pacing 影响
- **优点**：与计费系统完全解耦，不改变广告主的出价和扣费体验
- **缺点**：调控效果间接——α 降低排序分不一定线性地降低赢拍概率，效果依赖排序竞争格局

**3) Bid Shading（出价调整）**

Pacing 系数直接乘以广告出价，同时影响排序和计费。

- **调控系数**：出价 pacing coef `β`， `adjusted_bid = β × original_bid`
- **排序**： `rank_score ∝ β × bid × pCTR`，排序分随 β 同比例变化
- **计费**：**影响计费**——GSP 扣费基于调整后的出价排序，广告主实际 CPC 随 β 降低而降低
- **优点**：排序和计费一致，调控效果直接且可预测
- **缺点**：改变了广告主的实际扣费，需要与出价调控 λ 做好交互设计（避免双重调控冲突）

**4) 出价调控因子 λ融合（与出价调控统一）**

将 Pacing 信号直接融入出价调控因子 λ（[§2.3.3](03.bidding-products-and-algorithms.zh-CN.md#233-出价调控技术)），不单独维护 pacing 系数。

- **调控系数**：λ 同时承载成本/ROI 调控和预算 pacing 两个目标
- **排序**：通过 λ 调整出价，间接影响排序
- **计费**：**影响计费**——与 Bid Shading 类似，λ 调整后的出价参与扣费计算
- **优点**：系统最简洁，无需额外 pacing 模块；预算 pacing 和成本调控统一优化
- **缺点**：λ 需同时兼顾成本达成和预算平滑两个目标，调控复杂度高（参见 [§2.3.3.1.3](03.bidding-products-and-algorithms.zh-CN.md#23313-mcb 预算消耗--roi-下界约束) 双约束问题）

**实时调控算法：** 上述四种方法的调控系数（p / α / β / λ）均可通过 PID 或 MPC 算法实时更新：

- **PID 控制器**：基于当前消耗与目标消耗的偏差（误差信号），通过比例-积分-微分反馈调整系数。反应式调控，实现简单
- **MPC 控制器**：通过 Bid2X 模型预测不同系数值下的未来消耗趋势，在预算花费速度和出价目标约束之间 balance 选取最优系数值（如剔除撞线时间早于指定时间点的系数值）

#### 2.4.1.4 目标消耗曲线与实时调控/Target Spending Curve and Real-Time Control

Pacing 的完整流程分为两步：**离线确定目标消耗曲线**（预算应当按什么节奏花完）和**在线实时调控**（调整 [§2.4.1.3](#2413-业内-pacing-方法分类) 中的系数使实际消耗跟踪目标曲线）。

**一、目标消耗曲线设计（Spending Curve）**


| 策略                                  | 描述                          | 适用场景               |
| ----------------------------------- | --------------------------- | ------------------ |
| **Even Pacing（均匀分配）**               | 预算按时间均匀分配（如日预算 / 24 小时）     | 品牌曝光类广告，不关注特定时段转化  |
| **Traffic-weighted Pacing（流量加权分配）** | 预算按历史流量价值分布加权分配，高价值时段分配更多预算 | 效果类广告，关注 GMV/转化最大化 |


Traffic-weighted Pacing 的曲线设计要点：

- 基于历史数据统计各时间段的**流量价值指数**（综合 GMV、转化率、CPC 等指标）
- 重点识别和保障**晚高峰特征**（通常 18:00-22:00），该时段转化率和 GMV 占比显著高于其他时段
- 曲线通常以半小时或小时为粒度，并按地区/品类差异化配置

**二、在线实时调控**

目标消耗曲线确定后，在线层分钟级监控实际消耗与目标的偏差 `error(t) = actual_spend(t) - target_spend(t)`，通过 PID 或 MPC 算法实时更新 [§2.4.1.3](#2413-业内-pacing-方法分类) 中的调控系数（p / α / β / λ）：


| 调控算法    | 如何更新系数                                                                                   | 适用方法                         |
| ------- | ---------------------------------------------------------------------------------------- | ---------------------------- |
| **PID** | 基于当前偏差的比例-积分-微分反馈， `error > 0`（消耗过快）→ 减小系数抑制消耗， `error < 0` → 增大系数加速消耗                   | 四种方法均适用，实现简单                 |
| **MPC** | 通过 Bid2X 模型（[§2.3.4](03.bidding-products-and-algorithms.zh-CN.md#234-bid2x-mpc-预估模型)）预测不同系数值下的未来消耗轨迹，选取满足"预算在目标时间花完"约束下使投放效果最大化的系数值 | 主要用于 Bid Shading 和 Lambda 融合 |


**不同方法下调控的具体差异：**

- **Hard Throttling + PID**： PID 输出 PTR 增减量， `p(t+1) = clip(p(t) + Δp, 0, 1)`。调控粒度粗（参与/不参与是二元决策），但实现最简单
- **Rank Deboost + PID**： PID 输出 α 增减量，α 作用于排序分。由于 α 与赢拍概率的关系非线性（取决于竞争格局）， PID 参数需要针对不同竞价深度分别调优
- **Bid Shading + PID/MPC**： PID 或 MPC 输出 β 值，β 直接乘以出价。由于 β 同时影响排序和计费，调控效果更直接可预测； MPC 可利用 Bid2X 模型精确预测不同 β 下的消耗轨迹
- **λ 融合 + MPC**：λ 同时承载成本调控和预算 pacing 两个目标， MPC 在搜索最优 λ 时需同时满足成本/ROI 约束和预算平滑约束（参见 [§2.3.3.1.3](03.bidding-products-and-algorithms.zh-CN.md#23313-mcb 预算消耗--roi-下界约束) 双约束问题）

**三、两层架构（参考 Mystique）**


| 层级      | 职责                                   | 更新频率 |
| ------- | ------------------------------------ | ---- |
| **离线层** | 基于历史消耗数据和流量分布，为每个广告计划生成日级目标消耗曲线      | 天级   |
| **在线层** | 实时监控实际消耗与目标曲线的偏差，通过 PID/MPC 动态调整调控系数 | 分钟级  |

#### 2.4.1.6 Pacing 为何由平台控制/Why Pacing Is Platform-Controlled

Pacing 是**平台级**而非**广告主级**的调控机制，当前不支持广告主自行选择是否开启 Pacing。核心原因：

1. **全局最优 vs 个体最优**：单个广告主关闭 Pacing 可在凌晨抢占更多低价流量，但若所有广告主都关闭 Pacing，凌晨竞价深度暴涨、晚高峰竞价池枯竭，平台整体 CPC 和广告主群体 advv 均下降（[§2.4.1.2](#2412-核心问题预算撞线budget-hitting) 中的撞线连锁反应）
2. **博弈均衡问题**：Pacing 开关一旦可选，理性广告主会选择关闭以获取短期优势，形成囚徒困境——均衡结果是所有人关闭，回到撞线问题
3. **eCPM 竞价公平性**：Pacing 通过调整 ecpm_weight 影响排序分，如果部分广告主不受 Pacing 约束，它们在竞价中具有不对等优势，破坏二价拍卖的公平性

### 2.4.2 流量扶持框架/Traffic Support Framework

#### 2.4.2.1 扶持动机与业界思路/Motivation and Industry Approaches

广告系统主要依靠竞价机制从全量候选中筛选广告，天然存在**马太效应**：历史数据丰富的成熟广告在召回中更易命中、在排序中预估更准确，而新广告/冷启动广告因数据不足在各环节均处于劣势。流量扶持（Business Support / Traffic Boost）通过人工干预和策略调整，在竞价框架之上叠加定向扶持能力，解决以下问题：


| 扶持场景         | 说明                                                      |
| ------------ | ------------------------------------------------------- |
| **冷启动广告扶持**  | 新广告缺乏历史数据，在召回阶段易被忽略、在排序中 pCTR/pCVR 预估不准，需通过扶持给予曝光机会积累数据 |
| **平衡广告主利益**  | 头部广告主可能垄断流量，为中小广告主或长尾商品设置扶持队列，避免流量集中化，提升广告主留存率          |
| **满足特定业务目标** | 优先推广特定商家（如迁移 ROI2.0 商家、拉新商家、低预算使用率商家）                   |


**业界通用解法**可从三个维度归纳：


| 维度      | 核心思路                   | 典型方法                                                                            |
| ------- | ---------------------- | ------------------------------------------------------------------------------- |
| **模型侧** | 提升模型对弱势广告的预估准确性        | 预估校准（保序回归）、减少 ID 类特征增加泛化特征（统计特征、embedding、实时特征）、E&E 探索利用（Bandit / RL）、长尾广告的迁移学习 |
| **机制侧** | 扩量 + 调整排序，以收入损失换扶持目标达成 | 独立召回通路、Rank Boost 提权、Quota 保送、流量配额（按广告主/品类分配最低曝光份额）、分级流量放大、进退场机制                |
| **产品侧** | 降低目标广告的竞争门槛            | 专属广告资源位、一键起量工具、定向流量包、业务专属活动位                                                    |


**流量调控技术演进**（以内容平台实践为参考，思路同样适用于广告扶持场景）：

```
强插 → 提权(Boost) → 保量 → 差异化保量
```

- **强插**：最原始方式，直接在结果中插入目标广告/内容，体验差
- **提权（Boost）**：在粗排/重排阶段给目标广告的排序分乘以 > 1 的系数，实现简单但曝光量对系数敏感
- **保量**：为每个目标广告设定保量目标（如 24h 内 100 次曝光），根据已有曝光与目标的差距动态调整提权系数
- **差异化保量**：根据广告质量、广告主价值等信号为不同广告设定不同保量目标，达标后停止扶持转为自然竞争

这一从粗粒度到精细化的演进路线不仅适用于冷启动，也适用于其他扶持场景（如为低预算使用率广告保量、为特定业务广告差异化分配流量）。

**扶持的代价与权衡**：**任何扶持本质上都是以短期收入/效率损失换取长期生态健康**。学术研究表明，精心设计的冷启动算法可将成功率提升 60%+ 而短期收入损失仅 < 1%（参见 [§2.4.2.8](#2428-关键参考文献)）。核心优化目标是**以最小的收入/效率损失获取最佳的扶持效果**——无论是冷启动成功率、广告主留存率还是特定业务目标的达成率。

#### 2.4.2.2 全链路扶持框架设计/Full-Funnel Support Framework Design

**扶持框架的设计要素**

早期的扶持系统往往是各业务方在链路各模块中零散添加干预逻辑，随着业务增多，在圈选能力、策略精细度、代码复用、效果衡量等方面暴露诸多不足。一个好的扶持框架应具备以下设计要素：


| 设计要素             | 说明                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------- |
| **候选圈选灵活**       | 不仅支持离线打标，还能根据链路上下文（召回通路、用户实时特征）动态决定候选是否需要扶持；人群/query 圈选规则可配置化，新增规则无需开发新字段和算子                                         |
| **调权策略精细化**      | 超越简单的提权/降权，提供通用策略算子（quota 保送、出价调权、动态强插）和定制化插件接口，支持混排阶段的动态出价扶持等精细化流量择优策略                                              |
| **全链路统一管控**      | 所有人工干预策略绑定到统一的业务队列（Tag），通过队列打标逻辑统一控制策略的生效范围和具体参数，避免不同业务在各模块重复开发相似的干预逻辑                                               |
| **新业务接入敏捷**      | 通过配置化的基础算子（圈选、打标、调权、保送、出价）完成大多数业务需求， 0 代码开发；复杂需求提供自定义算子插件接口                                                          |
| **扶持成本可衡量**      | 能量化每个扶持业务的收入/效率损失（如 eCPM 下降、CTR 稀释），而非仅靠 AB 实验事后评估                                                                   |
| **扶持效果/ROI 可衡量** | 提供分业务队列的效果例行监控（曝光占比、渗透率、XTR 后验、漏斗各阶段拉空率和候选占比等），白盒化各业务队列对大盘的影响面和效果                                                    |
| **预算分配最大化 ROI**  | 在有限的扶持预算（流量份额）下，自动优化各业务队列的配额分配，最大化整体扶持 ROI                                                                           |
| **漏斗监控与归因**      | 各截断漏斗的业务队列候选统计（平均 item 数量、候选数量 >= 3/5/10/30 的请求比例、队列候选占比 >= 1%/3%/5%/10%/30% 的请求比例等），支持快速定位扶持失效环节；策略代码年久失修时能及时发现负向效果 |


基于以上设计要素，我们的全链路扶持框架的核心设计理念：**所有人工策略都挂载到统一的 Tag 体系上，通过配置驱动，工程定位为通用的策略引擎**。框架支持多业务共存，新业务可在 2 个工作日内完成小流量上线。

#### 2.4.2.3 候选圈选与打标/Candidate Selection and Tagging

扶持框架通过两层 Tag 实现精细化的候选圈选：

**Item Tag（离线打标）：**

- 不同业务对应不同的候选池，池内 item 打上相同的 item_tag
- Tag 由 **64 位 bit** 构成，每个 bit 代表一种业务，对应位为 1 表示该业务生效
- 数据流：业务方提供候选 item → 写入统一 tag 表 → 同步到 Redis → 通过 Tag Service 更新到 ads info 正排

**Biz Tag（在线计算）：**

- 为实现**定向扶持**（只对特定人群/query 生效），在线根据用户特征和 query 特征实时计算 biz_tag
- 同样为 64 位 bit，每个 bit 代表一种人群/query 类别
- 依赖 FSE 特征表中的用户画像（性别、年龄、点击量、购买量、行为序列）和 query 理解特征

**Tag 组合逻辑**：在线请求时， `item_tag AND biz_tag` 对应位均为 1 才激活扶持，即同时满足"该 item 属于扶持候选"且"该用户/query 属于目标人群"。

#### 2.4.2.4 分库召回/Separate-Index Recall

为扶持业务建立**独立召回队列**（独立 item 索引），每次请求从中单独召回 TopK，避免扶持候选在通用召回中被淹没。根据底层召回通路类型，分为三类实现：


| 召回类型       | 实现方式                                                        | 适用场景                   |
| ---------- | ----------------------------------------------------------- | ---------------------- |
| **KV 类召回** | 离线用 tag 过滤种子 item 的倒排拉链，保留匹配 tag 的结果，生成子队列写入 Redis          | itemCF 等统计类召回          |
| **离线向量召回** | 离线用 tag 过滤候选 embedding，在过滤后的子集上重新计算 I2I / U2I / Q2I 并取 TopK | deep I2I、offline Q2I 等 |
| **在线向量召回** | 在线 Vespa HNSW 检索时通过 tag 过滤，在每层检索相邻邻居时按 tag 筛选               | online Q2I、online U2I  |


多个业务的子队列通过 **zigzag 合并**生成一个融合的影子队列，在线按 `model_name` 区分不同队列进行检索。

#### 2.4.2.5 全链路统一调权/Unified Full-Funnel Weight Adjustment

扶持候选经过召回后，在后续每个漏斗环节接受统一的调权处理：

**Step 1 — 业务队列打标（Recall → Prerank）：**

Zigzag 对多路召回结果合并时，同步对候选进行 biz_tag 打标。打标后形成**多个业务队列**（有 tag 标记）和**一个非业务队列**，一起送入粗排。

**Step 2 — Quota 保送（Prerank → Rank）：**

在 Prerank 打分结束后，对有保送需求的业务队列，按 `biz_tag` 识别并按 `reserveQuotaRatio`（配置比例，通常 5%~10%）从业务队列中取 TopK，**强插到候选结果头部**直接保送到 Rank 阶段。保送候选豁免 zigzag 截断和 Prerank 后的其他策略过滤。

**Step 3 — Rank Boost 调权（Rank → MixRank）：**

在 Rank 阶段，传入 item_tag，读取对应业务的配置信息（ `pidBasedCoef`、`ruleBasedCoef` 等），对扶持候选进行排序分调权。调权后重排序，确保扶持候选在排序中更靠前。

**与计费的关系**： `rank_boost` 参与排序分计算但**不参与扣费**——在 [§2.4.3.1](#2431-product-ads) 的扣费公式中， `rank_boost` 被显式扣除：

```
deduction_price[i] = (rank_score[i+1] - porg[i] - ecpm_weight[i] × rank_boost[i])
                     / (ecpm_weight[i] × pctr[i])
```

#### 2.4.2.6 退出机制/Exit Mechanism

扶持不是永久的，需设计合理的退出条件避免过度干预：


| 退出条件       | 说明                                  |
| ---------- | ----------------------------------- |
| **冷启动完成**  | 广告积累足够的曝光/点击/转化数据后退出扶持队列，回归自然竞争     |
| **业务目标达标** | 如低预算使用率广告扶持 K 天后预算使用率达标（如 > 50%）则退出 |
| **扶持预算耗尽** | 后链路停止扶持（召回侧可能仍保留候选，存在少量 quota 浪费）   |
| **渐进式退出**  | 逐步降低 boost 系数而非突然停止，避免断崖式流量变化导致数据恶化 |


过度扶持的风险：如果 boost 力度过大，广告会展示给不匹配的受众，导致 CTR/CVR 异常偏低，冷启动后反而被排序模型长期打压。因此扶持力度需在"充分曝光"与"精准匹配"之间取得平衡。

#### 2.4.2.7 策略配置与监控/Strategy Configuration and Monitoring

框架通过 **AB 参数**配置各业务的扶持策略，参数以业务名为前缀（如 `coldStart_`），支持多业务共存：


| 参数名                 | 类型    | 说明                             | 作用域            |
| ------------------- | ----- | ------------------------------ | -------------- |
| `itemTagMask`       | int   | 该业务使用的 bit 位（1-64），关联 item tag | 全链路            |
| `bizTagMask`        | int   | 该业务使用的 bit 位（1-64），关联 biz tag  | 全链路            |
| `reserveQuotaRatio` | float | 粗排后业务队列的保送 quota 比例， 0 表示不保送   | 粗排后            |
| `pidBasedCoef`      | float | 基于 PID 调控的扶持力度系数，默认 1.0        | Online Bidding |
| `ruleBasedCoef`     | float | 手动配置的扶持系数                      | Online Bidding |


**监控**：通过 biz_tag 对应的 tag_id 统计各业务队列在漏斗不同阶段（召回、粗排、精排、混排）的平均候选数量，用于评估扶持效果和漏斗损耗。

### 2.4.3 混排和计费/Mixed Ranking and Billing

**Pacing 与混排的协同：**

Pacing（[§2.4.1](#241-pacing预算分配pacingbudget-allocation)）和混排通过排序分公式协同工作：

1. **Pacing 调控排序分**：当前方案 Rank Deboost 的 pacing coef α 直接乘以混排排序分中的 eCPM 部分（`rank_score = α × ecpm_weight × ecpm + porg`），α < 1 时降低广告在混排中的竞争力
2. **混排决定展示位次**：混排阶段按调整后的 rank_score 与有机内容竞争坑位，α 降低 → 广告排名靠后 → 赢拍概率下降 → 消耗减速
3. **扣费与 Pacing 解耦**：扣费公式使用原始 ecpm（不含 α），广告主实际 CPC 不受 pacing 影响

整体效果：Pacing 在时间维度控制"何时以多大力度参与竞拍"，混排在空间维度决定"广告出现在哪个位置"，两者通过 rank_score 串联——Pacing 调整排序分的强度，混排根据调整后的排序分分配坑位。

**各广告类型差异：**

各广告类型的扣费形式、计费点和混排优化目标存在显著差异：


| 维度         | Product Ads                                                  | Brand & Shop Ads  | Video Ads                                                   | Live Ads                                        |
| ---------- | ------------------------------------------------------------ | ----------------- | ----------------------------------------------------------- | ----------------------------------------------- |
| **扣费形式**   | GSP（多坑拍卖）                                                    | GFP（单坑拍卖）         | GSP（多坑拍卖）                                                   | FP（引入 rankcap & bidcap 进行二价打折）                  |
| **计费点**    | Click                                                        | Click             | 明投： Impression；暗投： Click                                    | 明投： Impression；暗投： Click                        |
| **混排优化目标** | Rcmd： order/gmv/rev/pc2； Search： order/gmv/relevance/rev/pc2 | 无混排（投放链路完全由广告侧控制） | 部分场景（如 ID trending）： rev/order/gmv/pc2/watchtime；其他大部分场景：强插 | rev/order/gmv/pc2/watchtime/follow/comment/like |


#### 2.4.3.1 商品广告/Product Ads

Product Ads 采用 **uGSP（Unified Generalized Second Price）** 结算机制，在 GSP 基础上引入质量得分，综合考虑广告 eCPM、推荐侧 pGMV、relevance 等信息。GMV Max 产品的广告与有机流量通过 API0-API3 交互完成融合投放，详见 [§2.3.5](03.bidding-products-and-algorithms.zh-CN.md#235-gmv-max-自动出价)。

**流量入口统一计费：** Product Ads 覆盖 Search 和 RCMD 两大流量类型，RCMD 包括 DD（Daily Discover）、YMAL（You May Also Like）、PP（Promoted Placement）、GAME、IN_SHOP（店铺内页推荐）等入口组。所有 Product Ads 入口组共享相同的 uGSP 扣费逻辑和点击计费方式，不因流量入口不同而产生计费差异。

**排序分公式：**

```
ads rank_score = ecpm_weight × (ecpm + rank_boost) + porg
```

- `ecpm_weight`： eCPM 权重（即混排公式中的 alpha）
- `ecpm = cpc_bid × pCTR`
- `rank_boost`：广告侧的扶持项
- `porg`：非 eCPM 打分（推荐/相关性），系数固定为 1（即混排公式中的 beta = 1）

**ecpm_weight 的配置与调优：**

实操中 porg 系数（beta）固定为 1，只调 `ecpm_weight`（alpha）。`ecpm_weight` 基于 ads-free 组的 GMV loss 采用 PID 动态调节，保证广告带来的用户体验折损可控。调控分为长短窗口两层：

1. **长窗口（天级）**：确定目标 adload。由于 GMV loss 波动较大，短周期 PID 不直接控 GMV loss，而是控 adload；长周期则基于不同 adload 下的 GMV loss 数据，确定在目标 GMV loss 范围内对应的目标 adload
2. **短窗口（分钟级）**：PID 反馈调节实时 adload，使其跟踪长窗口确定的目标 adload

本质上，`ecpm_weight` 越大，广告在混排中竞争力越强、adload 越高、GMV loss 越大；反之 `ecpm_weight` 越小，广告竞争力下降、adload 降低、GMV loss 减小。PID 通过动态调整 `ecpm_weight` 在收入和用户体验之间取得平衡。

**扣费公式（点击计费）：**

```
deduction_price[i] = (rank_score[i+1] - porg[i] - ecpm_weight[i] × rank_boost[i]) / (ecpm_weight[i] × pctr[i])
```

**排序与扣费中的 Additional 系列字段：**

online-bidding 精排阶段通过 `DeductionParam` 输出三个 Additional 系列字段给 ads-engine 扣费阶段，上述公式中的 `rank_boost` 在工程实现中即对应 `AdditionalBoost`：

| DeductionParam 字段 | 含义 | 对排序的影响 | 对扣费的影响 |
|---------------------|------|-------------|-------------|
| `AdditionalBoost` | 额外排序提升（如券利润 voucher_profit、扶持 boost） | 参与最终排序：`final_rank = ecpm + AdditionalBoost`，提升展示位次 | **不参与扣费**——扣费公式中被显式扣除 |
| `AdditionalDeboost` | 额外排序打压（如超投 deboost、pacing deboost） | 降低排序竞争力 | **不参与扣费**——与 Rank Deboost 同理 |
| `AdditionalDeductionPrice` | 直接叠加的额外扣费金额（绝对值，CPC 单位） | 不影响排序 | **直接参与扣费**——CPC 模式下直接加到 deduction_price；oCPM 模式下乘以 pctr 后叠加 |

ads-engine 的两次排序机制：
1. 第一次排序（纯 ecpm，不含 boost）→ 记录 `NextRankScoreWithoutBoost` 用于二价扣费参考
2. 第二次排序（ecpm + AdditionalBoost）→ 决定最终展示顺序

因此"页面上看到的广告顺序"和"二价结算参考分"并非同一个值。

与 `pOrg` 的关系：`pOrg` 是推荐侧非 eCPM 打分（organic score），在排序分和扣费中与 `AdditionalBoost` 独立——排序分 = ecpm_weight × (ecpm + AdditionalBoost) + pOrg，扣费时 pOrg 和 AdditionalBoost 都被扣除，确保广告主仅为自身 eCPM 竞争力付费。

**uGSP 与标准 GSP 的核心区别：**


| 维度    | 标准 GSP    | uGSP                  |
| ----- | --------- | --------------------- |
| 排名依据  | 仅按出价排序    | 按 f(出价, 质量得分) 排序      |
| 支付价格  | 直接取下一名的出价 | 下一名综合得分折算为当前质量得分对应的价格 |
| 目标    | 最大化平台短期收入 | 平衡收入与广告质量             |
| 广告主策略 | 仅优化出价     | 需同时优化出价和广告质量（CTR/CVR） |


**扣费价格裁剪（Deduction Bounds）：**

uGSP 二价公式计算出裸扣费价格后，还需经过多层裁剪确保价格合理：

```
1. second_price_ratio 保底：deduction_price = max(deduction_price, second_price_ratio × bid)
2. cap_deduction_price_ratio 封顶：deduction_price = min(deduction_price, cap_ratio × ugsp_price)
3. first_price_cap：deduction_price = min(deduction_price, bid × first_price_cap_coef)
4. 国家级最小价格：deduction_price = max(deduction_price, country_min_delta_price)
5. 广告级 min_cap / max_cap：clip(deduction_price, DeductionPriceMinCap, DeductionPriceMaxCap)
   （若为 0 则回退到 AB 参数 FallBackMinDeductionPriceCap / FallBackMaxDeductionPriceCap）
```

| 裁剪层 | 作用 | 来源 |
|--------|------|------|
| `SecondPriceRatio` | 防止二价过低（保底） | online-bidding DeductionParam |
| `CapDeductionPriceRatio` | 防止二价过高（封顶，相对于裸 uGSP 价格） | AB 实验参数 |
| `FirstPriceCapCoef` | 一价上限，确保扣费不超过出价的一定比例 | AB 实验参数 |
| `country_min_delta_price` | 国家级最低扣费，避免极端低价 | 国家配置 |
| `DeductionPriceMinCap/MaxCap` | 广告级保底/封顶 | online-bidding 按广告维度设置 |

OCPM 路径额外施加 `DeductionPriceMaxCap × OcpmMaxCapPctr` 上限，防止低转化率场景下 OCPM 扣费超出等价 CPC 上限。

#### 2.4.3.2 店铺广告/Shop Ads

Shop Ads 采用 **GFP（Generalized First Price，单坑拍卖）** 结算，投放链路完全由广告侧控制（Recall → Relevance Filter → Ranking → Rerank → Send），**无混排**。计费点为 Click。

#### 2.4.3.3 视频广告/Video Ads

Video Ads 采用 **GSP（多坑拍卖）** 结算：

- **明投（Mingtou）**：计费点为 Impression
- **暗投（Antou）**：计费点为 Click
- 仅部分场景（如 ID trending 等）存在混排，关注 rev/order/gmv/pc2/watchtime（需考虑 eCPM 与非收入/非 GMV 目标的兑换）
- 其他大部分地区和场景目前使用**强插**（Enforced Placement，不论自然排名直接置入指定位置）

#### 2.4.3.4 直播广告/Live Ads

Live Ads 采用 **FP（First Price）** 计费，通过引入 rankcap & bidcap 进行二价打折（效果类似二价）：

- **明投（Mingtou）**：计费点为 Impression
- **暗投（Antou）**：计费点为 Click
- 混排优化目标： rev/order/gmv/pc2/watchtime/follow/comment/like（需考虑 eCPM 与非收入、非 GMV 目标的兑换）

#### 2.4.3.5 超投防控/Over-Delivery Prevention

超投（Over-Delivery）指广告剩余预算不足以覆盖最后一次扣费，导致 `expected_rev > real_rev`，平台产生收入损失（rev_loss）。超投防控贯穿召回到计费的全链路：

| 阶段 | 机制 | 说明 |
|------|------|------|
| **Recall** | `OVERDELIVERYANTIFRAUDFILTER` | 在召回阶段基于反作弊策略过滤高风险广告，详见 [§3.3](../03.ads-engine/03.ads-recall-service.zh-CN.md) |
| **API2（在线出价）** | 超投风险判断 + deboost + additional_deduction | online-bidding 比较 `cpc_bid` 与 `rt_remain_budget`，对超投风险广告降低排序分（deboost）并计算 `additional_deduction` 降低扣费，详见 [§2.3.3.6](03.bidding-products-and-algorithms.zh-CN.md#2336-product-ads-超投控制策略) |
| **API3（扣费）** | Deduction bounds | 扣费裁剪层（min_cap/max_cap/first_price_cap）兜底防止极端扣费，详见上文扣费价格裁剪 |

#### 2.4.3.6 oCPM 与 oCPC 的计费差异/oCPM vs oCPC Billing Differences

oCPM（Optimized CPM）和 oCPC（Optimized CPC）在出价策略、排序、保留价、超投控制、boost 等机制上**完全一致**，唯一差异在于**扣费公式的量纲**：

| 维度 | oCPC | oCPM |
|------|------|------|
| **计费点** | Click（点击） | Impression（曝光） |
| **扣费公式** | `deduction_price = (NextRankScore - Porg) / (EcpmWeight × Pctr)` | `deduction_price = (NextRankScore - Porg) / EcpmWeight` |
| **量纲** | 每次点击价格（CPC） | 每千次曝光价格（CPM），不除以 Pctr |
| **AdditionalDeductionPrice** | 直接加到 deduction_price | 乘以 Pctr 后加到 deduction_price（量纲对齐） |
| **封顶** | `DeductionPriceMaxCap` | `DeductionPriceMaxCap × OcpmMaxCapPctr`（额外乘以 Pctr 校准系数） |

**其他机制无差异**：二价率计算、deduction_reason 分类、保留价（`ReservePriceBeta/Tr`）、超投检测与 deboost、boost 逻辑在 oCPM 和 oCPC 之间完全相同。

**量纲换算**：oCPM 扣费价格 ≈ oCPC 扣费价格 × Pctr × 1000。即同一个广告在 oCPM 模式下的单次曝光扣费 = oCPC 模式下的点击扣费 × 点击率。

#### 2.4.3.7 预算撞线与 Dormant 机制/Budget Exhaustion and Dormant Mechanism

Dormant（休眠）是预算撞线后广告的一种特殊状态：对于**已耗尽预算且超收**的广告，系统不将其下线，而是让其继续展示以增加可归因的广告价值（advv），从而提升广告主的投放效果。

**核心逻辑**：预算撞线的广告若已超收（实际 advv < 预期水平），继续展示可积累更多归因转化（如订单、GMV），有助于改善广告主的 ROI 表现，同时不会产生额外扣费。

**各模块的 Dormant 处理：**

| 模块 | 行为 | 说明 |
|------|------|------|
| **召回** | `AdsDormantConversionCheck` | 广告可见性检查：Search、DD/YMAL/PP 入口对 dormant 广告检查 TagB 休眠转化标签，命中则允许参竞；未命中则过滤（Unpick Reason: `OfflineFilterAdsDormantConversion`）。详见 [§2.1](01.recall-and-supply-strategy.zh-CN.md) AdsInfoFilter |
| **出价** | 软下线 / coef 极低 | GmvMax 场景下，`FinalRemainBudget <= 0` 时 `CoefTotal` 置为 `1e-6`（接近零出价），标记 `hit_budget_cap`。详见 [§2.3.3](03.bidding-products-and-algorithms.zh-CN.md#233-出价调控技术) |
| **Boost** | Dormant campaign 剔除 | boost-support-service 对 dormant campaign 的三条件判断：(1) 所有广告均命中 dormantTagBit=64；(2) `visible_start_ts` 在 campaign start 之后；(3) `visible_start_ts` 在未来。三者同时满足才剔除，否则仍参与权重计算 |
| **结算** | 不扣费 | Dormant 广告的展示不产生扣费（预算已耗尽），仅用于归因转化积累 |
| **Voucher** | `deduction_reason = 1` | 撞线后的 dormant 广告通过 `deduction_reason = 1` 标识，与常规 ads 发券和 non-ads 发券（`pricing_type = 29`）区分。详见 [§2.5](05.ads-smart-voucher.zh-CN.md) |
| **Adsload** | 不计入竞价 | 撞线广告不参与正常竞价，降低实际广告密度 |
