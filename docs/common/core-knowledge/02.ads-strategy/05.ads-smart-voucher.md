## 2.5 广告智能优惠券/Ads Smart Voucher

### 2.5.1 广告优惠券概览/Ads Voucher Overview

Ads Smart Voucher is the Product Ads voucher layer for ROI3 / ROI4(cofund). It does not merely change the bid; it adds a decision layer for "whether to issue a voucher, how large the voucher should be, and who bears the voucher cost" on top of the normal auction. The synchronized source KBs are `docs/common/sub-kb/2.5-voucher/strategy.md` (ROI3 strategy, online chain, analysis contract; last verified 2026-04-22, confidence medium) and `docs/common/sub-kb/2.5-voucher/model.md` (Uplift ROI3 model, sample, feature, strategy, SQL and playbook bundle; last verified 2026-04-30, confidence medium).

The practical ROI3 knowledge base uses two layers of definition:

- Historical / product-naming background: `ROI3 = GMV / (ad cost + coupon cost)`. This wording appears in earlier business material and remains useful for explaining why coupon cost is part of the optimization objective.
- Current analysis contract: ROI3 is understood through `base / voucher / uplift / cost`. A voucher is valuable only when the incremental value generated by issuing the voucher can cover the voucher cost under the current protection rule.

The current protection rule should be read as an operational guardrail, not as the only product definition:

```text
Guardrail = gmv_uplift / 4 + advv_uplift - cost_uplift > 0
```

This reconciles the older "ratio-style" ROI3 wording with the newer Uplift-based analysis contract. The source consistency audit marks the newer contract as an owner-confirmed local analysis contract, while keeping the ratio-style wording as background rather than deleting it.

**Core semantic locks.**

1. `uplift_*` means `voucher - base`.
2. `pcoc` means `predicted / actual`.
3. `pcr`, `pctr`, `pgmv`, `pc2`, `advv`, and coupon cost are different metric families and must not be merged into one "value" field.
4. `voucher_price` is the issued voucher face value, not the final redeemed coupon cost.
5. `reward_discount -> Metric_VOUCHER_PRICE` is closer to the order/redeem-side coupon cost chain.
6. Experiment-platform `ads_voucher_cost` is the current truth numerator for ROI3 budget-usage analysis.
7. `DailyVoucherPrice` and related HyperX trace fields explain what the controller observed; they are not the final truth cost.
8. AB platform group buckets, online experiment bucket, and runtime `roi3_traffic_bucket` are separate concepts.
9. Model calibration and pacing control are separate: calibration patches prediction values; control adjusts execution strength and budget rhythm.

#### 2.5.1.1 Ads Smart Voucher-ROI3(QCPX)/Ads Smart Voucher-ROI3 (QCPX)

ROI3 normally refers to platform-funded voucher issuance. The platform bears voucher cost and decides whether issuing a voucher makes platform value better than not issuing one.

**Business purpose:**

- Increase platform rev (ad spend driven by vouchers > voucher cost)
- Drive overall platform GMV growth (improved ad traffic efficiency → higher ad GMV → overall GMV growth)
- Improve merchant marketing efficiency and effectiveness (vouchers increase user willingness to place orders and order volume)

Under the current Uplift view, the core question is not "what is the final value after issuing a voucher", but "how much additional value does the voucher create versus the no-voucher base, and what does that additional value cost".

#### 2.5.1.2 Ads Smart Voucher-ROI4(cofund)/Ads Smart Voucher-ROI4 (cofund)

ROI4 / cofund normally refers to platform + advertiser co-funded vouchers. Compared with ROI3, it brings platform spend and ROI constraints more explicitly into the value function and control chain.

Important code and trace concepts for the ROI3 / ROI4 boundary include `enableCofund`, `targetPlatformSpendImps`, `getPlatformGmvRoi()`, and `voucher_pacing_control`.

### 2.5.2 发券工程链路和策略模块/Voucher Issuance Engineering Pipeline and Strategy Modules

#### 2.5.2.1 端到端发券链路/End-to-End Voucher Issuance Pipeline

The voucher issuance pipeline spans ads offline processing, API0-3, org rank/mixrank, online bidding, posterior aggregation, and controller feedback:

| Stage | Module | Stable responsibility |
|---|---|---|
| Offline | ads offline / index | Create available vouchers for each item and write voucher ID / face value into the ads forward index. |
| API0 / API1 | ads → org | Return available voucher candidates for each ad item. |
| Rank | org rank | Estimate `ctrUpliftRatio` and `cvrUpliftRatio` for each item × voucher candidate, then send uplift values back to ads through API2. |
| API2 | ads voucher decision | Combine bidding model values and uplift values to decide voucher ID, face value, discount ratio, uplift and eCPM. |
| MixRank | org mixrank | Mix-rank ad items with voucher information such as face value, discount ratio, uplift ratios and eCPM. |
| API3 | ads billing | Apply incremental billing through `additionDeduction`. |
| Posterior | order / click / imp aggregation | Aggregate actual exposure, click, order and redeem signals. |
| Control | `voucher_pacing_control` | Smooth spend, compare budget rhythm, and output execution coefficients such as `PidCoef`. |

#### 2.5.2.2 在线主链路/Online Main Path

The online path can be read as:

```text
request
  -> model layer reads raw heads
  -> calibration layer applies cali / ratio / cap / monotonicity
  -> common fields are written
  -> strategy layer prepares voucher candidates and calculates value / cost
  -> selector chooses the final voucher and writes strategy traces
  -> posterior aggregates real imp / click / order / redeem signals
  -> control layer smooths spend and emits PID / budget coefficients
```

`rerank_uni_pgmv.go` is the model / calibration-side bridge. It reads raw heads such as `direct_pgmv_7d`, `shop_pgmv_7d`, `pcr_0`, `uplift_ratio_*`, `uplift_pctr0`, and `uplift_pctr_ratio*`, applies fallback / calibration / ratio / cap / monotonicity logic, and writes public fields including `ModelPgmv`, `ModelPgpm`, `VoucherPcr0`, `VoucherCrUpRatio1..6`, `VoucherPctr0`, and `VoucherPctrRatio1..6`.

The current Uplift model facts that should stay locked in the total KB are:

1. The main abstraction is `uplift_pcr0 + six uplift_ratio heads`.
2. The method family is DragonNet + IPW + TMLE, not a normal single-tower CVR model.
3. The model keeps `direct_label_1d` compatibility, while practical Uplift training relies on multitask `[18:19]` with `direct_order_1h`.
4. Treatment / Control are rooted in `voucher_price > 0` and `voucher_price == 0`.
5. RCT analysis still relies heavily on reason `17 / 18 / 99`; reason `19` must be checked per script before being included.
6. The six main discount bins are `2% / 5% / 8% / 12% / 15% / 20%`.
7. CTR uplift can be loaded and processed, but when `Roi3EnableCtrUpliftRatio=false`, the main online voucher path is still CVR-uplift-first.

#### 2.5.2.3 策略模块和后处理/Strategy Modules and Post-Processing

`rerank_voucher_rule.go` and the voucher package can be read through the following stable function-level sequence:

1. `abTestConfigPrepare()`.
2. Candidate preparation through `dynamicVoucherPrepare`, `voucherListPrepare`, and `voucherListPrepareNew`.
3. Candidate filters such as max CPA cap, `DynamicVoucherCap`, `voucherPrice >= VoucherThresholdPrice`, and `MaxDiscountThresholdNoVoucher`.
4. `modelPrepare()` converts public model fields into strategy-consumable structures.
5. Request / item gating: `isUserValid`, `isItemRoi3Valid`, `isRoi3VoucherLimit`, and `isBudgetAvailable`.
6. Candidate scoring through `calcUpliftCTR()`, `calcUpliftCR()`, and `calcUpliftProfitAndROI()`.
7. `voucherSelector()` chooses the final voucher, with additional constraints for cofund send flag, only seller adjust, seller voucher threshold, and `voucherDiscountDisableList`.
8. Result and trace writing: `BestVoucherID`, `BestVoucherPrice`, `DynamicVoucherPrice`, `DynamicVoucherDiscount`, `VoucherPgpm`, `VoucherPcr`, `VoucherDeduction`, `VirtualVoucherPrice`, `VoucherUnpickedReason`, `VoucherUnpickedReasonBase`, `BidRerankTrace.PgmvV`, `BidRerankTrace.Pctr_0`, `BidRerankTrace.PctrV`, `BidRerankTrace.Pcr_0`, and `BidRerankTrace.PcrV`.

`RerankVoucherRulesNew` runs after `rerank_bidding` and before `rerank_subsidy` / `rerank_deduction`. The key post-processing rules are `RerankVoucherRuleNewV2`, `VoucherBidBoostRule`, `VoucherDeboostRule`, and `VoucherAdsAddDedRule`. In other words, the voucher main strategy first produces `VoucherPgpm`, `VoucherPcr`, and `VoucherDeduction`, then later rules translate them into boost, deboost, and deduction execution channels.

#### 2.5.2.4 控制层/Control Layer

`voucher_pacing_control` is the pacing controller, not the model predictor. Its stable flow is:

1. Pull order / click / impression posterior metrics.
2. Use `CaliCoef` to correct click-side spend into order-side spend.
3. Smooth order / click / impression signals.
4. Compare budget, CDF and smoothed spend to calculate PID error.
5. Output `PidCoef`, `Roi3BudgetCoefArray`, and `CofundBudgetCoefArray`.

The important boundary is that the controller adjusts rhythm and execution strength; it does not generate `pcr`, `pctr`, or `pgmv`.

### 2.5.3 发券模型预估/Voucher Issuance Model Estimation

#### 2.5.3.1 模型目标和因果定义/Model Objective and Causal Definition

The Uplift CR model serves ROI3 voucher selection, bidding, billing and evaluation. It estimates incremental conversion impact rather than just final conversion probability.

The base model is a causal-inference style incremental conversion model built around `DragonNet + IPW + TMLE`:

- `control tower` estimates no-voucher baseline conversion, usually surfaced as `pCVR_0` / `pcr_0`.
- `treatment tower` estimates uplift ratios for voucher discount bins.
- `propensity head` estimates `pi(t|x)` to correct treatment-selection bias through IPW.
- TMLE-style correction is used to further reduce bias in observational treatment data.

The practical online outputs are:

```text
uplift_pcr0
uplift_ratio1 ~ uplift_ratio6

pCVR_i = uplift_pcr0 * uplift_ratio_i
uplift_i = pCVR_i - uplift_pcr0
```

These outputs then flow into Profit, ROI, eCPMV, voucher selection, bid boost, deboost, and deduction calculations.

#### 2.5.3.2 样本链路和 Label/Sample Pipeline and Labels

The Uplift CR sample pipeline reuses the UniCR CR infrastructure: Rank FeatureDump + UB behavior stream join, RawSample landing, FP scenario processing, CR TrainData path, and LabelJoin. The real difference is the Uplift convertor and evaluation sample selection.

`convertor_uplift_cr_1h_auuc.py` is the key Uplift convertor. Its stable responsibilities are:

- identify whether a voucher was issued and generate `is_treatment`;
- identify whether a sample belongs to RCT and generate `is_rct`;
- fill uplift portrait default values;
- generate 1-hour training labels;
- rebuild multitask fields for Uplift training and AUUC evaluation.

The sample semantics are:

| Concept | Stable meaning |
|---|---|
| Treatment | Voucher was issued, rooted in `voucher_price > 0`. |
| Control | Voucher was not issued, rooted in `voucher_price == 0`. |
| RCT | Randomized samples that can be treated as less biased. |
| Non-RCT | Strategy-selected issue / no-issue samples with selection bias. |
| Main training label | `direct_order_1h`, because Ads vouchers are 1-hour vouchers and the treatment effect is most direct in the 1-hour window. |
| Discount bins | Six bins corresponding to `2% / 5% / 8% / 12% / 15% / 20%`. |

The model still has compatibility outputs such as `direct_label_1d`, but the current Uplift training interpretation should be anchored to the 1-hour direct-order label and the multitask `[18:19]` fields.

#### 2.5.3.3 模型特征/Model Features

The Uplift feature system has three layers:

| Feature layer | Status | Notes |
|---|---|---|
| Sparse features | In base | About 29 Uplift-specific sparse slots from the EGO main sample, covering user behavior, item attributes, category preference, shop signals, user profile and entrance context. |
| Dense / treatment features | In base | Includes baseline pCR, `item_price`, `platform_discount`, `shop_discount`, platform / shop voucher IDs, and training-time `voucher_price`. |
| User portrait features | Engineered, not yet in base | 38 defined / 36 used voucher-behavior portrait features from AFP hot-join side tables. |

Feature examples and constraints:

- Base sparse features cover long-term / short-term user price behavior, user-item interaction hits, category and shop preferences, item category / CR / freshness / price-fluctuation attributes, shop conversion signals, and a small number of user-profile / context features.
- Dense / treatment features explicitly let the model see the voucher and discount context. `voucher_price` slot `65160` is a training-time treatment grouping feature and is not available at inference before the voucher decision.
- User portrait features are split into `1.x` redemption behavior features and `2.x` voucher-sensitivity features. They introduce explicit "how this user historically responds to vouchers" signals instead of relying only on generic behavior.
- Portrait feature handling uses clipping / normalization for ratios, `log1p` for long-tail counts, log normalization for amount features, signed clipping for positive / negative sensitivity features, and embedding for low-cardinality discrete features.
- Known data-quality protections cover abnormal discount ratio, abnormal amount share, small-sample-amplified sensitivity, and cross-region amount-scale differences.

Known feature gaps:

- Base user portrait is still weak.
- Strong voucher-behavior semantic features have been engineered but not fully integrated into the base model.
- Some feature coverage is naturally low, so "no history = default value" is an expected modeling condition.

#### 2.5.3.4 模型结构、训练和 Serving/Model Architecture, Training, and Serving

The base Uplift model can be read as:

```text
feature input
  -> shared backbone
  -> propensity head
  -> control tower
  -> treatment tower x 3
  -> pcr0 and six uplift-ratio outputs
```

The current model-side limitations from the source KB are:

- The uplift-discount relationship in treatment towers is still close to a linear form.
- High-discount ranges are not well covered.
- Item price × discount interaction is still under-modeled.
- Monotonicity across discount bins is only partially constrained.
- Exact use of behavior-sequence modules such as `layers/BST.py` in the main DragonNet path remains **【待确认】**.

Important model / training entrypoints:

- `paidads-alg/ego_models/model_modules/cr_uplift/cr_uplift_dragonnet_ipw_1h.py`
- `paidads-alg/ego_models/model_modules/cr_uplift/layers/uplift_net_dragonnet.py`
- `paidads-alg/ego_models/model_modules/cr_uplift/`
- `convertor_uplift_cr_1h_auuc.py`

#### 2.5.3.5 评估体系/Evaluation System

Uplift evaluation cannot rely on model AUC alone because the model is ultimately used for incremental value. Offline evaluation focuses on:

- `pcr0` AUC / pCoC;
- AUUC for each uplift bin;
- pCoC for each uplift bin.

These answer whether baseline CR is accurate, whether uplift ranking is useful, and whether uplift values are calibrated. Online evaluation returns to Guardrail, GMV, ADVV, coupon cost, PC2, and revenue contribution.

The main evaluation risk is that training and business evaluation do not share exactly the same objective and window. This can systematically overestimate online Profit if the analysis mixes 1-hour direct-order training labels, 7-day business metrics, click-space model values, and experiment-page metrics without explicit context labels.

### 2.5.4 发券出价策略/Voucher Issuance Bidding Strategy

#### 2.5.4.1 Profit、ROI 和选券/Profit, ROI, and Voucher Selection

Voucher selection compares voucher benefit and voucher cost. The legacy formula in this chapter is still useful as a strategy-side abstraction, but it must be read together with the Uplift semantics above.

```
voucher_benefit = Rev_Coef × ctcvr_0 × ctcvr_uplift × cpa_bid / Rev_Troi
                + GMV_Coef × ctcvr_0 × ctcvr_uplift × (item_price / GMV_Troi - voucher_price)
                + PC2

voucher_cost    = Cost_Coef × ctcvr_0 × (1 + ctcvr_uplift) × q

voucher_profit  = voucher_benefit - voucher_cost
                = ctcvr_0 × { ctcvr_uplift × cpabid × Rev_Coef / Rev_Troi
                            + ctcvr_uplift × item_price × GMV_Coef / GMV_Troi
                            - (1 + ctcvr_uplift) × q × Cost_Coef }
```

Stable interpretation:

- `voucher_benefit` aggregates expected revenue / GMV / PC2-style value.
- `voucher_cost` estimates expected coupon cost.
- `voucher_profit = voucher_benefit - voucher_cost`.
- The selected voucher should maximize expected platform value under gating, budget, blacklist, cofund, seller-threshold and discount-disable constraints.
- For business-facing analysis, avoid treating one temporary Profit formula as the only ROI3 definition; the current total narrative is `base / voucher / uplift / cost`.

#### 2.5.4.2 排序、出价和计费/Ranking, Bidding, and Billing

The voucher decision influences ranking and billing through two incremental terms respectively:

```
addition_boost      = voucher_profit
                    = ctcvr_0 × { ctcvr_uplift × cpabid × Rev_Coef / Rev_Troi
                                + ctcvr_uplift × item_price × GMV_Coef / GMV_Troi
                                - (1 + ctcvr_uplift) × q × Cost_Coef }

addition_deduction  = uplift_advv
                    = ctcvr_0 × ctcvr_uplift × cpabid
```

- `addition_boost`: Applied to the mixed ranking score, improving the competitive advantage of items with issued vouchers in ranking
- `addition_deduction`: Applied to billing, charging the advertiser an additional amount for the incremental advv generated by voucher issuance

The `voucher_bid_boost_rule.go` expression can also be read as a click-space value/cost comparison:

- non-cofund: `adjustBid = VoucherPgpm / pctr * tCir * coef - VoucherPcr * VoucherPrice * order2Pay`
- cofund: `adjustBid = VoucherPgpm / pctr * tCir * coef - VoucherPcr * VoucherPrice * order2Pay + targetPlatformSpendImps / pctr`

`VoucherPgpm / pctr` is closer to click-space voucher value; `VoucherPcr * VoucherPrice * order2Pay` is closer to expected voucher cost per click. Therefore `VoucherPgpm` should not be directly interpreted as strict impression-space voucher GMV.

#### 2.5.4.3 成本、收入和 PC2 口径/Cost, Revenue, and PC2 Semantics

| Concept | Recommended interpretation | Common mistake |
|---|---|---|
| `voucher_price` / `BestVoucherPrice` | Face value of the selected voucher | Treating it as redeemed coupon cost |
| `reward_discount` | Redeemed coupon discount on the order side | Mixing it with issued face value |
| `Metric_VOUCHER_PRICE` | Posterior order/redeem-side coupon cost aggregate | Treating click / imp proxy spend as final truth |
| `Metric_VOUCHER_SPEND_CLICK / IMP` | Click / impression-side coupon-spend proxy | Replacing redeem-side truth |
| `CostUA / CostReal` | Advertiser actual spend / revenue | Treating all advertiser spend as voucher-only cost |
| `ads_voucher_cost` | Current experiment-platform truth coupon cost for budget usage | Treating it as globally canonical outside the experiment context |
| `local_new_pc2` | Current experiment-field terminology for a PC2-related value | Promoting it into the canonical PC2 definition |

`PC2` should stay at the profitability / profit-contribution signal level in this total KB. Exact dashboard / SQL variants need to be interpreted by context, such as local, proxy, adjusted proxy, or true PC2.

#### 2.5.4.4 AB 桶、反事实和预算使用率/AB Buckets, Counterfactuals, and Budget Usage

ROI3 analysis must distinguish three bucket systems:

- AB platform group buckets such as `656430` and `656436`;
- online experiment bucket such as `Roi3ExpBucket`;
- runtime trace bucket `roi3_traffic_bucket = voucherStrategyBucketId * 100 + voucherModelBucketId`.

Current `roi3_exp_v1` bucket semantics are:

| Bucket | Meaning | Analysis constraint |
|---|---|---|
| `656430 / 656431` | Random no-voucher base buckets | Main true-uplift counterfactual |
| `656432` | Random voucher treatment | Experiment reference bucket; do not mix with algorithm-selected voucher buckets; not included in pacing usage by default |
| `656433 ~ 656440` | Algorithm-selected voucher buckets | Main pacing execution buckets; `NoModelScoreNoVoucher = true` requires separate interpretation |

Because true no-voucher base cannot be observed for every treated sample, actual uplift is group-level:

```
actual_uplift_metric = actual_metric(treatment) - actual_metric(random_no_voucher_bucket)
```

Budget-usage analysis should separate:

- `truth_coupon_cost`: experiment-platform `ads_voucher_cost`, the current truth numerator;
- `controller_spend`: HyperX trace `DailyVoucherPrice`, used to explain controller observation;
- `pacing_target`: `coalesce(AdjustBudget, DailyBudget)`, with hourly CDF adjustment when needed.

Default formulas:

```text
truth_budget_usage =
  SUM(ads_voucher_cost on pacing buckets) / SUM(pacing_target on pacing buckets)

controller_budget_usage =
  SUM(controller_spend on pacing buckets) / SUM(pacing_target on pacing buckets)
```

For current `roi3_exp_v1`, pacing buckets are `656433 ~ 656440` and runtime `voucherStrategyBucketId = 2 ~ 9`. Base buckets and random voucher treatment should be shown separately unless the question is explicitly about total experiment contribution, such as Q5 / Q8, where `656432` is part of the experiment cost of collecting Uplift RCT data.

### 2.5.5 Budget Allocation & Incentive-Compatible Pacing

#### 2.5.5.1 Dual-Pool Budget Allocation

The platform daily voucher budget `B_total` is split into an **ads pool** `B_ads` and a **non-ads pool** `B_non_ads`:

- The allocation maximizes `total_rev_uplift(B_ads, B_non_ads)` subject to `pc2_cpigmv_overall ≤ guardrail` and `B_ads + B_non_ads = B_total`.
- A minimum floor `α_min` guarantees a minimum share for the ads pool.

The design rationale is that ads items generally have higher per-unit voucher return (voucher drives ad conversion → ad spend → platform revenue), so concentrating budget towards ads items is incentive-compatible.

#### 2.5.5.2 Shop-Level Allocation Within Ads Pool

Within `B_ads`, sub-budgets are allocated per shop based on ad revenue contribution:

```text
B_shop_i = B_ads × w_i / Σw_j
w_i = f(shop_ads_rev_contribution)    // f is a monotonically increasing concave function
```

- A concave function (e.g., `sqrt(rev)`) ensures diminishing marginal allocation, preventing top shops from monopolizing voucher budget.
- Shops contributing more ad revenue receive proportionally larger voucher budgets, creating an incentive-compatible mechanism.

#### 2.5.5.3 Per-Shop Pacing Coefficient

The existing `voucher_pacing_control` (§2.5.2.4) operates at a global level. Budget allocation extends this with per-shop pacing coefficients:

- Each shop in the ads pool maintains its own `pacing_coef`, updated per time window (e.g., hourly).
- The non-ads pool maintains a single global `pacing_coef`.
- The pacing coefficient modifies the `addition_boost` formula by multiplying `voucher_cost`:

```text
addition_boost = rev_uplift
               + platform_gmv_uplift × pc2_cpigmv
               + pc2_uplift
               - pacing_coef × voucher_cost
```

- `pacing_coef > 1` tightens issuance; `pacing_coef < 1` relaxes issuance.
- The ads pool uses a lower `coef_min` than the non-ads pool (e.g., 0.5 vs 0.8), giving ads items a natural advantage in voucher issuance.

#### 2.5.5.4 Incentive-Compatible Flywheel

The dual-pool allocation combined with per-shop pacing creates a positive feedback loop:

1. **More ad spend** → higher shop ad revenue contribution → larger voucher sub-budget
2. **Larger budget** → lower pacing coefficient → more vouchers issued
3. **More vouchers** → stronger product competitiveness → higher conversion and GMV
4. **Higher GMV** → incentive to increase ad spend → back to step 1

Guardrail enforcement uses a layered approach: a hard global `pc2_cpigmv ≤ threshold` constraint with soft per-pool limits that trigger pacing acceleration when exceeded.

##### 2.5.5.5.3 口径与设计结论/Metric and Design Conclusions

| Conclusion | Data basis | Design implication |
|---|---|---|
| Voucher-strength coefficients have reliable cost monotonicity. | KP4 `ROI3Coef` curves were monotonic on voucher cost across ID / TH / VN; KP6 pacingByHour showed night spend share moved `13.3% → 15.9% → 17.5% → 20.1%` as configured intensity increased. | Coefficients can be used as budget-control knobs.
