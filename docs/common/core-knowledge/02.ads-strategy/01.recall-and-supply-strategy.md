## 2.1 召回通路和供给策略/Recall Channels and Supply Strategy

### 2.1.1 召回定位/Recall Positioning

The recall stage operates over the full candidate ad inventory and is the source of the ad supply side. Its core characteristics are:

**1. Lightweight Models**: The recall stage faces a full ad inventory at the million scale, where the number of candidates O(module candidate count) is large. Therefore, the per-candidate computation complexity O(per-candidate computation time) must be kept at a low level. Candidate volume at each stage:


| Stage   | Candidate Scale                    | Description                                        |
| ------- | ---------------------------------- | -------------------------------------------------- |
| Recall  | Full ad inventory (millions)        | TopK recall yields roughly a few thousand items     |
| Prerank | Recall result set (thousands)       | Coarse filtering TopK yields roughly a few hundred  |
| Rank    | Prerank result set (hundreds)       | TopK is roughly half of prerank output or fewer     |
| MixRank | Rank result set                     | Final mixed ranking returned to users               |


Time complexity and accuracy ordering across stages: time complexity DNN > dual-tower vector > LR > rule-based; accuracy ordering is the same. Since recall faces millions of candidates, lightweight algorithms (dual-tower models, statistical collaborative filtering, etc.) are used.

**2. Multi-channel Parallel Recall**: To satisfy diverse business scenarios and user needs, the recall stage maintains multiple recall channels running in parallel, providing candidate sets from different angles:

- **Scenario Diversity**: The Search scenario models around Query (QueryUnderstanding); the Discovery scenario models around User (UserUnderstanding)
- **Objective Diversity**: Different channels focus on different objectives such as user engagement (click behavior), conversion rate (purchase/add-to-cart behavior), and monetization
- **User Interest Diversity**: Simultaneously covers long-term interests (Offline U2I) and short-term interests (Online U2I), balancing retargeting (capturing recent interests) and generalization (cross-domain interest expansion)

**Position in the Overall Pipeline.**

```text
Full ad inventory (millions)
  ↓  [Recall] Multi-channel parallel recall → Filter → Zigzag Merge → Thousands of candidates   ← This chapter's focus
  ↓  Prerank coarse ranking model scoring → Hundreds
  ↓  Rank fine ranking model scoring → Dozens
  ↓  MixRank mixed ranking → Final display
```

Full request pipeline: `request → query/user/context understanding → recall → filter → merge → prerank/rank → mixrank`.

**Responsibility Boundaries.**

- **What recall is responsible for**: Generating ad candidates for Search, DD, YMAL, RCMD, Live, Video, Shop, Brand, and other scenarios. By retrieval method, there are 6 major op categories (KNN / KV / Text / FSE Realtime / U2U2I / Fallback); by business channel, these manifest as U2I, I2I, Q2Tag2I, U2C2I/SID, Keywordless, Popularity, Rewrite, AdTag, Content Ads unified recall, and other queues.
- **What recall is NOT responsible for**: Final ranking, final bidding/pricing, charge settlement, delivery fulfillment, and the production and writing of candidate indexes themselves.
- **Upstream/downstream boundaries**:
  - **Upstream (features / indexing)**: `Ads Info` and `Indexer` are responsible for candidate searchability, field availability, and timeliness. `FSE` provides real-time user behavior, long-sequence features, and online features for `SimpleStandardURankerOp`. `AFP` provides offline feature lineage and serving-side feature processing. `EGO` handles dual-tower model training and serving, producing User Tower / Item Tower Embeddings.
  - **Downstream (ranking / bidding)**: `Prerank` coarse ranking determines candidates entering fine ranking; `Rank` fine ranking determines final priority; `Bidding` determines price and objective constraints; `MixRank` handles mixed ranking of ads and organic results.
  - **Merge and filter**: Recall internally includes `MergeRecallResultOp`, `AdsInfoFilter` (Search / Discovery), `RcmdAdsDedupOp` (Discovery only), `SnakeMergeFilterOp`, `BizTagCalculateOp`, `PackRecallAdsResultOp`, `SendRecallLogOp`, and other ops.

Therefore, "model recall returned it" does NOT mean "it will definitely enter prerank": candidates still go through merge, AdsInfoFilter, Discovery dedup, SnakeMerge truncation, biz tag calculation, packaging, and log forwarding. When debugging, first confirm at which stage the candidate stopped, then determine whether it's a model retrieval, filter, dedup, quota truncation, or downstream pipeline issue.

**Business Background and Pain Points.**

- **Recall Coverage**: Ads recall share in Ads impressions is below expectations (95% as team-level target); some scenarios have 0 candidates, low exclusivity, and poor long-tail coverage.
- **Ad Inventory Scale**: Ad inventory continues to expand (TW from 5.8M → 9.5M), but only a few dozen ads can be shown per request; the first-level filtering must complete in milliseconds.
- **Architectural Legacy**: Too many recall channels, fragmented indexes, heavy placement routing burden, leading to high maintenance costs, long parameter tuning chains, and inconsistent online diagnostics.
- **Model-Driven Direction**: 2025 Q1 successfully deployed offline U2I long-sequence multi-interest modeling in RCMD with online gains; current goal is to evolve toward a unified online long-sequence model, improving real-time performance and reducing offline maintenance costs.
- **Business Objectives**: Improve recall coverage, candidate quality, and revenue performance; unify indexes and business routing; accumulate recall knowledge base, analysis methods, and diagnostic skills.

**Quarterly Roadmap.**

- **2025Q1**: Unified Search / Discovery recall architecture, drove queue convergence, Search relevance, and full-pipeline consistency modeling.
- **2025Q3**: Advanced API0 / full bidding type unified recall, Query/User2Tag servicification, QIR migration, and relevance optimization; U2U2I full-rollout delivered significant revenue gains.
- **2025Q4**: Built Tag evaluation system, Recall Efficiency, U2C2I/SID, RCMD long-sequence onlineization.
- **2026Q1**: Continued Content Ads recall refactoring, Search LLM/Q2Tag2I, Search & RCMD model-driven recall, 2k long-sequence, model i2i, quota / downgrade / experiment monitoring capabilities.

**Architecture Modules.** The recall architecture is logically divided into the following core modules:


| Module                    | Function                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Request Understanding** | Unified understanding of input information (QueryUnderstanding for Search scenarios, UserUnderstanding for Discovery scenarios); results reused across the full pipeline |
| **Recall Queues**         | Multiple recall queues run in parallel to provide diverse candidate sets                                                                                |
| **Ads Info**              | Ad validity filtering (insufficient budget / suspended / insufficient inventory / blacklist); Discovery scenarios additionally perform seen-item filtering (items already shown are not shown again) |

### 2.1.3 商品卡流量广告召回/Product Card Traffic Ad Recall

#### 2.1.3.1 RCMD Item Ads 召回算法/RCMD Item Ads Recall Algorithm

##### 2.1.3.1.1 场景特性/Scenario Characteristics

The Discovery Ads scenario (DD, YMAL, GAME, Cart_Unify) has the following main characteristics:

- **Unified Multi-scenario Modeling**: There are many scenarios, and iterating on a single scenario contributes relatively little to overall revenue. Unified modeling is needed to improve iteration efficiency, with a focus on overall scenario-level returns
- **User-Centric**: Lacks explicit strong-interest user signals; only some scenarios have weak-interest Context (YMAL's PDP anchor item, Cart_Unify's cart items, etc.)
- **Dual Requirements for Generalization and Retargeting**: Must both satisfy user interest optimization (retargeting) and enable users to "browse" (generalization)
- **Alignment with Downstream Ranking Objectives**: Recall must comprehensively consider user interests and advertiser demands while staying consistent with downstream ranking objectives

##### 2.1.3.1.2 设计思路/Design Philosophy

Discovery Ads Recall algorithm modeling must have the following capabilities:

- Unified multi-scenario modeling capability that accommodates differences across scenarios
- Compatible with both retargeting and generalization requirements
- Capable of learning downstream objectives to align with downstream ranking
- Each module maintains independence while providing reusable results for other modules

The algorithmic framework is logically divided into three parts: UserUnderstanding, Recall Queues, and other modules (e.g., Tag Service, Zigzag merge, etc.).

##### 2.1.3.1.3 用户理解/UserUnderstanding

The UserUnderstanding module is responsible for producing User 2 Tag information (Tag broadly refers to the understanding of user interest intent) by combining User and Context Info, including:


| Component      | Status      | Description                                                            |
| -------------- | ----------- | ---------------------------------------------------------------------- |
| User Embedding | Available   | Model-produced UserEmbedding representation, reused by downstream stages |
| Similar Users  | In progress | Modeling similar user populations U2U                                  |
| Interest Cates | Planned     | Coarse-grained user interest categories, used for generalized recall or downstream features |
| High-frequency Items | Planned | User's frequently interacted historical items, used as Recall Triggers or user profile features |


Context Info for each scenario:


| Scenario   | Context Info                              |
| ---------- | ----------------------------------------- |
| DD         | None                                      |
| YMAL       | PDP anchor item                           |
| Cart_Unify | List of items added to cart / purchased   |
| Game       | None                                      |


##### 2.1.3.1.4 召回队列/Recall Queues

Discovery Ads Recall mainly includes 4 types of recall queues:

###### 2.1.3.1.4.1 U2I2I（协同过滤-实时兴趣）/U2I2I (Collaborative Filtering — Real-time Interests)

Based on the simple assumption that "items similar to items the user is interested in are also interesting to the user," implemented in two steps:

**Step 1 — Trigger Selection** (U2I part): Select Trigger items from the user's historical behavior sequence


| Scenario   | Trigger                                      |
| ---------- | -------------------------------------------- |
| DD         | User historical behavior sequence             |
| YMAL       | User historical behavior sequence + PDP anchor item |
| Cart_Unify | User historical behavior sequence + cart item list |
| Game       | User historical behavior sequence             |


Considerations for Trigger selection:

- **Combining Long-term and Short-term Interests** (planned): Prioritize the user's most recently interacted items (with different weights for different behaviors), while also considering frequently interacted items (long-term preferences, such as repurchased items); can use User2Tag (high-frequency items) results from UserUnderstanding as Triggers
- **Diversity Control** (planned): Avoid Triggers being too concentrated in the same category; strive for Trigger diversity

**Step 2 — Similar Item Expansion** (I2I part): Two measurement approaches:

**Approach A: Statistical Collaborative Filtering (ItemCF)**

Basic idea: If two items are clicked (or acted upon) by many of the same users, these two items can be considered highly similar.

Example calculation method: Suppose the following behavior matrix exists:


| User | Grapes | Apples | Cup |
| ---- | ------ | ------ | --- |
| A    | 1      | 1      | 0   |
| B    | 0      | 1      | 0   |
| C    | 0      | 1      | 0   |


Each item is represented as a vector (Grapes=[1,0,0], Apples=[1,1,1]), and cosine similarity is computed: `cos(Grapes, Apples) = 1 / (√1 × √3) ≈ 0.577`. Using this method, an N×N similarity matrix for all items is computed and written to cache for online retrieval.

Other variants: The industry has further improved upon ItemCF in terms of Trigger selection and similarity measurement methods. One particularly classic variant is the [Swing algorithm](https://www.cjh.zone/blog/recall-swing/).

Pros and cons: Computationally simple with few dependencies, but generalization is poor due to heavy reliance on User-Item historical behavior; unfriendly to new items and cold-start scenarios.

**Approach B: Deep Model Embedding**

Uses model-produced Item Embeddings directly to compute cosine similarity. Requires the model's Embedding output as a prerequisite, making the preprocessing slightly more complex, but generalization is good and friendly to new items, cold-start, and interest expansion.

###### 2.1.3.1.4.2 OnlineU2I（实时兴趣模型）/OnlineU2I (Real-time Interest Model)

Introduces a deep **dual-tower model (Dual-Tower)** to address cold-start, sparse data, and multimodal fusion issues in collaborative filtering:

**Model Characteristics:**

- **Scenario Reuse**: Integrates all region data from YMAL and DD through a unified interest model (One Model Serve All) to improve efficiency and generalization
- **Objective Reuse**: LTR simultaneously aligns with downstream objectives (order/click/impression) and user interests; full-space ordering: order > click > impression > un-impression > random
- **Output Reuse**: Simultaneously outputs User Embedding and Item Embedding for reuse by the UserUnderstanding module and other recall channels

**Features:**

- User side: basic user attributes (age/gender/occupation), real-time user behavior sequence (click/purchase/add-to-cart), context features (geographic location/time)
- Item side: basic attributes (ID/category/price), statistical features (CTR/CVR), multimodal features (title/picture embeddings)
- Context: scene id and region id, used to distinguish different scenarios within the unified model

**Sample Strategy**: Multi-objective point-wise learning, with positive and negative samples constructed according to the following full-space ordering:


| Objective     | Positive Sample Condition | Negative Sample Condition     |
| ------------- | ------------------------- | ----------------------------- |
| Order         | Has order behavior        | No order (including other behaviors) |
| Click         | Has click behavior        | Has impression but no click   |
| Impression    | Has impression            | Has un-impression             |
| Un-impression | Has candidate but no impression | Random sample            |


**Loss Function**: The objectives to align include order, click, impression, un-impression, and random. Batch in-batch negative sampling is used to implement the random objective, and for all other objectives, random is the negative sample. For each objective, a point-wise approach is used based on sample labels, and multi-objective fusion forms the final objective. A temperature coefficient τ is introduced in the loss to control the smoothness of the probability distribution; for each objective, the positive sample count N is used to amplify the predicted probability (`min(p × N, 1)`), so that samples already predicted with high probability no longer generate gradient backpropagation, avoiding over-optimization.

**Model Architecture**: The User tower and Item tower have essentially the same structure. The model routes different sub-networks via scene id and region id to learn shared parameters and scenario-specific parameters. Through this model, both Item Embeddings and User Embeddings can be obtained simultaneously. This model serves as the foundation for continuous iteration on contrastive learning, multi-objective learning, multimodal learning, and other technical directions to improve modeling expressiveness.

###### 2.1.3.1.4.3 Offline U2I（兴趣分层召回）/Offline U2I (Layered Interest Recall)

Compensates for the limitations of Online U2I in terms of data scope and computational complexity:


| Dimension       | Online U2I                                              | Offline U2I                                          |
| --------------- | ------------------------------------------------------- | ---------------------------------------------------- |
| Data Scope      | Short-term session data (last 10–50 interactions)       | Historical behavior spanning months to years         |
| Compute Complexity | Limited by low-latency requirements; lightweight model | Can use more complex models and refined feature engineering |
| Update Frequency | Real-time (millisecond-level)                          | Periodic (daily) updates                             |


Long-term interests are split by category into **11 interest points**, constructing a multi-head Tower (11 UserEmbeddings). Each interest point independently computes TopK, and results are consolidated via zigzag merge to produce the final Top500.

###### 2.1.3.1.4.4 人群兴趣-U2U2I/Crowd Interest — U2U2I

The various recall methods introduced above primarily rely on direct interactions between the target user and items (e.g., clicks, add-to-cart, orders), which to some extent limits the coverage and diversity of the recall set — especially in scenarios with sparse user behavior or many new users. U2U2I follows the logic of U2I2I (collaborative filtering), but upgrades the Trigger from an Item to a User, transforming it into U2U2I.

**Algorithm Approach**: Based on user profile or behavioral similarity, find a group of users similar to the target user, and then leverage these similar users' historical behavior records to recall relevant items. This approach can significantly expand the recall set, improving recommendation diversity and coverage, while also effectively mitigating cold-start issues and helping new users with limited behavioral data receive more accurate recommendations.

**Solution Design**: The U2U2I recall solution mainly consists of two parts: U2U and U2I.

**U2U (Similar User Lookup)**: Compute user embeddings (produced by the Online U2I model's user tower) to obtain a set of users similar to the target user. Since the full User set is too large (hundreds of millions), a strategy is needed to define a batch of active users as user candidates. These active users should ideally satisfy:

- Users with a certain volume of behavior (click/add-to-cart/purchase) in the last N days
- Users with a relatively large number of interactions to support subsequent U2I recall
- Users whose ad interactions span multiple categories to ensure recall diversity

**U2I (User Interest Expansion)**: Focuses on interactions between users and items (purchase records, click behavior, etc.), predicts the target's interest in items they haven't interacted with based on similar users' historical behavior, and expands these items to the target user to achieve the U2U2I objective.

**Online Architecture**: When a user requests the U2U2I service, the Online U2I model's User tower computes the current User's embedding and passes the result to Vespa. Vespa stores the user embeddings of active candidate users, and uses KNN to compute inner products between the target user and candidate users to select the TopK similar users. Finally, the filtered click or order sequences of similar users are recommended to the target user, completing a full U2U2I recall pass.

#### 2.1.3.2 Search Item Ads 召回算法/Search Item Ads Recall Algorithm

##### 2.1.3.2.1 场景特性/Scenario Characteristics

Search Ads are centered on Query, with the following main characteristics:

- Query is the user's **explicit expression of intent**; recall results must be strongly relevant to the Query
- Needs to simultaneously support **precise text-level matching** and **strong/weak semantic expansion** to enrich Query supply
- Query information runs through the entire Recall/Prerank/Rank pipeline; recall must comprehensively consider user interests and advertiser demand signals

##### 2.1.3.2.2 设计思路/Design Philosophy

- Unified understanding capability for Queries (QueryUnderstanding)
- Based on Query understanding, accomplish precise item matching at the text level and strong/weak relevant item expansion at the semantic level
- Model-based recall to learn downstream objectives and align with downstream ranking
- Each module maintains independence while providing reusable results

The algorithmic framework is logically divided into three parts: QueryUnderstanding, Recall Queues, and other modules (e.g., Relevance, Zigzag merge, etc.).

##### 2.1.3.2.3 QueryUnderstanding 模块/QueryUnderstanding Module

QueryUnderstanding is responsible for modeling the raw Query, with the following main functions:

- **QueryRewrite**: Spelling correction and Query rewriting, rewriting to highly relevant, semantically close Queries
  - Example: Incorrect input "desert dress" → rewritten to "beach dress"; "beach dress" → rewritten to "seaside dress"
- **QueryExtend (Query 2 UnifyQuery)**: Increases Query diversity while considering relevance, expanding the raw Query into a UnifyQuery
  - Example: "beach dress" → expanded to "dress", "summer dress", etc.
- **Query2Tag**: Decomposes RawQuery, QueryRewrite, and QueryExtend results into Tags for use by subsequent text-matching recall

| Source       | Input        | Example Search Query Tags         |
| ------------ | ------------ | --------------------------------- |
| RawQuery     | Beach dress  | [beach, dress, female]            |
| QueryRewrite | Seaside dress | [seaside, dress, female]         |
| QueryExtend  | Summer dress  | [summer, skirt, female]          |


**QueryRewrite Detailed Approach**

Search terms are divided into **common search terms** and **long-tail search terms**, each handled separately:

- **Common Search Terms**: Frequently occurring Queries; QueryRewrite results can be pre-computed offline and cached, reducing online compute load and allowing more complex models for more accurate results. Rewrite methods include:
  - **Swing/CF rewriting**: Averages 9.9 rewrite terms generated; 51.34% difference in newly recalled ad content
  - **Synonym replacement (gpt-4o-mini)**: Rewrites all terms with search volume > 5
  - **LLM rewriting (Qwen2-7B)**: After fine-tuning, averages 7.48 rewrite terms generated; 62.95% difference in newly recalled ad content
- **Long-tail Search Terms**: Rare Queries that cannot be predicted offline and can only use **real-time online LLM calls** to generate relevant rewrite results
- **Case Example**: Rewrite results for raw Query "Kaos oversize motif" (patterned oversized T-shirt) include "Kaos oversize" (oversized T-shirt), "Kaos oversize murah" (cheap oversized T-shirt), "Oversize wanita" (women's oversized), etc.

**QueryExtend (Query 2 UnifyQuery) Detailed Approach**

This module has no independent counterpart in Org Search — its functionality is merged with QueryRewrite there. Given the uncertainty in Org's iteration roadmap and differences in modeling objectives (Org targets highly relevant, similar Queries), Ads chose to build this module independently.

- **Common Search Terms**:
  - 1. Use QIR (Query-Item Relevance) scoring: if Query1-Item1 is relevant and Query2-Item1 is weakly relevant, then Query1-Query2 is weakly relevant
  - 2. Generate a large number of associated search terms for each common search term
  - 3. Generate a candidate set and use QIR scoring, further analyzing the average eCPM contributed by each search term to filter weakly relevant ones
  - 4. Finally push results to the online cache
- **Long-tail Search Terms**:
  - 1. Build a training dataset based on the results from common search terms
  - 2. Train a dual-tower Transformer architecture for Query-to-weakly-relevant-rewrite-term recall
  - 3. Filter the rewrite scope: apply K-means clustering on terms in the index, selecting the sample closest to each cluster centroid as the final Query

**Query Tag (Attribute Tag) Approach**

The Query Tag module is essentially an intermediate semantic representation layer. By mapping Queries and Items into the same Tag space, it resolves vocabulary gap issues in text matching:

- **Semantic Abstraction and Normalization**: On the Query side, search terms (e.g., "cheap durable Bluetooth headphones") are converted into structured labels (e.g., [value-for-money, Bluetooth headphones, durable]); on the Item side, titles are parsed to generate tags in the same dimensions, achieving text information standardization
- **Matching Efficiency Optimization**: Converts text matching into efficient computation between Tags (intersection, similarity), supporting different granularities of Tags (category "phone" vs. attribute "large battery")
- **Intent and Scenario Expansion**: Connects Queries to implied needs not explicitly expressed (e.g., "student laptop" → [lightweight, affordable, office]), matching low-frequency/complex Queries to relevant Items via generalized Tags
- **Business Logic Integration**: Supports manual rule interventions (e.g., advertiser-specified keywords/Tags), and can combine image, category, and other non-text information to generate composite Tags

Tag sources include: tokenization results of the Query itself, advertiser keywords, hot queries, and Query/Tags predicted by LLM models.

##### 2.1.3.2.4 召回队列/Recall Queues

Search Ads Recall mainly includes 3 types of recall queues:

###### 2.1.3.2.4.1 文本匹配（Query2Tag2Item）队列/Text Matching (Query2Tag2Item) Queue

Quickly filters candidate ads relevant to the user's intent from the massive ad inventory by analyzing the relevance between the user's Query and ad text features:

- **Offline Phase**: Preprocesses ad text (titles, descriptions, bidding keywords, etc.) — removing special characters, stopwords, tokenizing, normalizing — to build an inverted index from terms to ads
- **Online Phase**: Retrieves matching candidates from the inverted index based on Tags produced by QueryUnderstanding
- Matching targets: user Query against ad-bound bidding keywords, or Query against ad item text features (item name/brand/category name)

Common match types:

- **Exact Match**: Ads are returned only when the user's query exactly matches the ad's text features
- **Phrase Match**: Ads are shown when the user's query contains the complete phrase of the ad's text features
- **Broad Match**: Ads are shown when the user's query is semantically related to the ad's text features, even without an exact match

Using Exact Match as an example, the query process for user Query "phone stand": Query processing result → ["phone", "stand"] → look up corresponding ad lists → take the intersection of lists → filter by business requirements (budget/targeting conditions, etc.) → sort, truncate, and return results

###### 2.1.3.2.4.2 语义匹配（Online Query2Item）队列/Semantic Matching (Online Query2Item) Queue

Implements semantic-level matching between Query and Item using deep semantic models, covering semantically related ads unreachable by text matching. The Search Recall stage must simultaneously consider three primary objectives:

- Recall can model the full space and has reasonable generalization capability
- Consistency between recall objectives and downstream stages
- Recall results have a certain degree of relevance to the Query

**Model Approach**: Dual-tower model where the Query tower and Item tower encode independently; vector similarity is computed via ANN (Approximate Nearest Neighbor) retrieval. The same vector simultaneously serves both LTR (Learning to Rank, aligning with downstream objectives) and relevance modeling objectives.

**Features**:

- User side: basic user attributes (age/gender/occupation), user behavior sequence (click/purchase/add-to-cart, using only text information such as title), context features (geographic location/time)
- Item side: basic attributes (ID/category/price), statistical features (CTR/CVR), multimodal features (title/picture embeddings)

**Sample Strategy**: Improves pipeline consistency by learning the full-space ordering: `order > click > impression > un-impression > (relevance) > random`

**Loss Function**: A Relevance model is trained simultaneously alongside the LTR objective, used to filter data with weak relevance. For the filtered samples, each objective uses a point-wise approach based on labels. Final Loss = multi-objective fusion Loss + Relevance Loss.

###### 2.1.3.2.4.3 直投队列（Query2Item 队列）/Direct Placement Queue (Query2Item Queue)

Establishes Query-Item historical high-conversion mappings based on posterior statistics:

- Directly establishes Query-Item correspondences from historical conversion data as precise direct-placement candidates
- Can analyze the average eCPM contributed by each Search Term to filter weakly relevant search terms

### 2.1.4 非商品卡流量广告召回/Non-Product Card Traffic Ad Recall

#### 2.1.4.1 暗投 vs 明投/Explicit Placement vs. Implicit Placement

Ad serving is divided into two modes: **explicit placement (Mingtou)** and **implicit placement (Antou)**:


| Dimension   | Explicit Placement (Mingtou)                                             | Implicit Placement (Antou)                                                      |
| ----------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Definition  | Advertisers actively serve ads on specific content/traffic; the advertiser explicitly knows the placement location | Budget-surplus ad supply served by the platform in traffic scenarios not explicitly specified by the advertiser |
| Typical Case | KOL/Seller directly places ads on Video or Live content                 | Product Ads implicitly placed in Shop/Live/Video traffic entry points           |
| Billing     | CPM (Live/Video explicit placement) or Click (Search implicit placement)  | Usually reuses Product Ads ROI2 bidding and Click billing logic                 |


Comparison of placement pipelines across ad types:


| Ad Type          | Placement Pipeline                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Product Ads      | Full API0-3 pipeline (API0 Recall & Pre-ranking → API1 Org Recall → API2 Bidding & Strategy → API3 Billing)           |
| Brand & Shop Ads | Placement pipeline fully controlled by the Ads side (Recall → Relevance Filter → Ranking → Rerank → Send), no Org mixing |
| Video Ads        | API0-3 (API0 includes implicit 1.0 + explicit 1.0 + implicit 2.0 + explicit 2.0); Search scenario Video implemented via cover-swap |
| Live Ads         | Full API0-3 pipeline; unified pipeline achieved by upgrading 1.0 ads to 2.0 ads                                        |


#### 2.1.4.2 Shop 卡流量广告召回/Shop Card Traffic Ad Recall

Core objective: Recall and rank using both item and shop information to increase clicks and conversions.

**Recall Architecture**: Two indexes are built — an **index based on items under shops** and an **ad-keyword (ads-kw) dimension index** — to perform item recall and shop recall respectively, which are then merged to the Shop+Item dimension:

- **Item Path (Embedding Recall)**: Uses vector embeddings of items under shops to recall relevant items via vector retrieval
- **Keyword Path (Term Matching Recall)**: First recalls keywords purchased by the shop, then continues with term-matching recall based on those keywords

**Ranking**: The Shop Ads pCTR ranking model combines user features, Query-relevant item features, top-item features under the shop, shop-related features, and Query features to produce scoring results at the Shop and Item dimensions. The model introduces Attention modules targeting Candidate Items (Query-relevant items) and Shop Top Items (top items under the shop), and adds an Embedding module based on a pretrained large language model to compute the semantic relevance between Query and items.

#### 2.1.4.3 Video 卡流量广告召回/Video Card Traffic Ad Recall

Core objective: Recall and rank using both the linked items and video content to increase item clicks, conversions, and completion rate.

**Recall Types**: Video Ads include both explicit and implicit placement ads, with different recall strategies:

**Explicit placement recall** (KOL/Seller directly placing ads on Video) — parallel recall queues:


| Queue Name                       | Strategy                                            | Type                        |
| -------------------------------- | --------------------------------------------------- | --------------------------- |
| pop_like/view/order/gmv_videos   | Popular videos (ranked by likes/views/orders/GMV)   | Popularity-based recall     |
| User2Item2Video                  | User behavior items → related videos                | Video-item-based recall     |
| User2Item2Item2Video             | CF-similar items from user behavior items → related videos | Video-item-based recall |
| User2Following2Video             | Videos created by KOLs the user follows             | Creator-based recall        |
| Country New Ads/Video            | Cold-start for new ads/new videos                   | Cold-start                  |


**Implicit placement recall**: Based on U2I2I to recall implicit ad items, and maps items to their linked Videos (I2V) to recall Videos with mounted items. In vector recall (U2V), the explicit and implicit pipelines differ: explicit placement recalls directly based on Video Embeddings, while implicit placement uses item vectors as an intermediary.

**Preranking**: Multi-Task output (CTR + LTR features), combined with the ranking stage CR score to build LTR features, learning consistency with the ranking stage CR.

**Ranking**: Multi-objective scoring is handled by the Organic side:


| Objective              | Positive Sample                                                       | Negative Sample                  |
| ---------------------- | --------------------------------------------------------------------- | -------------------------------- |
| Outflow CTR            | Outflow clicks                                                        | Outflow impressions without click |
| Staytime               | Regression label (time from Video View start to end)                  | —                                |
| E-commerce/Ad in-flow click | video_anchor_click, enhanced_card_click, atc_click, buynow_click | Uncliked for each objective      |
| Ad outflow click       | Reuses native outflow CTR                                             | —                                |
| E-commerce/Ad conversion | Post-click conversion, ContentOA / AdsOA attribution                | Post-click non-conversion        |
| Content engagement     | like/follow/share and other per-objective clicks                      | Unclicked for each objective     |


#### 2.1.4.4 Live 卡流量广告召回/Live Card Traffic Ad Recall

Core objective: Recall and rank using both items and livestream rooms to increase item clicks, conversions, livestream room engagement, and dwell time.

**Recall Architecture**: Live Stream Ads recall includes two main directions — **Item Path** and **Streamer Path**:

- **Item Path (U2x2Item)**: The index combines currently live items in the streaming room (bag) and historically live items (hist); items are recalled based on user behavior and then mapped to streaming rooms
- **Streamer Path**: Based on categories the user has interacted with and streamers the user has watched, matches similar streamers and recalls their streaming rooms

Streamer Path parallel recall queues:


| Queue Name                          | Strategy                                            | Type                         |
| ----------------------------------- | --------------------------------------------------- | ---------------------------- |
| POPULAR_CCU / POPULAR_LIKE          | Popular live rooms by current CCU/Likes             | Popularity-based recall      |
| COLD_START / COLD_START_TARGET_ROI  | Cold-start queue                                    | Cold-start                   |
| USER_VIEW_STREAMER / USER_FOLLOWING | Recall based on streamers the user has watched/followed | Streamer-based recall    |
| USER_CATEGORY                       | Recall streamers based on user behavior categories  | Streamer-based recall        |
| USER_STREAMER                       | Recall streamers similar to those watched/followed by the user | Streamer-based recall |
| USER_I2I_BAG / USER_I2I_HIST        | Recall real-time/historical live items based on user behavior | Live-item-based recall  |
| PDP_RECALL                          | PDP-specific recall                                 | Private domain special recall |


**Preranking**: Based on an MMoE Multi-task model, outputs comprehensive pCTR, pCR, and pDeepView scores at the streaming room dimension. After preranking, each ad's bid price is requested to perform eCPM ranking, and the Top200 are sent to Org for ranking-stage mixed ranking.

**Ranking**: Multi-objective scoring is handled by the Organic side. The main scoring objectives for Live and the logic for selecting positive/negative samples are as follows. Live's CVR is directly modeled as View→Order (unlike Video ads which bill per Click — Live bills per View/impression), in-flow ad conversion uses AdsOA attribution, and out-flow ad conversion is modeled as outflow CTR × in-flow ad conversion.

**Common execution path.** The exact DAG differs by scene, but Search and Discovery Product Ads share the same high-level structure:

```text

  -> request understanding or OhMyEmb embedding
  -> queue-specific recall op
  -> MergeRecallResultOp
  -> SearchAdsInfoFilterOp or RCMDAdsInfoFilterOp
  -> RcmdAdsDedupOp for Discovery only
  -> SnakeMergeFilterOp
  -> BizTagCalculateOp
  -> PackRecallAdsResultOp
  -> SendRecallLogOp
  -> Prerank
```

So "the model recalled the item" does not mean "the item entered prerank." A candidate may be dropped by AdsInfoFilter, Discovery dedup, SnakeMerge quota truncation, or final packing/logging.

- User cold-start: When long-sequence user behavior is weak, relies on query/item-driven channels, support queues, and fallback; the KB has no dedicated user cold-start branch.
- Query cold-start: QT2I, LLM Q2I, Realtime Popular Q2I and other non-personalized queues serve as partial fallbacks; actual strategy follows the corresponding graph / AB config.

**Common pipeline (shared by all retrieval types).** All queues execute their ops in parallel independently → `MergeRecallResultOp` merge → `SearchAdsInfoFilterOp` / `RCMDAdsInfoFilterOp` filter → `RcmdAdsDedupOp` (Discovery only) dedup → `SnakeMergeFilterOp` quota truncation → `BizTagCalculateOp` → `PackRecallAdsResultOp` → `SendRecallLogOp` → Prerank.

**Cold-start strategy.** Recall does not have a single "cold-start branch"; cold-start coverage is distributed across multiple mechanisms:

*Processing flow in the model:*

```
Original Slot (sparse ID emb, dim=16×N)
  ├── Standard ID part ──→ concat ──→ [B, seq, 64]
  └── Extra Emb part ──→ ExtraFeatureAdapter(LayerNorm → Dense → Dropout) ──→ [B, seq, 48]
        ↓
     concat(ID part, Extra part) ──→ SharedItemDNN ──→ [B, seq, 64] (unified representation)
```

`ExtraFeatureAdapter` aligns external dense embeddings: LayerNorm normalization, then a Dense(ReLU) projection to target dimension with Dropout regularization. The output is concatenated with standard ID embeddings and fed into `SharedItemDNN` bottleneck (256→128→64) for unified-dimension representation. Applied to Target Item, PDP Item, and Click Sequence with the same Adapter + DNN structure. Verified for RCMD LongSeq DAG 1331/1332 only; PDP dual-tower DAG 1098/1099 does not use it.

AB parameters are registered in `paidads-recall` via `BaseRecallOp.Init`: the YAML `ab_param_key` string maps to a field's json tag in the `ABTestConfig` struct, and at runtime is retrieved from `GraphEngineCtx.GetABParam()` via reflection and deserialized into `RecallConfig`. KNN queues require checking two AB parameter layers: queue-level (`knnRecallCfg{queue_name}`) controls enable, limit, cache, TTL, read/write mode; model-level (`knnRecall*ModelCfg`) specifies Vespa / rank profile / embedding field. Final quantities are also affected by global `MergeQueueQuota` and `RecallPickedNum`.

**Configuration reverse-lookup guide (essentials).** Recommended paths for reverse-looking up complete configuration information from known clues:

| Known clue | First hop | Subsequent path |
|---|---|---|
| `queue_name` / `node name` | `graph-manager-conf/retrieval/*.yaml` locate node, determine `op` type | KNN → AB → OhMyEmb → EGO → AFP; Redis/FSE → QueueParam → paidads-alg offline output; QT2I → qt2iCfg → Vespa text matching |
| `model_name` / EGO serving name | EGO Portal query serving details → `online_model_name` / `checkpoint_id` | → `graph-manager-conf/ohmyemb/*.yaml` reverse-lookup node name by `model_name` → retrieval YAML find referencing queues |
| Scene (Search / DD / YMAL / PP / Game / Shop / Live) | Locate graph file by scene | Check `MergeRecallQueue` inputs to list all queues → inspect each upstream node op |
| `PIC` | Queue registry (`1R7lWvcDF-Mey4mJQ1bRgEQy9XWwHAEmR0dH51J-nqpk`) filter by PIC | Task-level sheet → DataSuite workflow → Data Delivery project 11 |

Key principles: (1) The first hop for any high-frequency op is always back to the graph—confirm which YAML it appears in and what nodes are connected before and after; (2) Redis / FSE / QT2I / Fallback do not need to chase EGO / AFP—focus on QueueParam / offline output / Vespa rank_profile; (3) Only KNN queue complete paths will cover AB + OhMyEmb + EGO + AFP + DataSuite; (4) When static fields and AB values conflict, AB / online values take precedence.
