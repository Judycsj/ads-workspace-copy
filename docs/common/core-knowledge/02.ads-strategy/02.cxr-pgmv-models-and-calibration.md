## 2.2 CXR & PGMV 模型和校准/CXR & PGMV Models and Calibration

### 2.2.1 CXR & PGMV 模型的定位及挑战/Positioning and Challenges of CXR & PGMV Models

[§1.3.2.2](../01.ads-overview/03.system-pipeline-modules.md#1322-价值预估) introduced the three core value estimation models in the ad system (pCTR, pCVR, pGMV). This chapter covers the modeling details of these models in depth. **CXR** is a collective term for click/conversion rate estimation models such as pCTR and pCVR (C = Click/Conversion, X = various conversion events, R = Rate), while **PGMV** is the GMV prediction model.

**Estimation Model System:**


| Model      | Full Name                         | Description                                                                                          | Modeling Type |
| ---------- | --------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------- |
| pCTR       | Predicted Click-Through Rate      | Predicts the probability that a user will click on an ad                                             | Classification |
| pCVR / pCR | Predicted Conversion Rate         | Predicts the probability of a conversion (order) after a click. The industry standard term is pCVR; the system internally abbreviates it as pCR — the two are equivalent | Classification |
| pGMV       | Predicted Gross Merchandise Value | Predicts the GMV (Gross Merchandise Value) that an ad will generate; estimated on the basis of an existing order | Regression |


**Core Challenges:**

The accuracy of estimation models directly affects advertiser ROI, platform ad revenue, and product sales efficiency. The main challenges are:

- **Sample Sparsity**: Conversion events (especially orders) are orders of magnitude fewer than clicks and impressions; training signals for pCVR and pGMV are sparse
- **Distribution Shift**: Online traffic distribution continuously changes; models need good generalization capability and timely calibration mechanisms
- **Multi-objective Trade-offs**: pCTR, pCVR, and pGMV must be jointly modeled within the same network; objectives are both competitive and synergistic

### 2.2.2 广告归因和模型 Label/Ad Attribution and Model Labels

[§1.2.5](../01.ads-overview/02.online-advertising-fundamentals.md#125-广告归因模型) introduced the general framework for ad attribution: Click/View attribution types, Last Touch priority rules, and Direct vs. Broad attribution methods. This section explains how the ROI2 product implements these attribution rules and how attribution results are converted into model training Labels.

**ROI2 Attribution Scope:**

Based on the Direct/Broad classification in [§1.2.5.3](../01.ads-overview/02.online-advertising-fundamentals.md#1253-direct-vs-broad-归因), ROI2 expands the attribution scope from Direct Ads Orders to Broad Ads Orders, bundling paid traffic and organic traffic to more completely measure ad value (AdvV):


| Attribution Type   | Determination Logic                                                  | Description                                                             |
| ------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Direct Ads Order   | Reverse-chronologically search the user's 7-day click sequence for an itemID match | Conversion item matches the clicked ad item                  |
| Shop Ads Order     | If no itemID match is found, search for a shopID match               | Conversion item is from the same shop as the clicked ad (different item) |
| Broad Ads Order    | Direct ∪ Shop (mutually exclusive, empty intersection)               | The evaluation metric for ROI2 ads                                      |


Attribution window: Both order types use a **7-day attribution window**.

Attribution determination process:

```
Order occurs → Search for click sequence within 7 days by userID
  → Reverse-chronologically search for itemID match → Direct Ads Order
  → If no itemID match, search for shopID match → Shop Ads Order
  → Neither matches → No attribution
```

**From Attribution to Model Labels:**

Attribution rules determine which orders count as ad conversions, thereby defining the model's training Labels. Using the Unicr model as an example:


| Label                               | Usage                                     |
| ----------------------------------- | ----------------------------------------- |
| direct 7d CR                        | 7-day direct conversion rate, used for online Serving |
| shop 7d CR                          | 7-day shop conversion rate, used for online Serving |
| direct 3d/7d prob, direct 1d/3d prob | Auxiliary objectives for delayed conversion probability modeling |
| shop 3d/7d prob, shop 1d/3d prob    | Auxiliary objectives for delayed conversion probability modeling |


The `direct` and `shop` Labels correspond to the two attribution types above, while auxiliary objectives such as `3d/7d prob` and `1d/3d prob` are used to mitigate the delayed feedback problem caused by the 7-day attribution window (see [§2.2.3](#223-样本生产和模型例行)).

**Why are direct and shop modeled independently?**

Direct conversion (clicked item = purchased item) and Shop conversion (click item A → purchase a different item B from the same shop) are two fundamentally different user behaviors:

- **Different Conversion Paths**: Direct is a short-path "see and buy" decision; Shop involves additional steps such as browsing the shop and comparing across items, resulting in a longer conversion funnel
- **Different Feature Signals**: Direct conversion is primarily driven by the item's own appeal (price, rating, image); Shop conversion relies more on shop-level features (shop category richness, user's historical preference for the shop)
- **Different Conversion Rate Magnitudes**: Shop CR is typically much lower than Direct CR; mixed modeling would cause high-frequency categories to dominate gradients, leading to underfitting for low-frequency ones

Independent modeling gives each Label its own prediction head, allowing the model to learn differentiated behavioral patterns under different attribution types. During online Serving, the two estimated values are also used separately in the AdvV calculation for ROI2.

### 2.2.3 样本生产和模型例行/Sample Production and Model Routine

**Delayed Feedback Sample Handling**: For samples with fewer than 7 days since the click, negative labels may contain false negatives. To balance model timeliness (bidding environment changes in real time), it is generally preferable to use the latest samples with some incorrect labels rather than sacrificing timeliness.

**Model Routine Update Process (3 Stages):**


| Stage                      | Description                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Stage 1 — Seed Round Training** | Uses only fully attributed samples (data before T-8), loads the T-8 checkpoint, trains on T-7 data, and generates a fully attributed model checkpoint      |
| **Stage 2 — Incremental Training** | Loads the T-7 Seed checkpoint generated in Stage 1, incrementally trains for 6 days (T-6 to T-1) on non-fully-attributed samples, generating an Online Serving checkpoint |
| **Release**                | Publishes the Online Serving checkpoint generated in Stage 2 to the online service                                                                           |


This "fully attributed Seed + incremental non-fully-attributed" combined strategy balances model accuracy (the Seed model eliminates false negative samples) and timeliness (incremental training leverages the latest data).

### 2.2.4 模型特征概览/Model Feature Overview

The feature system for CR/PGMV models covers the following main dimensions:


| Dimension           | Representative Features                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| Basic User Attributes | userid, age, gender, address                                                                     |
| User Tags/Preferences | user_type, intent_l0, user_prefer_cat                                                            |
| User Behavior Sequence | Click sequence (500), cart sequence (128), order sequence (128), including itemid/shopid/cat2/cat3, etc. |
| Item/Shop Features  | item id, shop id, cat2, cat3                                                                       |
| Business Scenario Features | Scenario (search/dd/ymal/pp), bidding method (SIMPLE ROI/Target ROI), ad placement position |


By incorporating **scenario features**, the model can accurately understand how item display and user behavior differ across business scenarios (product list pages, search result pages, etc.) and bidding environments (Simple, Target), improving conversion rate prediction accuracy. Different bidding methods (SIMPLE ROI / Target ROI) result in different traffic characteristics and ad placement positions; with bidding method features, the model can distinguish the display effects at different bidding positions.

### 2.2.5 商品卡 UniCR 与 pGMV 模型/Product Ads UniCR and pGMV Models

Product Ads ranking uses **UniCR** as the main fine-rank conversion and pGMV estimation model. UniCR does not only answer "will this click convert"; it estimates the commercial value of a clicked item and feeds the calibrated value into bidding and rerank.

The core pGMV definition is:

```text
pGMV = item_price * sold_cnt_smoothed * CR_7d
```

where `sold_cnt_smoothed` keeps the original value when `x <= 2` and uses `2 + log(x - 1)` when `x > 2`. UniCR models direct and shop value separately:

| Output family | Examples | Online role |
|---|---|---|
| Direct CR / pGMV | `direct_pcr_7d`, `direct_pgmv_7d` | Value from the clicked ad item itself |
| Shop CR / pGMV | `shop_pcr_7d`, `shop_pgmv_7d` | Value from other items in the same shop |
| Delay heads | `direct/shop_pcr_{1h,6h,1d,3d}` | Short-window conversion feedback for freshness |
| Order2Pay / ATC | `direct/shop_order2pay`, `ads_direct/shop_atc` | Auxiliary purchase-intent tasks |

Product Ads pGMV has five recurring challenges: multi-scenario traffic (`search`, `dd`, `ymal`, `pp`), 7-day delayed conversion feedback, multi-task direct/shop learning, long behavior sequence modeling, and a large feature system whose train-serving consistency must be continuously monitored.

#### 2.2.5.1 线上模型链路/Online Model Chain

The online Product Ads model chain is:

```text
Coarse-rank candidate item
-> UniCR main model
-> pGMV cali online post-calibration
-> bidding-side value / eCPM composition
-> rerank delivery
```

The rerank code path is `online-bidding/internal/rule/productads/rerank/model/rerank_uni_pgmv.go`. The main value formula is:

```text
value = direct_pcr_7d * cali_direct_pgmv_7d
      + shop_pcr_7d   * cali_shop_pgmv_7d
```

During promotion periods, the cali model switches the pGMV term to promotion-aware outputs:

```text
ecpm = pctr * (direct_pcr_7d * cali_direct_pgmv_7d_prom_v2
             + shop_pcr_7d   * cali_shop_pgmv_7d_prom_v2) * target_cir
```

Current online model families are:

|---|---|---|---|
| ID | `exp_s_atc_v1_id` / `exp_i_atc_v1_id`, `gpu_nsr_atc_v1_id_v0` | `prd_i_id_item`, `gpu_pgmv_cali_id_item` | Main source path in the Product Ads KB |
| L2 (TW, SG, TH, PH, MY, VN) | `exp_s_uni_atc_v1_L2` / `exp_i_uni_atc_v1_L2`, `gpu_pgmv_uni_L2_atc_v1` | `exp_i_l2_item` / `exp_i_l2_item_bdc` or `exp_i_vn_item` | Region-conditioned model/cali differences exist |

The current UniCR `final_loss` is the sum of four loss groups:

```text
final_loss = cr_loss + order2pay_loss + delay_feedback_loss + act_loss
```

Important label groups are:

| Loss group | Labels / heads | Weight semantics |
|---|---|---|
| CR Loss | `direct/shop_label_{1d,3d,7d}` -> `direct/shop_cr_{1d,3d,7d}` | Window-specific `label_weight` |
| Delay Loss | `direct/shop_label_{1h,6h}` -> `direct/shop_pcr_{1h,6h}` | Window-specific `label_weight` |

| ACT Loss | `ads_direct/shop_act_label` -> `ads_direct/shop_act` | `act_weight` |
| GMV labels | `direct/shop_gmv_label` | Used for pGMV target construction and evaluation, not as an independent `final_loss` term |

#### 2.2.5.3 训练范式、延迟反馈和评估/Training Routine, Delayed Feedback, and Evaluation

UniCR uses the same high-level "fully attributed seed + fresher incremental training" routine described in [§2.2.3](#223-样本生产和模型例行):

| Stage | Data and purpose |
|---|---|
| Seed | Train on T-8 fully attributed data to build a stable checkpoint |
| Increment | Continue from seed and train T-7 to T-2 to absorb fresher traffic |
| Eval / Release | Evaluate on T-1, then release the latest incremental checkpoint when gates pass |

The ID source configuration uses `unicr_pgmv_id_seed.py` / `unicr_pgmv_id_inc.py`, `Product_Rank_V3_exp_s_atc_v1_id/task.yaml` / `Product_Rank_V3_exp_i_atc_v1_id/task.yaml`, 15-16 A30 MIG workers, and 45-48 sample servers. Online serving uses the latest incremental checkpoint through `gpu_nsr_atc_v1_id_v0` under project `PaidadsUniCR` with `trt` executor.

**Online Serving Resources** (as of 2026-06-09):

| GPU Type | Cards | Notes |
|---|---:|---|
| A30 | 78 | — |
| L4 | 220 (52 + 168) | Two instances |
| T4 | 194 (74 + 68 + 52) | Three instances |

**Training Resources** (shared offline cluster):

- GPU: typically **16 cards** (A30 MIG)
- Resource utilization: above 50%
- Cold-start training (single day of samples): **< 1h**
- Warm-start training (last one month of samples): **~2 days**

Delayed feedback is modeled as a conditional cascade:

```text
CR_7d <- main tower output
CR_3d = cr_3d_prob * CR_7d
CR_1d = cr_1d_prob * CR_3d
PCR_6h = prob_6h * CR_1d
PCR_1h = prob_1h * PCR_6h
```

When a longer-window label has not returned, the corresponding shorter conditional probability is blocked with `label_weight=0` and conditional `stop_gradient`, avoiding false-negative gradients. The source KB records an ID evaluation snapshot from 2026-04-12: `direct_pcr_7d` AUC 0.8551, `shop_pcr_7d` AUC 0.9093, `direct_order2pay` AUC 0.7716, `shop_order2pay` AUC 0.7973, and 1h/6h/1d/3d/7d delay-head AUCs staying in a similar range. These values are historical examples, not current production SLOs.

#### 2.2.5.4 特征体系与特征明细/Feature System and Feature Details

UniCR features are dominated by sparse IDs, behavioral statistics, target item signals and sequence signals. The Product Ads feature detail source records 494 features in the 2026-04-27 pull, with sparse=469 and dense=20; all 494 were matched in that pull.

| Feature group | Scale / shape | Use |
|---|---|---|
| Dense | 2 slots, `AutoDis` | Continuous behavior statistics |
| OneHot | 5 slots, `OneHotToEmbeddingLayer` | Discretized statistics such as category or logistics matches |
| Sparse | About 316 model-side sparse slots | User, item, shop, category and prior-statistics embeddings |
| Target | 4 slots: `item_id`, `shop_id`, `global_subcat`, `global_thirdcat` | Target item representation |
| Query | Slot `1008`, 10 tokens | Search query representation |
| Behavior sequences | Click 500, cart/order 128 | Target-aware user interest through `SimpleAttentionV3` |
| Extra | 46 slots | Ads/user/context auxiliary signals |
| Entrance / OrgPredict / Price / SoldCnt | Dense and bucketized slots | Domain, upstream predictions, price and smoothed sales |

Feature processing follows a fixed model-side structure:

| Feature type | Processing |
|---|---|
| Dense | `get_dense_feature` -> `AutoDisLayer(emb_dim=16)` |
| Sparse | `get_slots` -> embedding lookup `(1,16)` |
| Query | `get_slots` with `(10,16)` then token aggregation |
| Target | 4 slots reshaped to `(-1, 4, 16)` |
| Behavior sequence | `SimpleAttentionV3(target, sequence)` |
| Domain | `ctx_entrance` -> `OneHotLayer` -> domain embedding |
| OrgPredict | pCTR / pCR prior scores bucketized by `HardBucketizeLayer` |
| Sold count | `I_price_usd_bucket` selects category-price-bucket sales statistics, then applies the smoothing function |

The full feature table is available in [Appendix A.10](#a10-feature-group-detail特征分组细节) and [Appendix A.11](#a11-unicr-full-feature-inventoryunicr-全量特征清单). The high-signal conclusions are: most zero/empty-rate buckets are low in the snapshot, 12 price/sales prior slots have 0.3-0.4 zero rate, user behavior features dominate the top mask-based feature importance results, and a few features have negative or near-zero importance and should be reviewed together with coverage and collinearity.

**Feature Gaps for Business Objectives:**

Main gaps: (1) insufficient **payment-behavior and add-to-cart** behavior sequence features; (2) incomplete **query-dimension behavioral features** (e.g., query-user cross statistics); (3) **user- and item-level statistical features** (e.g., cross-category purchase stats, recent item conversion rate) still have room for expansion.

#### 2.2.5.5 模型架构和 Domain 建模/Model Architecture and Domain Modeling

UniCR is a multi-task, multi-domain architecture built on `MMOE-STAR`:

```text
Feature encoding
-> EpNet domain-aware gating
-> FINT second-order feature interaction
-> MMOE-STAR multi-task trunk
-> CR / delay / ATC / Order2Pay towers
-> price * sold_cnt * CR_7d pGMV composition
```

| Module | Role |
|---|---|
| `AutoDisLayer` | Encodes continuous features into embeddings |
| `OneHotToEmbeddingLayer` | Converts one-hot statistics into dense embeddings |
| `HardBucketizeLayer` | Buckets OrgPredict scores before embedding |
| `SimpleAttentionV3` | Extracts target-aware interest from behavior sequences |
| `EpNetLayer` | Applies domain-aware gating to feature embeddings |
| `fint_interaction_layer` | Models second-order feature crosses |
| `MMOESTAR` | Shares experts across domains and tasks while keeping domain-aware outputs |
| `Order2PayLayer` / `ActLayer` / `ProbHourLayer` | Auxiliary conversion-intent and delay-feedback heads |

`STAR` domain is derived from `ctx_entrance`, not from raw traffic text:

| Entrance ID | Domain index | Meaning |
|---|---:|---|
| other | 0 | Default / fallback |
| 1 | 1 | Search |
| 3 | 2 | Daily Discover |
| 4 | 3 | YMAL |
| 8, 9, 10, 11 | 4 | Product Page and related entrances |

ID and L2 share the effective main feature families, but L2 keeps region-conditioned processing through `REGION_DENSE_SLOT=46354`, `REGION_SPARSE_SLOT=30585`, `num_regions=8`, and region-aware `HardBucketizeLayer` / `AutoDisLayer`. BR is still an open source-level comparison item.

#### 2.2.5.6 pGMV 校准系统/pGMV Calibration System

Product Ads pGMV cali is an online post-calibration system that maps raw UniCR pGMV closer to observed GMV:

```text
UniCR raw pGMV
-> SIR / ALL-level calibration
-> ItemCali item-level scale
-> promotion-time correction
-> gating, fusion and clipping
-> cali_direct/shop_pgmv_7d_v2 and promotion variants
```

| Component | Code / data | Function |
|---|---|---|
| SIR | `layers/sir_new_v2.py`, slots `16501~16523`, FSE `ads.cali_segment_data_v3` | Segment-level monotonic piecewise-linear calibration |
| ItemCali | `layers/item_cali.py`, slots `6136~6182`, FSE `ads.cali_item_data_v3_agg_rt` | Item-level `GMV / pGMV` scale with order-count and abnormal-scale gates |
| Promotion correction | `layers/fix_ar_ratio_v2.py`, slots `6200`, `6201`, `8888` | Corrects arrival-time GMV vs click-attributed GMV mismatch around campaigns |
| Fusion gate | `item_cali_main.py` | Uses `0.5 * ItemCali + 0.5 * SIR` only when order count and scale conditions pass |
| Clipping | model-side clipping thresholds | Bounds calibration by region and scenario-specific ranges |

SIR combines 1h and 24h statistics: MY/ID/VN/PH/BR use `[0.9, 0.1]`, while SG/TH/TW use `[0.8, 0.2]` for more stability. SG/TH use 5 buckets and other regions use 10 buckets, with 5-bucket data padded to the 11-dimensional 10-bucket shape.

ItemCali computes:

```text
scale = item_GMV_sum / item_pGMV_sum
final_score = 0.9 * (pGMV * scale_1d) + 0.1 * (pGMV * scale_3d)
```

It only contributes when `broad_order_cnt >= 15` and `scale_3d < 2/3 or scale_3d > 2`; otherwise the output falls back to SIR. Promotion correction uses:

```text
prom_ratio = click-attributed GMV / arrival-time GMV
SIR_prom = SIR_normal * prom_ratio
```

The promotion window is `[-120h, +24h)` around the region-adjusted campaign start time; outside the window `prom_ratio` is forced to 1.

**Strategies for Integrating Calibration into the PGMV Model:**

UniCR currently uses **external post-calibration** (SIR + ItemCali). Two viable paths to internalize calibration into the pGMV model itself are:

| Strategy | Description | Trade-offs |
|---|---|---|
| **Add auxiliary loss** | Add an auxiliary loss to the pGMV model that directly optimizes PCOC (`sum(pred) / sum(actual)` → 1.0); the model learns calibration through back-propagation | No extra inference cost; but a global PCOC objective makes fine-grained bucket control difficult |
| **Cascade lightweight sub-network** | Append a lightweight sub-network after the pGMV output layer for end-to-end calibration mapping; effectively integrates SIR/ItemCali logic into the model | Enables item/segment-level calibration; adds inference latency and parameters |

Both strategies are **exploratory directions** and have not been deployed to production.

#### 2.2.5.7 数据契约和分析口径/Data Contracts and Analysis Definitions

For Product Ads UniCR and cali analysis, the current entry table is:

```text
mkplpaidads_search_ads.item_basic_info_for_cali_and_case
```

It is a click-attributed detail table used to analyze business scale, value structure and prediction quality. Confirmed prediction fields are:

| Semantic field | Current field | Use |
|---|---|---|
| `raw_pred_pgmv` | `direct_pgmv_7d_sum` | Raw model prediction before cali |
| `cali_pred_pgmv` | `cali_direct_pgmv_7d_sum` | Calibrated prediction |
| `final_pred_pgmv` | `final_pgmv_sum` | Default first-pass prediction field |

Fields that still need schema confirmation include `pred_shop_pgmv_7d`, `actual_direct_gmv_7d`, `actual_shop_gmv_7d`, `actual_total_gmv`, `dt / region / entrance / placement`, and click-level keys such as `request_id / item_id / shop_id`.

Recommended analysis order:

1. Scale: clicks, requests, item count, shop count, actual GMV and predicted pGMV.
2. Structure: direct vs shop GMV share and predicted-vs-actual structure.
3. Prediction quality: `PCOC_final`, `PCOC_direct`, `PCOC_shop`, total bias and WMAPE.
4. Slices: `region`, `region x entrance`, `region x entrance x placement`.
5. Ranking quality: decile monotonicity, Top bucket GMV capture and bucket-level PCOC.

Standard derived metrics:

```text
PCOC_final = sum(final_pred_pgmv) / sum(actual_total_gmv)
WMAPE      = sum(abs(final_pred_pgmv - actual_total_gmv)) / sum(actual_total_gmv)
```

Do not equate `final_pgmv_sum` with a simple `direct + shop` sum before the schema is confirmed.

#### 2.2.5.8 监控和排查/Monitoring and Troubleshooting

Operational monitoring and troubleshooting entry points:

| Area | Entry |
|---|---|
| Feature null/zero/empty rates | Grafana `featurelog_monitor_all` and `mkplpaidads_search_ads.slot_quality_stats_new` |
| UniCR / URanker latency | `uranker-uworker` dashboard, especially `Rank Latency`, `Rank Latency P99`, `EgoPredict Latency`, `FeatureProcess Latency` |
| PCOC dashboard | DataSuite dashboard `f1379dc0-6a0d-42d0-ba27-b3c3586f3b84` |
| PCOC daily stats | Use the `agents/common/ads-diagnose-model-deepdive-hb.md` agent; input region (e.g. ID) and a date range, then query "arrival-scope PCoC" |
| Business analysis | `mkplpaidads_search_ads.item_basic_info_for_cali_and_case` |

When UniCR / pGMV behaves abnormally, debug in this order: scale, direct/shop structure, prediction quality, ranking monotonicity, then link-level causes such as label backfill, feature coverage, cali correction, online output mapping, and single-path direct/shop anomalies.

| Symptom | First checks |
|---|---|
| PCOC suddenly high or low | Label backfill, attribution window, actual GMV semantics, SIR bucket statistics |
| One region abnormal | Region-specific model or cali weights, 5-bucket / 10-bucket strategy, promotion offset, FSE region slot |
| Search and non-Search diverge | OrgPredict Search-only validity, domain mapping, entrance feature coverage |
| pGMV buckets are not monotonic | Ranking quality, SIR merge buckets, sample size, feature drift |
| Cali correction jumps | SIR 1h/24h fusion, ItemCali order gate, `scale_3d`, promotion ratio, clipping thresholds |
| Latency increases | EGO Predict, FeatureProcess, Rank latency and feature-request path |

**Sparse Embedding / Dense Weight Over- and Under-fitting Detection:**

- **Over-fitting**: val AUC rises after masking the slot; train-val AUC gap > 0.01; low-frequency ID embedding norms are abnormally large
- **Under-fitting**: AUC diff ≈ 0 after masking; slot `zero_rate > 60%`; layer gradient norm stays near 0
- Backbone gradient = 0 in Increment stage is expected `stop_gradient` behavior, not under-fitting

### 2.2.6 非商品卡模型/Non-Product Card Models

- **Product Ads** (e.g., search ads, recommendation ads):
  - Objective: Drive user clicks and conversions (purchases), heavily reliant on matching user intent with products.
  - Characteristics: Strong time-sensitivity, conversion-oriented, SKU-level granularity.
- **Brand Ads**:
  - Objective: Increase awareness, engagement, and preference for brands/shops/content/streamers, indirectly driving transactions.
  - Includes three types:
    - **Shop Ads**: Promote the overall image of a merchant.
    - **Live Ads**: Combine livestream content with real-time interaction and orders to enhance user immersion.
    - **Video Ads**: Content-driven user attraction and product discovery.

**Summary**: Brand Ads focus more on content quality, user interest retention, and brand/content impression; Product Ads emphasize immediate conversion.

The model architecture comparison for Brand & Content Ads is as follows:


| Dimension            | Product Ads                          | Shop Ads/Display Ads                              | Video Ads                                                       | Live Ads                                                                                     |
| -------------------- | ------------------------------------ | ------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Recall Objective** | Items (SKUs) matching user purchase intent | Shops and items matching users' latent interest/preference | Videos and items matching user interests              | Livestream rooms (with engagement and conversion potential) and items that users may be interested in |
| **Recall Method**    | Based on item features               | Based on shop items, based on shop brand keywords | Based on linked items, based on video content/creator           | Based on livestream items, based on live streamers                                           |
| **Ranking Direction** | Item CTR (relevance), item conversion rate | Shop/item clicks (relevance), shop/item conversion | Item clicks under video, order conversions under video, video watch time/completion rate, LTR alignment for mixed ranking | In-stream item clicks, order conversions in livestream room, dwell/interaction in livestream room, LTR alignment for mixed ranking |

#### 2.2.6.1 Shop Ads 模型/Shop Ads Model

Shop Ads promotes an entire shop rather than a single item: one ad card carries a shop plus up to 10 of its items, so the ranking stack must reason over the shop dimension and the item dimension simultaneously. Two independent inference models drive ranking — a **pCTR model** and a **pCR model** — whose outputs are combined by the scoring layer.

**Scoring Formula**

```
Final Score = eCPM + α · eGMV = pCTR · bidPrice + α · pCTR · pCR · AOV
```

`pCTR` = predicted click rate; `pCR` = predicted post-click conversion rate; `AOV` = shop-level average order value (static statistic); `α` = revenue/GMV balance weight. A shop ad is displayed when the final score clears the eCPM threshold set by traffic control.

**pCTR Model**

A dual-tower multi-task model jointly predicting `shop_ctr` (click on the shop card) and `item{i}_ctr` (i = 1..10, click on each item in the card); shared representations lift both tasks.

- **Feature groups**: shop / shop multi-value (seq 5) / top-shop-items (≤20, attention-pooled) / item (Top-N, ITEM_LEN=10) / user / query / user×shop cross stats / user behavior (UB).
- **Interaction**: **SeNet** (field re-weighting) + **FINT** (pairwise field interaction), applied to context / user / item groups.
- **UB modeling**: click/cart/order each over **6 time windows (1h/3h/1d/3d/14d/60d)**, attended by **DIN multi-head**, steered by an enriched query embedding; short-negative sequence via contrastive DIN (negated embeddings).
- **MMOE**: **2 experts (item + shop) shared by both towers through a soft gate**; the shop tower also consumes the pooled item-expert output, so item-level click patterns debias shop-level scoring (exposure/position debiasing).
- **Calibration & outputs**: post-hoc calibration → `shop_ctr`, `item{i}_ctr`.

**pCR Model**

An **MMOE-STAR** model for the click→(cart)→order funnel, explicitly modeling two paths — direct (`pCR2`: click→order) and indirect (`pCR1`: click→cart→order) — fused per user:

```
pCVR = direct_weight · (1 − pATC) · pCR2 + indirect_weight · pATC · pCR1
```

with weights from a light user-conditioned tower (user_id + country).

- **Feature groups**: shop / user / keyword+cross / country (domain indicator) / item (≤10) / UB click(500) / cart(128, time-decay) / order(128) / short-negatives(1d/3d/7d).
- **Interaction**: SeNet on all groups; FINT only on shop+user (skipped on the large context/item groups to avoid O(L²) cost).
- **UB modeling**: a single consolidated long sequence per behavior, DIN multi-head; contrastive DIN for short negatives.
- **Domain adaptation**: **EpNet** country-embedding gating — one model serves 8 markets (ID/MY/SG/TH/PH/VN/TW/BR) without per-country weights.
- **Joint tasks**: pCTR / pATC / pCTATC / pCR1 / pCR2 / pCVR / pCTCVR; `final_loss = pCTR + pATC + pCTATC + pCTCVR` (pCR1/pCR2/pCVR are GAUC-monitored, gradients flow via pCTCVR).
- **Calibration & outputs**: per-country calibration table (loaded from HDFS) → `shop_broad_cr` (calibrated pCVR), `pCVR` (raw).

**Training Data**

- **FeatureDump** (raw hourly, pre-FP): Hive `mkplpaidads_offline.ssp_raw_sample_shop_ads_hourly_reg_live`.
- **Train data** (post-FP, EGO parquet): `hdfs://R2/projects/mkplpaidads_offline/hdfs/prod/alg/shop_ads/train_data_parquet/{region}/{dt}/{hh}`; readiness marker `mkplpaidads_offline.shop_ads_{region}_gentraindata`.
- **Label delay**: CTR 1–2h (near-real-time); CR 7d (attribution window). BR traffic is dumped independently and synced to the SG cluster after the 7-day window.

**Online Serving**

EGO + AFP inference, served via URank, weights refreshed daily; **model routing is per-country** via AB features (`shopAdsPCtrURankerModel` 3288 / `shopAdsPCrURankerModel` 3283). pCTR is `gpu_shopads_pCTR_base` (20505) across all regions; pCR is region-specific (`gpu_shopads_pCR_base` 21743 / `gpu_shopads_pCR_new_labels` 24088 / `gpu_shopads_pCR_all_features_satt` 23681) — see the team KB §10 serving matrix for the per-country routing (changes frequently). Flow: AFP feature fetch → EGO checkpoint inference → URank orchestration → `pCTR` + `pCR` returned to the ranking service.

#### A.8 Calibration Operational Detail/校准运维细节

**SIR algorithm:**

```text
Given bucket boundaries x_0, x_1, ..., x_n (pGMV means)
and corresponding values y_0, y_1, ..., y_n (GMV means)

For x falling in bucket i:
f(x) = k_i * (x - x_i) + y_i
k_i = (y_{i+1} - y_i) / (x_{i+1} - x_i)
```

**1h / 24h fusion weights:**

| Region | w_1h | w_24h | Reason |
|---|---:|---:|---|
| MY, ID, VN, PH, BR | 0.9 | 0.1 | Sufficient data, 1h already stable |
| SG, TH, TW | 0.8 | 0.2 | Smaller data volume, needs more 24h stability |

**Bucket strategy:**

- SG / TH: 5 buckets for statistical stability.
- Other regions: 10 buckets.
- 5-bucket data padded to 11 dimensions to align with 10-bucket.

**`merge_bucket` constraints:**

- Each bucket has sufficient samples: at least `total_clk / bucket_number`.
- Each bucket GMV statistic large enough: at least `17,500,000`.
- Inter-bucket actual GMV/click strictly monotonically increasing.

**ItemCali time window:**

```text
final_score = 0.9 * (pGMV * scale_1d)
            + 0.1 * (pGMV * scale_3d)
```

Safety mechanisms:

- Small-value protection: GMV or pGMV < `10,000` → scale defaults to 1.
- Order count gate: `broad_order_cnt >= 15` required to potentially enable item calibration.
- Deviation gate: `scale_3d < 2/3` or `scale_3d > 2` to enable; otherwise fallback to SIR.

**Promotion `dt` calculation:**

```text
Per-region promotion actual start = start_time_base(slot 6200) + region_offset
dt = (cur_time(slot 8888) - per-region actual start) // 3600
```

Region offsets:

| Region | Offset |
|---|---:|
| MY, SG | +0h |
| TW, PH | +4h |
| TH, ID, VN | +5h |
| BR | +15h |

Influence window:

- `dt ∈ [-120h, 0)`: 5 days pre-promotion, ratio gradually increases.
- `dt ∈ [0, +24h)`: 1 day post-promotion, ratio falls from peak.
- `dt <= -120h` or `dt >= +24h`: ratio forced to 1.

Data sources:

- `start_time_base` (slot 6200) and `prom_scale` (slot 6201) written by operations ~2 days pre-promotion via `sales_data_for_fes_new.sql` to FSE.
- `cur_time` (slot 8888) injected by online serving automatically.
- `params.py` parameters fit offline via L-BFGS-B on historical promotion data, stored by `{REGION}_{ENTRANCE}_{PLACEMENT}`.

**Clipping thresholds:**

```text
calib_score = clip(calib_score, ref / (1 + thre), ref * (1 + thre))
```

| Scenario | thre | Allowed range |
|---|---:|---|
| SIR most regions | 0.35 | `[pGMV/1.35, pGMV*1.35]` |
| SIR TW low bucket (< 3) | 0.5 | `[pGMV/1.5, pGMV*1.5]` |
| SIR TW high bucket shop | 0.4 | `[pGMV/1.4, pGMV*1.4]` |
| SIR promotion TW / SG | 0.5 | `[pGMV/1.5, pGMV*1.5]` |
| Item + SIR fused | 0.5 | `[pGMV/1.5, pGMV*1.5]` |

#### A.9 Data Tables and Analysis Definitions/数据表与分析口径

**Business analysis entry table:**

```text
mkplpaidads_search_ads.item_basic_info_for_cali_and_case
```

This is a click-attribution detail table containing predicted and actual values, usable for analyzing UniCR pGMV business scale, value structure, and calibration deviation. It answers three types of questions:

1. Business scale: How much direct / shop GMV ad clicks actually generate.
2. Value structure: Whether GMV comes primarily from direct or shop, and whether `region / entrance / placement` show significant differences.
3. Prediction quality: Whether UniCR pGMV is consistent with actual GMV, and where deviations concentrate.

**Core metrics:**

Scale metrics:

| Metric | Formula | Description |
|---|---|---|
| Click volume | `count(*)` | Sample scale |
| Distinct requests | `count(distinct request_id)` | Request coverage |
| Distinct items | `count(distinct item_id)` | Supply coverage |
| Distinct shops | `count(distinct shop_id)` | Merchant coverage |
| Actual GMV/click | `sum(actual_total_gmv) / count(*)` | Average actual value per click |

Prediction quality:

```text
PCOC_final  = sum(final_pred_pgmv) / sum(actual_total_gmv)
PCOC_direct = sum(pred_direct_pgmv_7d) / sum(actual_direct_gmv_7d)
PCOC_shop   = sum(pred_shop_pgmv_7d) / sum(actual_shop_gmv_7d)
WMAPE       = sum(abs(final_pred_pgmv - actual_total_gmv)) / sum(actual_total_gmv)
```

Calibration chain diagnostics:

| Metric | Formula | Description |
|---|---|---|
| Raw prediction total | `sum(raw_pred_pgmv)` | Pre-calibration scale |
| Calibrated prediction total | `sum(cali_pred_pgmv)` | Cali output scale |
| Calibration multiplier | `sum(cali_pred_pgmv) / sum(raw_pred_pgmv)` | Overall lift or compression |
| Per-click correction | `avg(cali_pred_pgmv - raw_pred_pgmv)` | Average correction per click |
| Per-click correction rate | `avg((cali_pred_pgmv - raw_pred_pgmv) / nullif(raw_pred_pgmv, 0))` | Relative correction magnitude |

Ranking ability:

| Metric | Formula | Description |
|---|---|---|
| Bucket monotonicity | `ntile(10)` by `final_pred_pgmv`, check predicted mean vs actual mean per bucket | High-score samples should have higher actual value |
| Top bucket GMV capture | `top10% bucket actual_gmv / total actual_gmv` | How much real GMV high-score traffic captures |
| Bucket PCOC | `sum(pred) / sum(actual)` per bucket | Locate over/under-estimation by score segment |

**First-pass analysis path:**

1. Overall: click volume, actual GMV, final predicted pGMV, pGMV/click, `PCOC_final`, WMAPE.
2. Direct / shop split: output both direct and shop GMV, pGMV, PCOC and proportions when fields are available.
3. Calibration chain: `direct_pgmv_7d_sum` → `cali_direct_pgmv_7d_sum` overall and slice changes.
4. Core dimension drill-down: prioritize `region`, `region × entrance`, `region × entrance × placement`.
5. Bucket analysis: 10 or 20 buckets by `final_pred_pgmv`, check GMV capture, monotonicity and per-bucket PCOC.

**SQL standard definitions:**

Outermost layer should unify derived fields first, then aggregate:

```text
raw_pred_pgmv    = coalesce(direct_pgmv_7d_sum, 0)
cali_pred_pgmv   = coalesce(cali_direct_pgmv_7d_sum, 0)
final_pred_pgmv  = coalesce(final_pgmv_sum, 0)
actual_total_gmv = coalesce(actual_direct_gmv_7d, 0) + coalesce(actual_shop_gmv_7d, 0)
abs_err_total    = abs(final_pred_pgmv - actual_total_gmv)
```

Aggregation layer:

```text
total_click                = count(*)
total_actual_gmv           = sum(actual_total_gmv)
total_final_pred_pgmv      = sum(final_pred_pgmv)
avg_actual_gmv_per_click   = sum(actual_total_gmv) / count(*)
avg_final_pgmv_per_click   = sum(final_pred_pgmv) / count(*)
pcoc_final                 = sum(final_pred_pgmv) / nullif(sum(actual_total_gmv), 0)
wmape_total                = sum(abs_err_total) / nullif(sum(actual_total_gmv), 0)
```

**Field confirmation rules:**

After obtaining the table structure, prioritize confirming:

1. Whether `final_pgmv_sum` is only the calibrated direct final value, or includes other post-processing.
2. Whether actual values are split into direct / shop columns, or only total GMV.
3. Whether `region`, `entrance`, `placement` exist.
4. Whether `request_id`, `item_id`, `shop_id` exist.
5. Whether the date field is `grass_date`, `dt`, or another partition name.

Minimum analyzable set requires: date, click-level primary key, predicted value and actual value.
