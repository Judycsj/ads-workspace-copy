## 2.1 召回通路和供给策略/Recall Channels and Supply Strategy

### 2.1.1 召回定位/Recall Positioning

召回阶段面向全量广告候选库，是广告供给侧的源头，其核心特点：

**一、模型轻量化**：召回阶段面向百万级全量广告库，候选数量 O(模块候选数量) 较大，因此单个候选计算复杂度 O(单个候选计算时间复杂度) 必须控制在较低水平。不同阶段候选量规模：


| 阶段      | 候选规模       | 说明               |
| ------- | ---------- | ---------------- |
| Recall  | 全量广告库（百万级） | 召回 TopK 约几千条     |
| Prerank | 召回结果集（千级）  | 粗筛 TopK 约几百条     |
| Rank    | 粗排结果集（百级）  | TopK 约为粗排的一半甚至更少 |
| MixRank | 精排结果集      | 最终混排后返回给用户       |


各阶段时间复杂度和精度排序：时间复杂度 DNN > 向量双塔 > LR > 规则类；精度排序同上。召回阶段面向百万级候选，因此采用轻量化算法（双塔模型、统计协同过滤等）。

**二、多路并行召回**：为满足多业务场景和用户多样性需求，召回阶段同时维持多种召回通路并行，从不同角度提供候选集：

- **场景差异性**： Search 场景围绕 Query 建模（QueryUnderstanding）， Discovery 场景围绕 User 建模（UserUnderstanding）
- **目标多样性**：不同通路分别侧重用户活跃度（点击行为）、转化率（购买/加购行为）、商业变现等不同目标
- **用户兴趣多样性**：同时覆盖长期兴趣（Offline U2I）和短期兴趣（Online U2I），兼顾重定向性（捕捉最新兴趣）和泛化性（跨领域兴趣扩展）

**在整体链路中的位置。**

```text
全量广告库（百万级）
  ↓  [Recall] 多路并行召回 → 过滤 → Zigzag Merge → 几千条候选   ← 本章关注
  ↓  Prerank 粗排模型打分 → 几百条
  ↓  Rank 精排模型打分 → 几十条
  ↓  MixRank 混排 → 最终展示
```

一次请求的完整链路：`request → query/user/context understanding → recall → filter → merge → prerank/rank → mixrank`。

**职责边界。**

- **负责召回什么候选**：为 Search、DD、YMAL、RCMD、Live、Video、Shop、Brand 等场景生成广告候选。按检索方式分 6 大类 op（KNN / KV / Text / FSE Realtime / U2U2I / Fallback），按业务通路表现为 U2I、I2I、Q2Tag2I、U2C2I/SID、Keywordless、Popularity、Rewrite、AdTag、Content Ads unified recall 等队列。
- **不负责什么**：不负责最终排序、最终竞价/出价、扣费结算、投放履约，也不负责候选索引的生产与写入本身。
- **与上下游的边界**：
  - **上游（特征 / 索引）**：`Ads Info` 与 `Indexer` 负责候选可检索性、字段可用性与时效性。`FSE` 提供实时用户行为、长序列特征及 `SimpleStandardURankerOp` 的在线特征。`AFP` 提供离线特征血缘与 serving 端特征处理。`EGO` 负责双塔模型训练与 Serving，产出 User Tower / Item Tower Embedding。
  - **下游（排序 / 竞价）**：`Prerank` 粗排决定进入精排的候选；`Rank` 精排决定最终优先级；`Bidding` 决定价格和目标约束；`MixRank` 负责广告与自然结果的混排。
  - **合并与过滤**：召回内部包含 `MergeRecallResultOp`、`AdsInfoFilter`（Search / Discovery）、`RcmdAdsDedupOp`（仅 Discovery）、`SnakeMergeFilterOp`、`BizTagCalculateOp`、`PackRecallAdsResultOp`、`SendRecallLogOp` 等 op。

因此，"模型召回到了"不等于"一定进入粗排"：候选还要经过 merge、AdsInfoFilter、Discovery 去重、SnakeMerge 截断、业务标签计算、打包和日志透传。排查时应先确认候选停在哪个阶段，再判断是模型检索、过滤、去重、quota 截断还是下游链路问题。

**Search / Recommend 召回统一口径。** 理解搜索和推荐场景的召回统一时，需要拆成工程侧和算法 / 策略侧两层。工程侧不是把 Search 和 Recommend 合成同一个 DAG，也不是强行共用同一批队列；统一点在于：同一套 `paidads-recall` 服务框架、Graph Engine 执行契约、`graph-manager-conf` 配置仓库、Operator 抽象、AB / 降级 / 缓存 / 过滤 / merge / 日志观测机制。场景差异保留在 `SPEX_SDU`、DAG 文件、场景 handler、QueryUnderstanding / UserUnderstanding 和具体队列策略中。

工程侧统一可以按以下层次理解：

| 层次 | 已统一的部分 | Search / Recommend 保留的差异 |
|---|---|---|
| 调用链路 | 在 GMV MAX / 新链路中，`ads-engine` 通过 API0 调 `paidads-recall` 拉 Ads 候选，API1 再补 AdsInfo；召回结果以候选 id + queue/source 信息返回给后链路。背景见 [系统链路模块](../01.ads-overview/03.system-pipeline-modules.zh-CN.md)。 | Search 请求的显式输入是 query；Recommend / Discovery 请求的核心输入是 user、entrance、PDP/cart/game 等上下文。 |
| 服务入口 | `paidads-recall` 是统一 Retrieval 服务 binary。[`server/retrieval/run.go`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/server/retrieval/run.go) 根据 `SPEX_SDU` 互斥分发：`deep.paidads.recall.search -> SearchServe`、`paidads.discoveryretrieval -> RcmdServe("")`、`retrieval.videoads -> RcmdServe("video")`、`shopads.retrieval -> ShopServe`、`retrieval.liveads -> LiveAdsServe`。共享 `initConfig` 初始化动态配置、related item、AdsInfo SDK 和 op debug。 | Search 和 Recommend 仍是不同 SDU / handler：Search 使用 `search-retrieval`，Recommend 使用 `rcmd-retrieval`。上线、容量和 preliminary 选择仍要按受影响路径判断。 |
| Graph 配置 | `graph-manager-conf` 的 [`config.yaml`](https://git.garena.com/shopee/deep/searchads/graph-manager-conf/-/blob/master/config.yaml) 在同一个 `retrieval` service 下注册 `search_recall.yaml`、`recommend_dd.yaml`、`recommend_ymal.yaml`、`recommend_pp.yaml`、`recommend_game.yaml`、`video_ads_recall.yaml`、`shop_search_retrieval.yaml`、`live_ads_recall.yaml` 等图。`paidads-recall` 通过 `GraphManagerVersion` 绑定具体配置版本。 | Search 主图是 `search_recall.yaml` / `image_search_recall.yaml`；Recommend 主图按入口拆为 `recommend_dd / ymal / pp / game`。统一的是 Graph Engine DAG 契约，不是同一份 YAML。 |
| Graph 执行 | Search resource 会用 `util.GetDagEngine("retrieval", "search_recall")` 加载 Search 图；Recommend resource 会把 DD / YMAL / PP / Game 加载为 entrance_group 到 GraphEngine 的映射。所有图都由 Graph Engine 执行 `args / inputs / outputs` 形式的 Operator。 | Search 的图前段围绕 QueryUnderstanding、Q2I、QT2I、relevance；Recommend 的图前段围绕 UserContext、PDP/cart/game trigger、U2I / I2I / U2U2I。 |
| Operator 抽象 | KNN / KV / Text / FSE / filter / merge / pack / log 都以 Operator 方式注册和编排。通用队列字段包括 `queue_name`、`ab_param_key`、`model_param_key`、`vespa_name`、`rank_profile`、`required_output`、`recall_limit` / `result_global_limit`、`downgrade_level`。新增队列通常先改 `graph-manager-conf/retrieval/*.yaml`，再更新 `paidads-recall` 的 AB 参数和 graph version。 | KNN 方向按 seed / target 拆成 `KnnQ2IOp`（Search Q2I）、`KnnU2IOp`（Recommend U2I）、`KnnU2UOp`（U2U2I）；KV 方向按 `RedisQ2IOp`、`RedisI2IOp`、`RedisU2IOp` 等区分。 |
| 过滤 / 合并 / 打包 | [`MergeRecallResultOp`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/common_operator/merge_queue_result_op.go) 统一把各队列输出按 label 拆分、队列内去重、按 `DefaultLimit` 截断并写入 `QueueCollection`；[`CommonAdsInfoFilterOp`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/common_operator/ads_info_filter_op.go) 统一收集 ad/item/live id、批量拉 AdsInfo、执行 base check，再调用场景 filter；`SnakeMergeFilterOp`、`PackRecallAdsResultOp`、`SendRecallLogOp` 统一做截断、响应打包和日志。 | Search filter 由 `SearchAdsInfoFilterOp` 扩展 query / relevance / keyword 相关规则；Recommend filter 由 `RCMDAdsInfoFilterOp` 扩展 placement、pricing type、anti-fraud、已展示去重等推荐场景规则。 |
| 运行时控制与观测 | ABTestConfig / SPEX 动态配置统一控制 `enable`、limit、cache、`model_param_key`、downgrade；`queue_name` / queue label 统一贯穿 recall log、source funnel、`op_debug_info` 和 Graph Engine operator latency。工程 KB 的 [Ads Recall Service](../03.ads-engine/03.ads-recall-service.zh-CN.md) 已把这些归纳为“系统通用逻辑”。 | 具体指标前缀、SDU pattern、队列 limit 和 AB 字段名仍按 Search / Recommend 图和队列分别配置。 |

**Search API0 Recall 执行入口。** 问“广告召回在 API0 pipeline 中的执行位置、DAG 包含哪些 operator、执行顺序如何”时，先落到 `paidads-recall` Search handler 和 `graph-manager-conf` 的 `search_recall` 图：

| 查询点 | 结论 / 入口 |
|---|---|
| Search API0 代码入口 | [`RecallAds`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/search/handler.go#L23) 校验请求、构造 `NewRetrievalReqContextV2`，随后执行 `resource.NewRecallGraphEngine.Execute(..., "SendRecallLog", "PackRecallAdsResult")`。 |
| DAG 加载入口 | Search resource 通过 [`util.GetDagEngine("retrieval", "search_recall")`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/search/resource.go#L234) 初始化 Search Recall 图；`GetDagEngine` 内部调用 [`graphmanager.GetGraph`](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/utils/utils.go#L65) 并解析 YAML。 |
| Search Recall DAG | 权威配置是 [`graph-manager-conf/retrieval/search_recall.yaml`](https://git.garena.com/shopee/deep/searchads/graph-manager-conf/-/blob/master/retrieval/search_recall.yaml)。前段是 `FetchQueryInfo / FetchQueryFeatures / FetchUserFeature / GetQueryUnderstanding / GenerateRecallOptionV2 / CheckFirstPage`；中段并行跑 `QT2I_611020304`、`Q2I_611030109/611030110`、`FSE_Q2I_611030202`、`Q2I2I_612031201`、keyword match、KNN Q2I 等队列；后段是 `MergeRecallQueue -> AdsInfoFilter -> SnakeMergeFilter -> BizTagCalculate -> PackRecallAdsResult`，并由 `SendRecallLog` 产出 trace。 |

接口统一的边界也要说明清楚：O4-KR2-KP4 的 [Retrieval Interface Unification](../../../team/00.paid-ads-dev/10.trd-prd-td-list/2026q2/o4/kr2-kp4-202606021105/epic-file.md) 处理的是 Retrieval 接口协议、入口参数、response parser、Resp / preliminary / AB validation 的对齐；它不重写召回算法本身。当前文档记录 Live、Shop、BrandMax、Video Retrieval 接口统一均已 rollout，其中 Shop 有明确迁移事实，其他入口以现有结构统一 / recall 链路覆盖。

算法 / 策略侧的边界更收敛：目前真正做统一建模的是 **UniModel KNN**，主要覆盖 Search KNN Q2I（如 `611010104`）和 Discovery / YMAL U2I（如 `623012108`）这类向量召回；其他队列还不是统一模型。Search 侧主力仍是 query 驱动的 Q2I / Q2Tag2I / LLM Q2I 等队列；Recommend / Discovery 侧主力仍是 user / item / PDP 驱动的 U2I、I2I、U2U2I 等队列。

UniModel KNN 的统一方式如下：

| 维度 | 统一处理方式 |
|---|---|
| 统一范围 | 同一套训练代码支持 `Search / DD / YMAL` 三个 entrance，覆盖 8 个 region。样本中通过 `entrance` 和 `country` 特征区分场景和国家，而不是为每个场景完全维护一套独立模型。 |
| 模型结构 | Item Tower 共享权重，输出统一 item embedding；User 侧按场景保留差异：RCMD（DD + YMAL）User Tower 是 `256 -> 128 -> 64` 的 MLP，Search User Tower 由 Query Tower 和 User Personalization Tower 经过 sigmoid gate 融合。Item Tower 同样走 `256 -> 128 -> 64` 后做 L2 normalize。 |
| 特征组织 | 共享 item 侧 item/shop/category、title token、title FastText/Attention embedding、item dense embedding 等特征；Search 侧额外使用 query token / query embedding；Recommend 侧使用用户行为序列、入口、PDP context、recent item / PDP item 等兴趣上下文。不同场景的特征被组织进同一训练图，再按 `entrance_flag` 分流到 Search 或 RCMD tower。 |
| 样本组织 | 训练样本用 `entrance_flag` 区分 `Search=0 / DD=1 / YMAL=2`，用 country slot 区分 region；每条样本包含正样本和请求内 / easy / NSC 等负样本，常见总候选维度为 `TOTAL_TRAIN_ITEMS=104`。代码中会按 Search / RCMD 先做 `dynamic_partition`，分别走对应 user tower，再把结果 stitch 回统一 batch。 |
| 目标和评估 | CTR softmax loss 按 `Search / DD / YMAL × 8 region` 拆成 24 个分区分别打 `ctr_auc_{scene}_{region}`；同时引入 ADVV contrastive loss，并以 `ctr_loss + 0.1 * advv_loss` 作为训练 loss。这样能在同一模型里共享 item 表达，同时保留不同场景、国家的效果观测。 |
| 在线产出 | 在线侧通过 OhMyEmb / EGO 产出 `user_emb_output` 和 `item_emb_output`，再被不同 retrieval graph 中的 KNN 队列引用。Search graph 用 Query / Search user embedding 去查 Q2I KNN；Recommend graph 用 user embedding 去查 U2I KNN。 |

因此，“算法统一”不能泛化到所有召回队列。队列编号、KNN/KV/Text/FSE/U2U2I/Fallback 检索范式、OhMyEmb / Vespa / Redis / FSE 供给底座可以统一沉淀；但具体队列策略仍按场景拆分：Search 保留 QueryUnderstanding、Q2I、Q2Tag2I、相关性过滤；Recommend 保留 UserUnderstanding、PDP/cart/game trigger、I2I、U2U2I、已展示去重和场景过滤。

**业务背景和痛点。**

- **召回覆盖**：Ads impression 中 ads recall 占比低于预期（95% 为 team-level 目标），部分场景存在 0 候选、独占率低、长尾差等问题。
- **广告库规模**：广告库持续膨胀（TW 从 580 万 → 950 万），但单次请求仅能展示几十条广告，第一级筛选必须在毫秒级完成。
- **架构历史包袱**：召回通路多、索引分散、placement 路由负担重，导致维护成本高、调参链路长、线上诊断不统一。
- **模型化方向**：2025 Q1 已在 RCMD 场景落地离线 U2I 长序列多兴趣建模并取得线上收益；当前目标是演进为在线统一长序列模型，提升实时性并降低离线维护成本。
- **业务目标**：提升 recall coverage、候选质量和收入表现；统一索引和业务路由；沉淀召回知识库、分析方法和诊断 skill。

**季度路线图。**

- **2025Q1**：统一 Search / Discovery 的 recall 架构，推动队列收敛、Search relevance 和全链路一致性建模。
- **2025Q3**：推进 API0 / 全 bidding type 统一召回、Query/User2Tag 服务化、QIR 迁移与相关性优化；U2U2I 全量后带来显著收入增益。
- **2025Q4**：建设 Tag 评估体系、Recall Efficiency、U2C2I/SID、RCMD 长序列在线化。
- **2026Q1**：继续推进 Content Ads recall 重构、Search LLM/Q2Tag2I、Search & RCMD 模型化召回、2k 长序列、model i2i、quota / 降级 / 实验监控等能力建设。

**架构模块。** 召回架构从逻辑上拆分为以下核心模块：


| 模块                        | 功能                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------- |
| **Request Understanding** | 对输入信息进行统一理解（Search 场景为 QueryUnderstanding， Discovery 场景为 UserUnderstanding），结果全链路复用 |
| **Recall Queues**         | 多种召回队列并行运行，提供多样化候选集                                                                 |
| **Ads Info**              | 广告有效性过滤（预算不足/停投/库存不足/黑名单）； Discovery 场景额外进行已读过滤（已展示的商品不再二次展示）                       |
| **Tag Service**           | 在召回阶段之后对每个召回 item 动态打标，生成丰富标签信息，供后续链路（粗排/精排/重排）进行策略扶持或业务规则干预                        |
| **Relevance Strategy**    | （仅 Search）过滤与 Query 不相关（ir）的 item，保留弱相关（sw）和相关（r）结果送往后链路                            |
| **Zigzag 合并**             | 各召回通路结果合并截断，各通路召回数量不同，通过 zigzag 实现按比例合并，确保最终 TopK 控制在合理范围                           |


**核心概念术语。**

*队列与通路：*

| 概念 | 定义 | 落点 |
|---|---|---|
| recall channel | 单一路径或队列，例如 KNN、Q2Tag2I、U2I、I2I、Keywordless | 召回的基本组织单元 |
| queue_name | 召回队列的 9 位数字编码，例 `611020304`、`624012101` | 统一标识场景 / 通路类型 / 服务类型 / 具体队列 |
| candidate | 召回阶段输出的广告候选集合 | 后续 filter / merge / rank 的输入 |
| query understanding | 对 query / user / context 的理解结果（rewrite、意图特征等） | Search 场景入口 |

*检索方式（op 级）：*

| 概念 | 定义 | 落点 |
|---|---|---|
| KNN recall | 通过 Vespa ANN 向量索引做双塔近邻检索 | 模型化召回队列的主要在线执行方式 |
| KV recall | 通过 Redis 查离线算好的 I2I / U2I 映射 | 离线产出队列的在线执行方式 |
| text recall | 通过 Vespa 倒排索引做关键词匹配 | Search 特有的文本匹配队列 |
| FSE realtime recall | 基于 FSE 在线实时用户行为 / 长序列特征做召回 | 承接 `SimpleStandardURankerOp` 的在线 reranker |
| U2U2I recall | KNN + FSE 两阶段（先 U→U，再 U→I）组合召回 | RCMD / Discovery 主力收入队列之一 |
| fallback recall | 当前置队列 0 候选或降级时启用的兜底通路 | 保障 0 候选兜底与稳定性 |

*模型与样本：*

| 概念 | 定义 | 落点 |
|---|---|---|
| dual-tower model（双塔模型） | User / Query 塔与 Item 塔分别编码成向量，通过余弦相似度检索 TopK | Recall 最主要的模型架构 |
| I2I（Item-to-Item） | 给定一个 Item，找到相似 / 相关 Item | 策略 I2I（ItemCF 共现）与模型 I2I（Embedding 暴力近邻）实现不同 |
| U2I（User-to-Item） | 用户塔 × Item 塔的 TopK 召回 | 长序列 / 多兴趣双塔的主形态 |
| Q2I / Q2Tag2I | Query 塔 → Item 或 Query → Tag → Item 的 Search 专用通路 | Search relevance + 扩召回同时兼顾 |
| Extra Embedding | 用离线预计算的稠密 embedding（LLM / MPI）替代 sparse fkey | 长序列模型训练/serving 的关键特征形态 |
| checkpoint | 模型训练产出的快照，用于 serving 发布 | 每个 checkpoint 绑定样本日期 |

*合并 / 过滤 / 降级：*

| 概念 | 定义 | 落点 |
|---|---|---|
| merge / truncate | 多队列结果的合并、去重、截断过程 | 决定候选量、独占率与后链路负载，对应 `MergeRecallResultOp` / `SnakeMergeFilterOp` |
| AdsInfoFilter | 召回后的 ads 基础过滤链（可见性 / 审核 / 类目 / 黑白名单 / 价格 / placement / 视频匹配 / 店铺评分 / 反作弊 / 同店 / 跨境等） | Search 与 Discovery 走不同实现 |
| RcmdAdsDedup | Discovery 专属的跨队列去重 op | 仅 Discovery 启用 |
| biz tag | 候选在 `BizTagCalculateOp` 阶段写入的业务标签 | 供下游 Prerank / Rank / 监控使用 |
| downgrade level | L2 / L3 / LM 三级降级，逐级关停非关键通路与模型 | 稳定性兜底 |

Discovery 和 Search 场景在算法建模上差异较大，下文分别介绍各自的召回算法；对于业务需求算法支持（扶持队列等）的设计思路则统一在 [§2.4.2](04.traffic-strategy-and-billing.zh-CN.md#242-流量扶持) 介绍。

### 2.1.3 商品卡流量广告召回/Product Card Traffic Ad Recall

#### 2.1.3.1 RCMD Item Ads 召回算法/RCMD Item Ads Recall Algorithm

##### 2.1.3.1.1 场景特性/Scenario Characteristics

Discovery Ads 场景（DD、YMAL、GAME、Cart_Unify）主要特征：

- **多场景统一建模**：场景数量多，单个场景迭代对整体收入贡献较小，需统一建模提升迭代效率，重点关注整体场景收益
- **以 User 为主**：缺少用户强兴趣显式表达，仅部分场景有弱兴趣 Context（YMAL 的 PDP 主宝贝、Cart_Unify 的购物车 items 等）
- **泛化性和重定向性双要求**：既要能满足优化用户兴趣（重定向），也要能让用户"逛"起来（泛化）
- **需与后链路排序目标对齐**：召回既要综合考虑用户兴趣、广告主诉求，又要和后续链路的排序目标保持一致

##### 2.1.3.1.2 设计思路/Design Philosophy

Discovery Ads Recall 算法建模需具备以下特性：

- 多场景统一建模能力，兼容不同场景间差异性
- 兼容重定向和泛化性需求
- 可学习后链路目标，对齐后链路排序
- 各模块保持独立性同时为其他模块提供复用性结果

算法框架从逻辑上拆分为 UserUnderstanding、Recall Queues 和其他模块（如 Tag Service、Zigzag 合并等）三部分。

##### 2.1.3.1.3 用户理解/UserUnderstanding

UserUnderstanding 模块负责围绕 User 结合 Context Info 产出 User 2 Tag 信息（Tag 泛指用户的兴趣意图理解），包括：


| 组件             | 状态  | 说明                                 |
| -------------- | --- | ---------------------------------- |
| User Embedding | 已具备 | 模型化的 UserEmbedding 表达，供后链路复用       |
| 相似 User        | 建设中 | 建模用户的相似群体 U2U                      |
| Interest Cates | 规划中 | 用户粗粒度兴趣类目，用于泛化召回或后链路特征             |
| 历史高频 item      | 规划中 | 用户高频历史兴趣，用作 Recall Trigger 或用户画像特征 |


各场景的 Context Info：


| 场景         | Context Info          |
| ---------- | --------------------- |
| DD         | 无                     |
| YMAL       | PDP 主宝贝               |
| Cart_Unify | 购物车中已加购/购买的 item list |
| Game       | 无                     |

##### 2.1.3.1.4 召回队列/Recall Queues

Discovery Ads Recall 主要包含 4 种类型的召回队列：

###### 2.1.3.1.4.1 U2I2I（协同过滤-实时兴趣）/U2I2I (Collaborative Filtering — Real-time Interests)

基于"用户感兴趣的 item 的相似 item 也是用户感兴趣的"这一朴素假设，分两步实现：

**Step 1 - Trigger 选取**（U2I 部分）：从用户历史行为序列中选取 Trigger item


| 场景         | Trigger                  |
| ---------- | ------------------------ |
| DD         | 用户历史行为序列                 |
| YMAL       | 用户历史行为序列 + PDP 主宝贝       |
| Cart_Unify | 用户历史行为序列 + 购物车 item list |
| Game       | 用户历史行为序列                 |


Trigger 选取的考虑因素：

- **长短期兴趣结合**（规划中）：优先选择用户最近交互物品（不同行为权重有差异），同时兼顾高频交互物品（长期偏好，如复购商品），可基于 UserUnderstanding 的 User2Tag（high frequent items）结果作为 Trigger
- **多样性控制**（规划中）：避免 Trigger 过于集中在同一类别，尽量做到 Trigger 的多样性

**Step 2 - 相似 item 扩展**（I2I 部分）：两种度量方案：

**方案 A：统计协同过滤（ItemCF）**

基本思想：如果两个 item 被很多个用户同时点击（或其他行为），可以近似认为这两个 item 具备高度的相似性。

计算方法示例：假设存在如下行为矩阵：


| 用户  | 葡萄  | 苹果  | 水杯  |
| --- | --- | --- | --- |
| A   | 1   | 1   | 0   |
| B   | 0   | 1   | 0   |
| C   | 0   | 1   | 0   |


将每个 item 向量化表达（葡萄=[1,0,0]，苹果=[1,1,1]），计算余弦相似度： `cos(葡萄, 苹果) = 1 / (√1 × √3) ≈ 0.577`。通过此方法计算所有 item 的 N×N 相似度矩阵，写入 Cache 供线上读取。

其他变种思路：业界基于 ItemCF 围绕 Trigger 选取和相似度度量方法有进一步改进，其中比较经典的是 [Swing 算法](https://www.cjh.zone/blog/recall-swing/)。

优缺点：计算简单、依赖少，但因强依赖 User-Item 历史行为，泛化性较差，对新品/冷启等不友好。

**方案 B：深度模型 Embedding**

直接使用模型产出的 Item Embedding 计算余弦相似度。需要前置依赖模型的 Embedding 输出结果，前置计算略复杂，但泛化性好，对新品/冷启/兴趣破圈友好。

###### 2.1.3.1.4.2 OnlineU2I（实时兴趣模型）/OnlineU2I (Real-time Interest Model)

引入深度**双塔模型（Dual-Tower）**解决协同过滤的冷启动、稀疏数据、多模态融合等问题：

**模型特点：**

- **场景复用**：将 YMAL 和 DD 所有 Region 数据整合，通过统一兴趣模型（One Model Serve All）提升效率和泛化能力
- **目标复用**： LTR 同时对齐后链路目标（order/click/impression）和用户兴趣，全空间序： order > click > impression > un-impression > random
- **产出复用**：同时输出 User Embedding 和 Item Embedding，供 UserUnderstanding 模块和其他召回通路复用

**特征：**

- User 侧：用户基础属性（年龄/性别/职业）、用户实时行为序列（点击/购买/加购）、上下文特征（地理位置/时间）
- Item 侧：基础属性（ID/类别/价格）、统计特征（CTR/CVR）、多模态特征（title/picture embeddings）
- Context： scene id 和 region id，用于在统一模型内区分不同场景

**样本策略**：多目标 point-wise 学习，正负样本按以下全空间序构造：


| 目标            | 正样本条件      | 负样本条件           |
| ------------- | ---------- | --------------- |
| Order         | 有 order 行为 | 无 order（含其他行为）  |
| Click         | 有 click 行为 | 有曝光无 click      |
| Impression    | 有曝光        | 有 un-impression |
| Un-impression | 有候选未曝光     | random 样本       |


**Loss 函数**：要对齐的目标包括 order、click、impression、un-impression 以及 random。使用 batch 内负采样实现 random 目标，对其他目标 random 均为负样本。对每个目标依据样本的 label 采用 point-wise 方式学习，多目标融合形成最终目标。Loss 中引入温度系数 τ 控制概率分布的平滑度；对每个目标，正样本数量 N 用于放大预测概率（ `min(p × N, 1)`），使得已被高概率预测的样本不再产生梯度回传，避免过度优化。

**模型结构**： User 塔和 Item 塔结构基本一致。模型内通过 scene id 和 region id 路由不同的子网络，学习共享参数和场景独特参数。通过此模型，可同时得到 Item Embedding 和 User Embedding。后续在此模型基础上，持续迭代对比学习、多目标学习、多模态学习等技术方向，提高模型的表达精度。

###### 2.1.3.1.4.3 Offline U2I（兴趣分层召回）/Offline U2I (Layered Interest Recall)

弥补 Online U2I 在数据范围和计算复杂度方面的限制：


| 维度    | Online U2I           | Offline U2I    |
| ----- | -------------------- | -------------- |
| 数据范围  | 短期会话数据（最近 10-50 次交互） | 数月乃至数年历史行为     |
| 计算复杂度 | 受低延迟要求限制，轻量级模型       | 可用更复杂模型和精细特征工程 |
| 更新频率  | 实时（毫秒级）              | 周期性（天级）更新      |


按类目将长期兴趣拆分为 **11 个兴趣点**，构建多头 Tower（11 个 UserEmbedding），各兴趣点独立计算 TopK，最终通过 zigzag merge 汇总得到 Top500。

###### 2.1.3.1.4.4 人群兴趣-U2U2I/Crowd Interest — U2U2I

前文介绍的多种召回方式主要依赖目标用户与商品的直接交互（如点击、加购、下单等），这在一定程度上限制了召回集合的覆盖率和多样性，尤其在用户行为稀疏或新用户较多的场景下问题更加明显。U2U2I 沿着 U2I2I（协同过滤）的思路，将 Trigger 升级为 User，即变成了 U2U2I。

**算法思路**：基于用户画像或行为相似度，找到与目标用户相似的一组用户，然后利用这些相似用户的历史行为记录来召回相关商品。一方面能够显著扩充召回集合，提升推荐的多样性和覆盖率；另一方面也能有效缓解冷启动问题，帮助缺乏行为数据的新用户获得更精准的推荐。

**方案设计**： U2U2I 的召回方案主要包括 U2U 和 U2I 两部分。

**U2U（相似用户查找）**：通过计算 user embedding（基于 Online U2I 模型 user 塔产出）来获取和目标 user 相似的用户集合。由于全量 User 集合太大（亿级别），需要通过策略定义一批活跃用户作为 user candidate，这些活跃用户需尽可能满足：

- 用户最近 N 天有一定量的行为（点击/加购/购买）
- 用户交互行为较多，能够满足后续 U2I 召回
- 用户交互广告品类不单一，以满足召回的多样性

**U2I（用户兴趣扩展）**：关注用户与物品之间的交互（购买记录、点击行为等），根据相似用户的历史行为预测其对未接触物品的兴趣，通过把这部分 Item 扩展给目标 User 达到 U2U2I 的目标。

**在线架构**：当用户请求 U2U2I 服务时， Online U2I 模型的 User 塔会计算当前 User 的 embedding，并把结果传入到 Vespa。Vespa 中存储着活跃 candidate 用户的 user embedding，通过 KNN 计算目标用户和 candidate 用户的内积来选取 TopK 相似 User。最终把相似 User 的过滤后的点击或下单序列推荐给目标 User，完成 U2U2I 的一次完整召回。

#### 2.1.3.2 Search Item Ads 召回算法/Search Item Ads Recall Algorithm

##### 2.1.3.2.1 场景特性/Scenario Characteristics

Search Ads 以 Query 为核心，主要特征：

- Query 是用户的**显式兴趣表达**，召回结果必须与 Query 强相关
- 需同时具备**文本层面的精准匹配**和**语义层面的强/弱相关扩展**，提高 Query 供给丰富度
- Query 信息贯穿 Recall/Prerank/Rank 全链路，召回需综合考虑用户兴趣和广告主诉求表达

##### 2.1.3.2.2 设计思路/Design Philosophy

- 具备对 Query 的统一理解能力（QueryUnderstanding）
- 基于 Query 理解，完成文本层面的精准 item 匹配和语义层面的强/弱相关 item 扩展
- 模型化召回学习后链路目标，对齐后链路排序
- 各模块保持独立性同时提供复用性结果

算法框架逻辑上拆分为 QueryUnderstanding、Recall Queues 和其他模块（如 Relevance、Zigzag 合并等）三部分。

##### 2.1.3.2.3 QueryUnderstanding 模块/QueryUnderstanding Module

QueryUnderstanding 负责对原始 Query 建模，主要功能：

- **QueryRewrite**：拼写纠错及 Query 改写，改写到高相关、语义相近的 Query
  - 例：错误输入"沙漠连衣裙"→ 改写为"沙滩连衣裙"；"沙滩连衣裙"→ 改写为"海滩连衣裙"
- **QueryExtend（Query 2 UnifyQuery）**：在考虑相关性基础上增加 Query 多样性，将原始 Query 扩展为 UnifyQuery
  - 例："沙滩连衣裙"→ 扩展为"连衣裙"、"夏天连衣裙"等
- **Query2Tag**：对 RawQuery、QueryRewrite、QueryExtend 结果做 Tag 分解，供后续文本匹配召回使用


| 来源           | 输入    | Search Query Tag 举例 |
| ------------ | ----- | ------------------- |
| RawQuery     | 沙滩连衣裙 | [沙滩, 连衣裙, 女性]       |
| QueryRewrite | 海滩连衣裙 | [海滩, 连衣裙, 女性]       |
| QueryExtend  | 夏日裙装  | [夏天, 裙装, 女性]        |


**实现和 MText 集成。** 在线 Search Recall 里的 QueryUnderstanding 不是单个本地规则函数，而是由 Recall Graph、Feature Server、QueryRewrite 服务和 MText 服务串起来的聚合结果：

| 层次 | 代码/配置入口 | 关键逻辑 |
| --- | --- | --- |
| Search Recall DAG | `graph-manager-conf/retrieval/search_recall.yaml` | `FetchQueryFeatures` 先取 query 特征，`GetQueryUnderstanding` 再产出 `QueryUnderstand`；后续 `QT2I_611020304`、Redis Q2I、FSE Q2I、KNN Q2I、`BizTagCalculateOp` 等节点都消费这份统一的 QueryUnderstanding 结果。 |
| Recall 调 Feature Server | `paidads-recall/pkg/retrieval/service/fetch_query_features_op.go` | `FetchQueryFeaturesOp` 以 `Country / RequestId / Query / WebLabConfStr / UserId / EntranceGroup` 调 Feature Server，`Modules` 固定请求 `Mtext` 和 `QueryRewrite`，`FetchMode` 为 `CALC_WHEN_FAIL`。 |
| Feature Server DAG | `graph-manager-conf/featureserver/feature.yaml`、`feature-server/config/live.yml` | `QueryAdapter` 解析原始 query；`TextProc` 产出 `QuerySlice / QueryHash`；`QueryRewrite` 产出 `Queries / Scores / Models / Extras`；`Mtext` 产出 `MtextQuery / RewrittenQueries / TokensExp`。 |
| QueryRewrite / QueryExtend / Query2Tag | `feature-server/pkg/operator/query_rewrite.go` | 当 AB `EnableQueryUnderstand` 打开时，`QueryRewriteOp` 调 `deep.paidads.query_rewrite.query_understand`，请求里带 `QueryExtendNum`、extend/rewrite 的 redis version、model version、threshold 等参数；响应的 `EntityList` 会被拆成 query、score、source/model 和 `extra`。`extra` 中的 `tag_info` 是 Query2Tag 结果。 |
| MText | `feature-server/pkg/operator/mtext_op.go` | `MtextOp` 把 raw query 和 rewritten queries 合成 batch，调用 `paidads.search_ads.mtext.proc_query` 获得 tokens、phrases、common tokens，并额外调用 `proc_intonation` 产出 `TokensExp`。raw query 的 common tokens join 后是 `MtextQuery`；每个 rewrite/extend query 也有对应的 MText 结果。 |
| Recall 侧组装 | `paidads-recall/pkg/retrieval/service/get_query_understanding_op.go` | `GetQueryUnderstandingOp` 校验 `RewrittenQueries / TagInfos / MtextRewrittenQueries / RewrittenQueryModels / RewrittenQueryScores` 长度一致后，将每个 query 包装成 `recall_data.ContextData`：`model=raw` 标为 `raw`；命中 rewrite version/model 标为 `rewrite`；命中 extend version/model 标为 `extend`。每条数据额外带 `tag_info`、`mtext`、`model`、`mtext_query=CommonTokens join(" ")`，raw/首个同 raw 的 rewrite 还会带 `exact_query_tokens`。 |

字段语义上要区分三层 query：`RequestHeader.query` / recall request query 是用户原始搜索词；Feature Server 的 `MtextQuery` 或 `ContextData.extra["mtext_query"]` 是 MText common tokens 拼接后的标准化文本；`recall_log.query_text_proc` 是召回内部处理后的搜索词，可能包含 tokenize、重排、MText 等处理，主要用于匹配广告。做 case 排查时，原始意图看 `query`，匹配链路看 `mtext_query`、`exact_query_tokens` 和 `query_text_proc`。

特征来源可以按“线上消费字段”和“MFP/FSE 逻辑表”两层理解：

| 侧别 | 线上消费字段 | MFP/FSE 来源口径 |
| --- | --- | --- |
| Query 特征 | Recall 直接消费 Feature Server 聚合后的 `QueryRewrite.{Queries,Scores,Models,Extras}` 和 `Mtext.{MtextQuery,RewrittenQueries,TokensExp}`；`Extras.tag_info` 是 Query2Tag 的结构化标签。 | MFP feature table `6724` 属于 Query 侧平台特征口径；代码里通常不写 table id，而是通过 Feature Server / QueryRewrite 服务拿聚合结果。排查表源时优先用 FSE 平台按 table id 或 query 侧表名反查。 |
| User 特征 | Search Recall DAG 中 `FetchUserFeature -> UserFeatureContext` 产出用户理解结果，后续用于 BizTag、过滤/重排辅助等。 | 当前 Feature Server 配置中 `UserUnderstanding` 通过 `FseFetchUserFeatureOp` 读取 `ads/user_understanding_feature_table`，主键为 `grass_region, user_id`，输出 `UserTag`；MFP feature table `5560` 可按该逻辑表在 FSE 平台核对。`UserCTR` 另读 `ads/paidads_scoring_feature_category_userctrv2_v2`，主键 `country, user_id`，输出 `Click / Impression / Click14D`。 |

OhMyEmb 侧也会复用 MText，但用途不同：`ohmyemb/online_query_user.yaml` 和 `offline_query_user.yaml` 先用 `MTextOp[string]` 生成 `QueryMText`，再送入 SPM/FastText/EGO；Query rewrite/extend 的 Vespa 表 `knn_qrwt` 以 `QueryMText` 作为 key。因此，QueryUnderstanding 在线结果解决“raw/rewrite/extend/tag/mtext 如何喂给召回队列”，OhMyEmb 的 MText 解决“query embedding/index key 如何与离线索引一致”。

排查顺序建议：先看 `FetchQueryFeatures:Result` 是否包含 `Mtext` 与 `QueryRewrite` 两个 module，再看 `GetQueryUnderstanding:QueryUnderstand` 是否有 raw/rewrite/extend 三类 seed；若为空，检查 AB `EnableQueryUnderstand`、rewrite/extend version 和 threshold、Feature Server `get_feature` 错误、MText `proc_query/proc_intonation` 超时或长度不一致日志。若是文本匹配漏召，再继续看 `QT2I_611020304` 的 `qt2iCfg611020304`、`sa_text_match_recall` 的 tag 字段命中、`query_text_proc` / `exact_query_tokens` 与离线 item tag 是否一致。

**QueryRewrite 详细方案**

对于搜索词，分为**常见搜索词**和**长尾搜索词**两类分别处理：

- **常见搜索词**：频繁出现的 Query，可通过离线缓存提前计算 QueryRewrite 结果，降低在线计算压力，并可使用更复杂的模型构建更精准的结果。改写方法包括：
  - **Swing/CF 改写**：平均生成 9.9 个改写词，新召回广告内容差异 51.34%
  - **同义词替代（gpt-4o-mini）**：对所有搜索量 >5 的词进行改写
  - **LLM 改写（Qwen2-7B）**：经过调整后平均生成 7.48 个改写词，新召回广告内容差异 62.95%
- **长尾搜索词**：冷门 Query，在离线无法提前预知，只能在线**实时调用 LLM** 生成相关的改写结果
- **Case 示例**：原始 Query "Kaos oversize motif"（带图案的宽松 T 恤）的改写结果包括 "Kaos oversize"（宽松 T 恤）、"Kaos oversize murah"（便宜的宽松 T 恤）、"Oversize wanita"（女款宽松版）等

**QueryExtend（Query 2 UnifyQuery）详细方案**

此模块在 Org Search 无独立模块，和 QueryRewrite 功能二合一。考虑到 Org 迭代的不确定性以及建模目标的差异性（Org 侧面向高相关、相似的 Query）， Ads 选择自建。

- **常见搜索词**：
  - 一、利用 QIR（Query-Item Relevance）打分判断 Query1-Item1 相关且 Query2-Item1 弱相关，则 Query1-Query2 为弱相关
  - 二、对每个常见搜索词大量生成关联搜索词
  - 三、生成候选集并利用 QIR 评分，进一步分析每个搜索词贡献的平均 eCPM 来筛选弱相关搜索词
  - 四、最后刷到线上缓存
- **长尾搜索词**：
  - 一、基于常见搜索词的结果构建训练数据集
  - 二、利用双塔 Transformer 架构训练 Query 对弱相关改写词的召回能力
  - 三、筛选改写范围，对索引中的词使用 K-means cluster，取最靠近每个 cluster 中心点的样本作为最终 Query

**Query Tag（属性 Tag）方案**

Query Tag 模块本质是语义的中间表示层，通过将 Query 和 Item 映射到同一 Tag 空间，解决文本匹配中的词汇鸿沟问题：

- **语义抽象和标准化**： Query 侧将搜索词（如"便宜耐用的蓝牙耳机"）转化为结构化标签（如[性价比, 蓝牙耳机, 耐用]）； Item 侧解析标题生成同维度标签，实现文本信息标准化
- **匹配效率优化**：将文本匹配转化为 Tag 之间的高效计算（交集、相似度），支持不同粒度的 Tag（品类"手机" vs 属性"大电池"）
- **意图和场景扩展**：通过 Tag 关联 Query 未明确表达的隐含需求（如"学生电脑"→[轻薄, 平价, 办公]），对低频/复杂 Query 通过泛化 Tag 匹配到相关 Item
- **业务逻辑融合**：支持人工规则干预（如广告主指定 keyword/Tag），可结合图像、类目等非文本信息生成复合 Tag

Tag 的来源包括： Query 自身的分词结果、广告主的 keyword、hotquery、LLM 模型预测出的 Query/Tag 等。

##### 2.1.3.2.4 召回队列/Recall Queues

Search Ads Recall 主要包含 3 种类型的召回队列：

###### 2.1.3.2.4.1 文本匹配（Query2Tag2Item）队列/Text Matching (Query2Tag2Item) Queue

通过分析用户 Query 与广告文本特征的相关性，从海量广告库中快速筛选与用户意图相关的候选广告：

- **离线阶段**：对广告文本（标题、描述、bidding keyword 等）预处理（去除特殊符号、去停用词、分词、规范化），构建从词项（term）到广告的倒排索引
- **在线阶段**：基于 QueryUnderstanding 产出的 Tag，从倒排索引中检索匹配候选
- 匹配对象：用户 Query 与广告绑定的 bidding keyword，或 Query 与广告商品文本特征（商品名/品牌/类别名）

常见的匹配类型：

- **精确匹配（Exact Match）**：广告仅在用户查询与广告特征文本完全一致时返回
- **短语匹配（Phrase Match）**：广告在用户查询包含广告特征文本的完整短语时展示
- **广泛匹配（Broad Match）**：广告在用户查询与广告特征文本语义相关时展示，即使不完全匹配

以精确匹配为例，对用户 Query"手机支架"的查询过程： Query 处理结果 → ["手机", "支架"] → 查找对应广告列表 → 取列表交集 → 按业务需求过滤（预算/投放条件等）→ 排序截断返回结果

###### 2.1.3.2.4.2 语义匹配（Online Query2Item）队列/Semantic Matching (Online Query2Item) Queue

基于深度语义模型实现 Query 与 Item 的语义层面匹配，覆盖文本匹配无法触达的语义相关广告。在 Search Recall 阶段需同时考虑三个主要目标：

- 召回能够对全空间进行建模，具备一定的泛化能力
- 召回的目标和后链路的一致性
- 召回的结果和 Query 存在一定的相关性

**模型思路**：双塔模型， Query 塔和 Item 塔分别编码，通过 ANN（近似最近邻）检索计算向量相似度。同一个向量同时兼顾了 LTR（Learning to Rank，对齐后链路目标）和相关性建模两个目标。

**特征**：

- User 侧：用户基础属性（年龄/性别/职业）、用户行为序列（点击/购买/加购，仅使用 title 等文本信息）、上下文特征（地理位置/时间）
- Item 侧：基础属性（ID/类别/价格）、统计特征（CTR/CVR）、多模态特征（title/picture embeddings）

**样本策略**：通过学习全空间的序来提升链路一致性： `order > click > impression > un-impression > (relevance) > random`

**Loss 函数**：在 LTR 目标的基础上，同步训练 Relevance 模型，用于对弱 Relevance 的数据进行过滤。对过滤后的样本，每个目标依据 label 采用 point-wise 方式学习，最终 Loss = 多目标融合 Loss + Relevance Loss。

###### 2.1.3.2.4.3 直投队列（Query2Item 队列）/Direct Placement Queue (Query2Item Queue)

基于后验统计建立 Query-Item 历史高转化映射：

- 通过历史转化数据直接建立 Query-Item 对应关系，作为精准直投候选
- 可分析每个 Search Term 贡献的平均 eCPM，进行弱相关搜索词过滤

### 2.1.4 非商品卡流量广告召回/Non-Product Card Traffic Ad Recall

#### 2.1.4.1 暗投 vs 明投/Explicit Placement vs. Implicit Placement

广告投放分为**明投（Mingtou）**和**暗投（Antou）**两种模式：


| 维度   | 明投（Mingtou）                          | 暗投（Antou）                            |
| ---- | ------------------------------------ | ------------------------------------ |
| 定义   | 广告主主动对特定内容/流量进行广告投放，广告主明确感知投放位置      | 预算过剩的广告供给，由平台投放在广告主未明确指定的其他流量场景      |
| 典型案例 | KOL/Seller 直接对 Video 或 Live 内容明投广告   | Product Ads 暗投到 Shop/Live/Video 流量入口 |
| 计费点  | CPM（Live/Video 明投）或 Click（Search 暗投） | 通常复用 Product Ads ROI2 出价和 Click 计费逻辑 |


各广告类型的投放链路对比：


| 广告类型             | 投放链路                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| Product Ads      | API0-3 完整链路（API0 召回&预排 → API1 Org Recall → API2 出价&策略 → API3 计费）           |
| Brand & Shop Ads | 投放链路完全由广告侧控制（Recall → Relevance Filter → Ranking → Rerank → Send），无 Org 混排 |
| Video Ads        | API0-3（API0 含暗投 1.0+明投 1.0+暗投 2.0+明投 2.0）；搜索场景 Video 通过换封形式实现              |
| Live Ads         | API0-3 完整链路；通过将 1.0 广告升级到 2.0 广告实现链路统一下线                                   |


#### 2.1.4.2 Shop 卡流量广告召回/Shop Card Traffic Ad Recall

核心目标：结合商品和店铺信息进行召回和排序，达到增加点击、转化的目标。

**召回架构**：构建了**基于 shop 下 item 的索引**和**广告-关键词（ads-kw）维度索引**两路，分别进行 item 召回和 shop 召回，召回后 merge 到 Shop+Item 维度：

- **Item 路径（Embedding 召回）**：基于 shop 下 item 的向量 Embedding，通过向量检索召回相关 Item
- **Keyword 路径（Term 匹配召回）**：先召回店铺购买的 kw，再以 kw 继续走 Term 匹配召回

**精排**： Shop Ads 的 pCTR 排序模型结合用户特征、Query 相关商品特征、Shop 下热门商品特征、Shop 相关特征、Query 特征，产出 Shop 和 Item 维度的打分结果。模型引入了针对 Candidate Item（Query 相关商品）和 Shop Top Item（Shop 下热门商品）的 Attention 模块，同时加入基于预训练大语言模型的 Embedding 模块，计算 Query 和商品的语义相关性。

#### 2.1.4.3 Video 卡流量广告召回/Video Card Traffic Ad Recall

核心目标：结合下挂商品和视频内容进行召回和排序，达到增加商品点击、转化、完播的目标。

**召回类型**： Video Ads 包含明投和暗投两种广告，召回策略各有差异：

**明投召回**（KOL/Seller 直接对 Video 投放）并行召回队列：


| 队列名                            | 策略                           | 类型       |
| ------------------------------ | ---------------------------- | -------- |
| pop_like/view/order/gmv_videos | 热门视频（按 like/浏览/order/gmv 排序） | 热门召回     |
| User2Item2Video                | 用户行为商品 → 相关视频                | 基于视频商品召回 |
| User2Item2Item2Video           | 用户行为商品 CF 相似商品 → 相关视频        | 基于视频商品召回 |
| User2Following2Video           | 用户 Follow 的 KOL 创作视频         | 基于创作者召回  |
| Country New Ads/Video          | 新广告/新视频冷启动                   | 冷启动      |


**暗投召回**：基于 U2I2I 召回暗投广告商品，通过商品-视频映射（I2V），将挂载商品的 Video 召回。向量召回（U2V）中明投和暗投链路有差异：明投直接基于 Video Embedding 召回，暗投通过商品向量中转。

**粗排**： Multi-Task 输出（CTR + LTR 特征），结合精排 CR 分数构建 LTR 特征，学习与精排 CR 的一致性。

**精排**：由 Organic 侧负责多目标打分：


| 目标        | 正样本                                                           | 负样本     |
| --------- | ------------------------------------------------------------- | ------- |
| 外流 CTR    | 外流点击                                                          | 外流曝光未点击 |
| Staytime  | 回归 Label（Video View 开始到结束的时间）                                 | —       |
| 电商/广告内流点击 | video_anchor_click、enhanced_card_click、atc_click、buynow_click | 各目标未点击  |
| 广告外流点击    | 复用原生外流 CTR                                                    | —       |
| 电商/广告转化   | 对应点击后转化， content OA / AdsOA 口径                                | 点击后未转化  |
| 内容互动      | like/follow/share 等各目标点击                                      | 各目标未点击  |


#### 2.1.4.4 Live 卡流量广告召回/Live Card Traffic Ad Recall

核心目标：结合商品和直播间进行召回和排序，达到增加商品点击、转化、直播间互动、停留时长的目标。

**召回架构**： Live Stream Ads 召回包含 **Item 路径**和 **Streamer 路径**两大方向：

- **Item 路径（U2x2Item）**：索引中结合当前直播间上播商品（bag）和直播间历史上播商品（hist），基于用户行为召回商品再映射到直播间
- **Streamer 路径**：基于用户行为过的类目和观看过的主播，匹配相似主播，召回相应直播间

Streamer 路径并行召回队列：


| 队列名                                 | 策略                   | 类型        |
| ----------------------------------- | -------------------- | --------- |
| POPULAR_CCU / POPULAR_LIKE          | 当前 CCU/Like 热门直播间召回  | 热门召回      |
| COLD_START / COLD_START_TARGET_ROI  | 冷启动队列                | 冷启动       |
| USER_VIEW_STREAMER / USER_FOLLOWING | 用户历史观看/Follow 主播召回   | 基于主播召回    |
| USER_CATEGORY                       | 用户行为类目召回主播           | 基于主播召回    |
| USER_STREAMER                       | 用户观看/follow 主播相似主播召回 | 基于主播召回    |
| USER_I2I_BAG / USER_I2I_HIST        | 用户行为召回实时/历史上播商品      | 基于直播间商品召回 |
| PDP_RECALL                          | PDP 专项召回             | 私域特殊召回    |


**粗排**：基于 MMoE 的 Multi-task 模型，综合输出直播间维度的 pCTR、pCR、pDeepView 打分。粗排后结合每个广告的 bid price 进行 eCPM 排序，返回 Top200 给 Org 做精排混排。

**精排**：由 Organic 侧负责多目标打分， Live 广告的 CVR 直接建模 View→Order（区别于 Video 广告的 Click 计费， Live 是 View/曝光 计费），内流广告转化用 AdsOA 口径，外流广告转化用外流 CTR × 内流广告转化建模。

**通用执行路径。** 各场景 DAG 有差异，但 Search / Discovery Product Ads 可以概括为：

```text
request / context / FSE feature
  -> request understanding 或 OhMyEmb embedding
  -> queue-specific recall op
  -> MergeRecallResultOp
  -> SearchAdsInfoFilterOp 或 RCMDAdsInfoFilterOp
  -> RcmdAdsDedupOp（仅 Discovery）
  -> SnakeMergeFilterOp
  -> BizTagCalculateOp
  -> PackRecallAdsResultOp
  -> SendRecallLogOp
  -> Prerank
```

因此，“模型召回到了”不等于“一定进入粗排”：候选可能被 AdsInfoFilter、Discovery 去重、SnakeMerge quota 截断或最终打包 / 日志阶段丢弃。

*G. Support / Cold-start（扶持与冷启兜底）*

冷启策略不是单独的一条全局分支，而是由扶持队列、非强个性化队列和 fallback 共同承担：

- Item 冷启：Search `611610102`、Discovery `623612102` 明确承担冷启广告扶持；前提仍是 item 已进入索引并具备基础可召回字段。
- 成熟广告扶持：Search `611610101`、Discovery `623612101` 面向成熟广告扶持，与冷启扶持队列一起补长尾供给。
- User 冷启：当用户长序列行为弱时，通常更多依赖 query / item 驱动队列、扶持队列和 fallback；KB 当前没有单独沉淀一套 user cold-start 专用分支。
- Query 冷启：QT2I、LLM Q2I、Realtime Popular Q2I 等非强个性化队列承担部分兜底；这是基于队列用途的解释，实际策略仍以对应 graph / AB 为准。

**通用流程（所有检索类型共享）。** 各队列按各自的 op 并行执行互不依赖 → `MergeRecallResultOp` 合并 → `SearchAdsInfoFilterOp` / `RCMDAdsInfoFilterOp` 过滤 → `RcmdAdsDedupOp`（仅 Discovery）去重 → `SnakeMergeFilterOp` quota 截断 → `BizTagCalculateOp` → `PackRecallAdsResultOp` → `SendRecallLogOp` → Prerank。

**实时去重（仅 Discovery）。** `RcmdAdsDedupOp` 调用 `FilterShownRecallAds`（[ads_dedup_op.go](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/recommend/operator/ads_dedup_op.go)）：

| 条件 | 说明 |
|------|------|
| 开关 | AB `RecallAutofreshEnable` 且 Spex `CountryDedupTTLSec` 非空 |
| 逻辑 | 请求携带 `DedupItemList`（已曝光 item + 时间戳），对每个候选检查 `now - timestamp < TTL`，在 TTL 内的 item 被去重 |
| 视频特殊逻辑 | Video 入口按 `video_id` 而非 `item_id` 去重 |
| 保护机制 | 若去重会导致某队列所有候选被移除，则跳过该队列的去重 |
| Unpick Reason | `OfflineFilterRealtimeFilter` |

**SnakeMerge（quota 截断）。** `SnakeMergeFilterOp`（[snake_merge_filter_op.go](https://git.garena.com/shopee/deep/paidads-recall/-/blob/master/pkg/retrieval/common_operator/snake_merge_filter_op.go)）：

- 按 AB `MergeQueueQuota` 配额比例，各队列交替取出候选（Zigzag 方式）
- 按 AB `RecallPickedNum` 截断到最终 TopK
- 未被 pick 的候选记录 Unpick Reason
- 实际"优先级"由 merge 输入顺序、`MergeQueueQuota` 和 `RecallPickedNum` 共同决定，不是某个队列把自己的 TopK 直接塞进粗排。不同 region × entrance 的在线 quota 需要回 AB Test Platform 查生效配置。

*各队列 Target Quota 实时快照与查询。* `SnakeMergeFilterOp` 在运行时上报了每个队列实际分配到的 target quota 和 picked count，指标为 `paidads_retrieval_common_ads_queue_summary`，可在 Grafana 或 PromQL 中按 `queue_tag`、`country`、`entrance_group` 维度查询。查询示例：

```promql
-- 各队列分配到的 quota 上限
avg(paidads_retrieval_common_ads_queue_summary{component="snake_merge_queue_target_quota",country="ID",entrance_group="DD"}) by (queue_tag)

-- 各队列实际 picked 数量
avg(paidads_retrieval_common_ads_queue_summary{component="snake_merge_queue_picked_count",country="ID",entrance_group="DD"}) by (queue_tag)
```

**冷启策略。** Recall 没有单一的"冷启分支"，冷启覆盖分散在多种机制中：

- **Item 冷启**：Search 扶持队列 `611610102` 和 Discovery 扶持队列 `623612102` 专门面向冷启广告；新商品首先依赖索引可召回性（Ads Info / Indexer 写入 Vespa 后才可被检索）。
- **User 冷启**：没有专门的用户冷启分支，依赖 query / item 驱动的非个性化通路（QT2I 文本匹配、LLM Q2I、Realtime Popular）和 Fallback 兜底。
- **Query 冷启**：长尾 query 通过 QT2I 文本匹配（`611020304`）、LLM 离线 Q2I（`611030109`/`611030110`）和 Realtime Popular（`611030202`）等非强个性化通路覆盖，不依赖双塔模型的 query embedding。

*模型中的处理流程：*

```
原始 Slot (sparse ID emb, dim=16×N)
  ├── 标准 ID 部分 ──→ concat ──→ [B, seq, 64]
  └── Extra Emb 部分 ──→ ExtraFeatureAdapter(LayerNorm → Dense → Dropout) ──→ [B, seq, 48]
        ↓
     concat(ID part, Extra part) ──→ SharedItemDNN ──→ [B, seq, 64] (统一表示)
```

`ExtraFeatureAdapter` 对外部挂载的 dense embedding 做对齐：先 LayerNorm 归一化，再经一层 Dense(ReLU) 映射到目标维度，附加 Dropout 正则化。处理后与标准 ID embedding 拼接，送入 `SharedItemDNN` 瓶颈层（256→128→64）得到统一维度表示。该技术对 Target Item、PDP Item 和 Click Sequence 三个位置均应用相同的 Adapter + DNN 结构。仅验证用于 RCMD LongSeq DAG 1331/1332；PDP 双塔 DAG 1098/1099 不使用。

### 2.1.7 召回上线、评估和数据契约/Recall Launch, Evaluation, and Data Contracts

召回改动通常拆成三条相互依赖但可分开推进的线：模型配置、retrieval 队列配置、实验 / rollout 验收。源 KB 刻意沉淀 SOP 入口，而不是要求读者手工修改所有服务。

**上线流程。**

| 线条 | 首选入口 | 主要产出和门禁 |
|---|---|---|
| 新增 KNN 模型 | `ads-recall-ohmyemb-add-model` | 在 `graph-manager-conf/ohmyemb` 新增 `SimpleStandardURankerOp` 节点，校验 `node_name` 唯一性，把 YAML 转为 `model_conf`，用 `ads-recall-ohmyemb-debug` 测试，再提交代码 review。它不会自动更新 `oh-my-embedding` graph version、发布服务、检查 Redis/Vespa 或配置 AB 实验。 |
| 新增 KNN / KV 队列 | `ads-recall-add-queue` | 加载参考队列，预览 retrieval DAG / `MergeRecallQueue` / AB / Makefile 变更，更新 `graph-manager-conf/retrieval` 与 paidads-recall AB 配置，运行 ABTestConfig 校验和 RESP Lab preliminary test。生产 tag / release 仍由 owner 控制。 |
| AB 实验 | AB Test Platform / `sp-ab` | 对 `623012104`，Feature 为 `knnRecallCfg623012104`（Feature ID 3586），Scene 为 `paidads_universal`（ID 1361），Layer 为 `recall_u2i_longseq`（ID 175210）。配置按 region × entrance 维护。 |
| Rollout review | `ads-rollout-generate` | 生成或追加 rollout 文档，包含 project info、实验数据 tab、guardrail snapshot、核心指标 uplift 和 Recall metric。Monthly Uplift 公式为 `base_value × uplift% × (1 / experiment_traffic_ratio) × 30`。 |
| Feature launch | AB Feature Launch | Rollout 审批后选择 launch value 和 scope，按 region 放量，并确认关联实验已 Complete。 |

**Recall AB 实验设计和观察原则。** 实验单元、scene、region、entrance 和 traffic split 应按实验目的选择：Search 相关改动走 Search 场景，RCMD / Discovery 相关改动走 RCMD / DD / YMAL 等相关场景；通用召回模型或通用队列通常优先做全 region 实验，再按 `region × entrance` 观察分区效果。常见流量起点是每个桶 `10%`。Control / treatment 的流量隔离、互斥和命中由 AB Test Platform 处理，KB 只要求核对 Scene / Layer / Feature value 是否与目标队列、region、entrance 对齐。实验一般至少 `7` 天，依据 AB 报表和 `ads-rollout-generate` 判断关闭、更新或推全。上线前看离线 `offline_recall_rate / precision_at_100` 等候选覆盖指标；实验中看在线 Grafana、AB 实验报告和 Recall Rele Log Monitor / DataSuite 离线看板；推全后继续观察大盘整体数据，以及 EGO / URanker / OhMyEmb / Retrieval 等线上资源和依赖健康。

**Rollout guardrail 和 Monthly Uplift 准入表。** `ads-rollout-generate` 的 rollout 数据页固定包含 `Guardrail Summary` 和 `Overall Core Metric Uplift`。KB 不固化某天、某 region 的静态阈值；region 级阈值和 PASS / FAIL 结果以 AB Platform `Snapshot Detail` 页面为准，rollout 文档按国家逐行沉淀结论。

| 模块 | 必填指标 / 字段 | 粒度和来源 | 准入 / 处理规则 |
|---|---|---|---|
| Guardrail Summary | AB Snapshot Detail 中展示的所有 guardrail 指标；对 FAIL 指标记录 `metric name + change%` | 每个 rollout country 一张 snapshot；从 AB Platform `Snapshot Detail` 页面使用 `Save as Image` 导出 | `all pass` 可进入后续收益评审；若存在 FAIL，必须在 rollout doc 明确标红失败指标并补充人工解释。skill 不生成失败原因，不允许编造解释 |

**召回“低价值”判断和后链路截断。** 当前 KB 中没有一条可以直接套用到所有入口、所有召回队列的固定规则，例如“`pCTR < x`、`pCVR < y` 或 `ADVV < z` 就判定该 Recall 没价值”。需要把三类机制区分开：

| 层级 | 判断对象 | 是否是价值判断 | KB 中可观测字段 / 证据 |
|---|---|---:|---|
| 召回 / AdsInfoFilter | 广告是否可投、审核、预算、类目、相关性、频控等 | 否，主要是合法性 / 有效性 / 相关性过滤 | `reason`、`filter_stage`、`rele_score`、`recall_remove_reason` |
| Merge / quota | 队列保量、去重、SnakeMerge 截断 | 部分反映供给优先级，但不是 pCTR / pCVR / ADVV 阈值 | `queue_tag(s)`、`is_top`、`biz_tag`、各阶段 count |
| 粗排 / 精排 / MixRank / dispatch | 候选能否进入下一阶段并最终曝光 | 是，低价值候选通常表现为低分、低 eCPM、低预估 GMV 并被截断 | `prerank_score`、`rank_score`、`mixrank_score`、`prerank_pctr`、`rank_pctr`、`mixrank_pctr`、`prerank_pcr`、`rank_pcr`、`mixrank_pcr`、`rank_ecpm`、`mixrank_ecpm`、`rank_estimated_gmv`、`mixrank_estimated_gmv`、`final_stage` |

Product Ads 后链路可以在内部 KB 中看到精排侧公式，但粗排公式只在 KB 中描述了职责和日志字段，未展开完整模型结构和统一阈值。粗排阶段负责把召回候选快速截断到精排候选（当前上限约 400 个 item），`paidads_mart.dwd_trace_recall_log_di__reg_s0_live` 中可观测粗排 `pctr`、`pcr`、`ecpm_score` 和 `bid_price`；详细架构需查 `paidads-alg` 的 prerank 代码。少数垂类有场景级粗排 / 动态过滤公式，例如 Live Ads 预排会把 `pCTR`、`pCR`、`pCTCVR`、`eCPM`、`eGMV`、`pRank` 加权合成，Shop Ads 有动态 eCPM percentile threshold / `LOW_ECPM` 过滤原因，但这些不能泛化成 Ads Recall 的全局低价值阈值。

精排 / rerank 侧 KB 有明确的价值组合公式。Product Ads UniCR 先得到点击后价值：

```text
pGMV = item_price * sold_cnt_smoothed * CR_7d

value = direct_pcr_7d * cali_direct_pgmv_7d
      + shop_pcr_7d   * cali_shop_pgmv_7d

ecpm = pctr * value * target_cir
target_cir = 1 / targetROAS
```

在 ROI2 口径下也可以写成统一形式：

```text
eCPM = pCTR * pCVR * (pAOV / targetROAS) * lambda
```

Online-bidding 中 Product Ads rerank 是 10 阶段流水线：`rerankModel -> rerankPrepare -> rerankPlatformVoucher -> rerankVoucher -> rerankBidding -> rerankVoucherNew -> rerankCalculatePadvv -> rerankSubsidy -> rerankDeduction -> rerankFinalization`。其中 Model 阶段填充 `Pgmv`、`ModelPgmv`、`ModelBroadPcr`，Bidding 阶段填充 `CpcBid`、`TargetCir`、`BiddingData`、`BidArr`，统一 CPC bid 公式为：

```text
CpcBid = pGMV * targetCir * finalCoef
       = pGMV * targetCir * bidCoef * underBidCoef * modelCoef * manuelCoef
```

因此，“低 pCTR / 低 pCVR / 低 ADVV 的 Recall 没价值”更准确的解释是：低 `pCTR` 会压低点击概率乘子，低 `pCR / pCVR` 会压低转化价值，低 `pGMV / target_cir / finalCoef` 会压低 bid 或 eCPM；这些候选通常在 `prerank -> rank -> mixrank -> dispatch` 链路中排序靠后或被截断。`ADVV` 更多是后验评估 / 调控口径，诊断表中常按 CPA 类 `broad_gmv_amt_usd * target_cir`、其他定价类型按 `expenditure_amt_usd` 归一；对单次在线新候选，链路主要用预测 value / eCPM / bid 来排序，不应把后验 ADVV 误写成召回层硬过滤阈值。

如果要判断某一路 Recall 是否“没价值”，建议按队列 / 入口 / 国家做相对分析，而不是找全局阈值：先看 full link 表中该队列从 `is_recall` 到 `is_prerank / is_rank / is_mixrank / is_dispatch` 的阶段留存，再比较 `pctr / pcr / ecpm / estimated_gmv / score` 的分位数，最后关联 performance / tracking 看后验 `rev / advv / gmv / order / CTR / CVR / ROAS`。当一个队列长期表现为采纳低、独占低、阶段截断早、排序价值分位低且后验业务指标差，才可以在经营上判断为低价值召回。

**API0 / API1 透出数量和质量分析。** API0 / API1 的透出数量不在 KB 固化静态值。实时数量先看 [New Ads Engine Migrating Grafana](https://monitoring.infra.sz.shopee.io/grafana/d/MDjU0zPNk/new-ads-engine-migrating?orgId=39&var-entrance=SEARCH&var-country=ID) 中 API0 / API1 ads number 或 output size 面板；离线质量分析走 `srdi_mart.dwd_sr_data_warehouse_rcmd_unify_full_link_log_1h` 和 `srdi_mart.dwd_sr_data_warehouse_search_unify_full_link_log_1h`，用 full link 表的 `recall_type` 区分来源：API0 表示来自 Ads 链路，对应 `recall_type in (1, 3)`；API1 表示来自 Org 链路，对应 `recall_type in (2, 3)`。其中 `recall_type = 3` 同时属于 API0 和 API1，按 API 维度对比时应展开到两边分别统计，不要把 API0 + API1 简单相加当作去重总量。正式分析前先按当天数据跑 raw `recall_type` 分布校验，避免业务线新增枚举导致误分组。

```sql
    FROM srdi_mart.dwd_sr_data_warehouse_search_unify_full_link_log_1h
    CROSS JOIN params p
    WHERE regional_date = p.biz_date
      AND regional_hour = p.biz_hour
      AND country = p.target_country
      AND request_id IS NOT NULL
      AND item_id IS NOT NULL
      AND coalesce(ads_id, 0) > 0
      AND pmod(abs(xxhash64(request_id)), 1000000) < CAST(p.sample_rate * 1000000 AS BIGINT)

    UNION ALL

    SELECT
        'rcmd' AS source_scene,
        entrance AS entrance_name,
        country,
        regional_date,
        regional_hour,
        request_id,
        ads_id,
        item_id,
        recall_type,
        is_recall,
        is_prerank,
        is_rank,
        is_mixrank,
        is_dispatch,
        dispatch_position,
        prerank_score,
        rank_score,
        mixrank_score,
        prerank_pctr,
        rank_pctr,
        mixrank_pctr,
        prerank_pcr,
        rank_pcr,
        mixrank_pcr,
        rank_ecpm,
        mixrank_ecpm,
        rank_estimated_gmv,
        mixrank_estimated_gmv,
        final_stage
    FROM srdi_mart.dwd_sr_data_warehouse_rcmd_unify_full_link_log_1h
    CROSS JOIN params p
    WHERE regional_date = p.biz_date
      AND regional_hour = p.biz_hour
      AND country = p.target_country
      AND request_id IS NOT NULL
      AND item_id IS NOT NULL
      AND coalesce(ads_id, 0) > 0
      AND pmod(abs(xxhash64(request_id)), 1000000) < CAST(p.sample_rate * 1000000 AS BIGINT)
),
source_labeled AS (
    SELECT
        *,
        'API0_ADS_RECALL' AS api_source,
        CASE recall_type
            WHEN 1 THEN 'API0_ONLY'
            WHEN 3 THEN 'API0_AND_API1'
        END AS recall_type_name
    FROM base
    WHERE recall_type IN (1, 3)

    UNION ALL

    SELECT
        *,
        'API1_ORG_RECALL' AS api_source,
        CASE recall_type
            WHEN 2 THEN 'API1_ONLY'
            WHEN 3 THEN 'API0_AND_API1'
        END AS recall_type_name
    FROM base
    WHERE recall_type IN (2, 3)

    UNION ALL

    SELECT
        *,
        'UNMAPPED_RECALL_TYPE' AS api_source,
        concat('UNKNOWN_', cast(coalesce(recall_type, -1) AS varchar)) AS recall_type_name
    FROM base
    WHERE recall_type IS NULL OR recall_type NOT IN (1, 2, 3)
)
-- recall_type=3 会展开到 API0 和 API1 两行；比较 API0/API1 时可用，不能把两边简单相加当去重总量。
SELECT
    source_scene,
    entrance_name,
    api_source,
    recall_type,
    recall_type_name,
    count(DISTINCT request_id) AS request_cnt,
    count(*) AS candidate_item_rows,
    count(DISTINCT concat(request_id, '#', cast(item_id AS varchar))) AS uniq_req_item_cnt,
    count_if(is_recall) AS recall_item_cnt,
    count_if(is_prerank) AS prerank_item_cnt,
    count_if(is_rank) AS rank_item_cnt,
    count_if(is_mixrank) AS mixrank_item_cnt,
    count_if(is_dispatch) AS dispatch_item_cnt,
    count_if(is_dispatch) * 1.0000 / nullif(count(*), 0) AS dispatch_rate,
    avg(CASE WHEN is_dispatch THEN dispatch_position END) AS avg_dispatch_position,
    approx_percentile(CASE WHEN is_dispatch THEN dispatch_position END, 0.5) AS p50_dispatch_position,
    avg(coalesce(mixrank_score, rank_score, prerank_score)) AS avg_best_stage_score,
    avg(coalesce(mixrank_pctr, rank_pctr, prerank_pctr)) AS avg_pctr,
    avg(coalesce(mixrank_pcr, rank_pcr, prerank_pcr)) AS avg_pcr,
    avg(coalesce(mixrank_ecpm, rank_ecpm)) AS avg_ecpm,
    avg(coalesce(mixrank_estimated_gmv, rank_estimated_gmv)) AS avg_estimated_gmv
FROM source_labeled
GROUP BY 1, 2, 3, 4, 5
ORDER BY source_scene, entrance_name, api_source, recall_type;
```

*手动查询指引：*

- **查算法最近更新时间**：在线模型队列走 `queue → retrieval YAML → OhMyEmb 节点 → EGO serving / checkpoint → ready_at_time`，再看 DataSuite 训练任务最近成功时间；非 KNN 队列走 `queue → 任务等级表 / DataSuite workflow → 最近运行时间 → marker → Data Delivery sinker / version`。
- **查模型是否已发布到线上**：先用 Queue Registry / retrieval YAML 确认队列对应的 DataSuite 调度、AB key 和 OhMyEmb `model_name / service_name`，再读 DataSuite asset 的 `content` 中的 `model_name / model_version`，最后在 EGO 对比“最新 checkpoint”和“当前 serving checkpoint”。若最新 checkpoint 的 `related_serving` 已包含当前 serving，说明已发布；若最新 checkpoint 更新但 serving 仍指向旧 checkpoint，说明训练已产出但线上未切到新模型。该链路高度依赖队列文档中登记的 DataSuite / owner / queue 信息；若登记缺失或过期，只能先落到 graph / AB / EGO 层，不能直接给完整发布结论。
- **查召回算法耗时**：队列级总耗时看 [Retrieval Service](https://monitoring.infra.sz.shopee.io/grafana/d/9j91dj8Mz?orgId=39) / [Retrieval v3](https://monitoring.infra.sz.shopee.io/grafana/d/G66aGJ4Vk?orgId=39)；KNN 模型推理耗时看 Predictor / OnlinePS 面板；依赖侧耗时看 [Dependency Monitor](https://monitoring.infra.sz.shopee.io/grafana/d/zvx0F0yVk?orgId=39)。
- **查 EGO / URanker 集群利用率**：先按队列反查 `model_name / service_name`，再看 Predictor / OnlinePS 面板的 QPS / 延时 / 错误率。
- **查 ads item 是否进出索引**：查 `mp_paidads.ods_shopee_paidads_index_log`，按 `item_id / grass_date / placement / operation` 看索引事件；具体触发根因需到 Ads Info / Indexer 侧排查。

模型发布状态的最短判定流程：
1. `queue_id → Queue Registry / retrieval YAML`：拿到队列用途、DataSuite 调度链接、`required_output`、OhMyEmb 节点和 AB key。Queue Registry 中的登记信息是这条链路的起点；若未登记 DataSuite / workflow 链接，自动化只能先做代码和平台侧反查。
2. `queue_id → AB Feature`：KNN 队列通常按 `knnRecallCfg{queue_id}` 命名，可在 AB Platform Feature List 搜索队列号或 feature_key 拿到 `feature_id`；当前 `sp-ab search --keyword` 是实验搜索，不等价于 Feature List 搜索，拿到 `feature_id` 后再用 `sp-ab feature <feature_id>` / `feature-values` 导出详情。
3. `DataSuite asset → model_name / model_version`：若链接指向 workflow，用 `workflow/detail` 看子节点；若指向具体任务 / file，用 `file/detail` 看 `content`。DataSuite Cookie 可由 `sra-ds-sql-query` 读取；不应只用无 Cookie `curl` 页面壳。
4. `EGO serving → 当前线上 checkpoint`：用 `service_name / model_name` 反查 online model、当前 version、`checkpoint_id`、`update_time`。
5. `EGO checkpoint → 最新训练产物`：按 offline `model_id / version_id` 拉 checkpoint 列表，比较最新 checkpoint 与当前 serving checkpoint。
6. 判定：两者一致或最新 checkpoint 的 `related_serving` 包含当前 serving = 已发布；训练最新 checkpoint 更新但 `related_serving` 为空且 serving 仍旧 = 未发布；队列是 Redis / FSE / QT2I / fallback 时，不应强行套 EGO，继续查 DataSuite / Data Delivery / FSE。

注意：这套发布状态链路目前对 KNN / OhMyEmb / EGO serving 型队列访问效果最好，尤其是 `KnnQ2IOp` / `KnnU2IOp` 这类有 `knnRecallCfg{queue_id}`、OhMyEmb 节点和 EGO checkpoint 的队列。共享 OhMyEmb 节点的多个队列只能先得到“模型节点级”的发布状态；`KnnU2UOp + GetFseU2IOp` 等混合链路只能用 EGO 判断第一阶段 embedding，新鲜度还要继续检查 FSE / Data Delivery 后半段。Redis / FSE / QT2I / fallback 等其他类型队列目前还缺少同等顺滑的一键链路，需要继续补队列文档、DataSuite / Data Delivery 权限和对应类型的自动化方案。

**Recall 日常健康最小检查集。**

- **供给层**：看各队列 recall 量、filter 后量、SnakeMerge 前后量、picked / final 候选数，以及 0 候选或异常掉量。
- **服务层**：看 Retrieval QPS、P99、错误率、队列级耗时。
- **依赖层**：看 Vespa / Redis / FSE / EGO / OhMyEmb 错误率、延时、cache hit、OhMyEmb `ready_at_time`。
- **效果层**：看 `ads_adopt_ratio`、adopt / exclusive、曝光 / 点击 / 下单、CTR / CVR、GMV、Rev、Advv。
- **最小面板组合**：Funnel、Queue Metrics、Retrieval Service、Dependency Monitor、Recall Rele Log Monitor。

**常见 Recall 诊断路径。** 源 sub-KB（§10.2.5）维护了 22 类常见问题的路由表，覆盖模型目标、样本构造、独占率 / 采纳率查询、队列配置反查、特征审计、quota 分配、更新频率、集群利用率、耗时分析、覆盖率统计、架构概览、DAG 链路、冷启策略、降级 / cache、离在线一致性等方面。路由原则：**KB 记录“怎么查、按什么口径解释”，不沉淀某个实验或某天的静态数值**；涉及实际数值时，必须带 `date / region / entrance / exp_id / queue_id` 重新跑 SQL 或看监控。

**单请求未召回 item 的 debug SOP 和工具缺口。** 当前 `auto-case-attribution` 是可依赖的请求级归因 skill：它已有 workflow gates、SQL playbook 和 Search / YMAL 归因报告样例，适合做批量 case 抽样、归因报告和队列级问题拆解。缺口在于它还没有覆盖“给定单个 `request_id + item_id`，一键解释 item X 为什么没有在该次请求中召回”的单点 debug 模式；这类 case 仍需要把 `op_debug_info`、recall log、index log、full-link 和后验表串起来做人工判断。正式建设目标是在 `auto-case-attribution` 中补 single-case debug mode，或新增伴随的 `ads-recall-case-debug` skill，把下方人工 SOP 自动化。

| 字段 | 是否必填 | 说明 |
|---|---:|---|

| `grass_region` | 必填 | 例如 `ID / SG / VN` |
| `scene / entrance / biz_type` | 必填 | Search / DD / YMAL / cart / game 等；决定查哪张 full-link 表和 recall `biz_type` |
| `request_id` | 必填 | 用于 recall log、full-link、tracking / performance 对齐 |
| `item_id` | 必填 | 目标 item X |
| `queue_id / queue_tag` | 强烈建议 | 没有队列时只能先做全队列扫描，结论会更粗 |
| `ads_id / shop_id / placement / pricing_type` | 可选 | 有助于区分一个 item 下多条广告、Shop Ads / Product Ads / Live Ads 形态 |
| `query / pdp_item_id / user_id / exp_id / ab_test_sign` | 可选 | Search 补 query；YMAL / PDP 补 `pdp_item_id`；实验 case 补 `exp_id` 或 `ab_test_sign` |

标准人工 SOP：

| Step | 要回答的问题 | 查什么 | 结论分流 |
|---:|---|---|---|
| 0 | case 信息是否完整、时间和场景是否对齐 | 输入字段、timezone、`scene -> biz_type / entrance` 映射 | 信息不完整时先补字段；不要跨 timezone 或跨 entrance 直接下结论 |
| 1 | item / ads 是否有线上供给资格 | `mp_paidads.ods_shopee_paidads_index_log`，必要时再查 AdsInfo / Quick Debug Bot | 若索引不存在、`visible=0`、`operation` 非 INDEX 或 `reason` 非空，优先归因为供给 / 索引 / AdsInfo 问题 |
| 2 | 这个 request 是否真的跑了目标召回链路 | 在线复现看 `op_debug_info`；历史 case 看 `paidads_mart.dwd_trace_recall_log_di__reg_s0_live` 的 request 级行、`ab_test_sign`、`queue_tag(s)`、`is_full_sample` | 若 request 没有目标队列行，查 AB、队列开关、降级、GraphManagerVersion、入口是否匹配 |
| 3 | item X 是否进入过召回候选 | recall log 按 `request_id + item_id` 查 `queue_tag(s)`、`reason`、`filter_stage`、`rele_score`、`pctr/pcr/ecpm_score`、`light_recall_rank`、`recall_rank` | 无行 = 没被任何记录到的队列产出；有行但 `reason` 非 picked = 被过滤；picked 但后面不见 = 继续查合并 / 后链路 |
| 4 | 如果队列没有产出，后端召回源为什么空 | KNN 查 `model_param_key / required_output / vespa_name / embedding_field / rank_profile / distance / limit / OhMyEmb ready_at_time`；Redis 查 `{model}:{source}:{country}:{seed}`；FSE 查 feature table key；Text/QT2I 查 QueryUnderstanding / MText / tag 字段；U2U2I 要拆 U2U 相似用户和 FSE U2I 两段 | 归因为覆盖问题、索引新鲜度、模型 embedding 缺失、Redis / FSE 数据缺失、query/tag/seed 不匹配或依赖异常 |
| 5 | 如果已产出，为什么没有进最终 recall response | `AdsInfoFilterOp`、`RcmdAdsDedupOp`、`SnakeMergeFilterOp`、`BizTagCalculateOp`、`PackRecallAdsResultOp`、recall log `reason/filter_stage/recall_rank` | 归因为 AdsInfoFilter、相关性、去重、quota / SnakeMerge 截断、保送 / biz_tag 或响应打包问题 |
| 6 | 如果 recall 已通过，是否死在后链路 | full-link 表看 `is_recall / is_prerank / is_rank / is_mixrank / is_dispatch`、`*_remove_reason`、`final_stage`、`dispatch_position`、`prerank/rank/mixrank` 分数 | 归因为 prerank / rank / mixrank / dispatch，而不是 recall 未召回 |
| 7 | 如果后验事件中看到 item，但链路日志看不到 | tracking / performance 表按 `request_id + item_id / ads_id + date + region` 对齐，检查 queue id、request id 归一化和采样 | 归因为数据链路、采样、tracking queue 丢失或 request id 口径不一致 |
| 8 | 输出归因结论 | 用固定 taxonomy 输出：`not_in_index`、`queue_not_run`、`backend_empty`、`not_generated`、`filtered`、`dedup_or_quota`、`downstream_drop`、`tracking_or_sampling_issue`、`insufficient_evidence` | 每个结论必须带证据字段、表名、分区和下一步 owner |

**配置反查指南（精要）。** 从已知线索出发反查完整配置信息的推荐路径：

| 已知线索 | 第一跳 | 后续路径 |
|---|---|---|
| `queue_id` / `queue_name` / `node name` | Queue Registry 查用途、PIC、DataSuite 链接；`graph-manager-conf/retrieval/*.yaml` 定位节点，判 `op` 类型 | KNN → AB Feature List 搜 `knnRecallCfg{queue_id}` → OhMyEmb → EGO → AFP；Redis/FSE → QueueParam → DataSuite / paidads-alg 离线产出；QT2I → qt2iCfg → Vespa 文本匹配 |
| `model_name` / EGO serving 名 | EGO Portal 查 serving 详情 → `online_model_name` / `checkpoint_id` | → `graph-manager-conf/ohmyemb/*.yaml` 按 `model_name` 反查节点名 → retrieval YAML 查引用队列 |
| 场景（Search / DD / YMAL / PP / Game / Shop / Live） | 按场景定位 graph 文件 | 看 `MergeRecallQueue` inputs 列出所有队列 → 逐个查上游节点 op |

关键原则：（1）队列文档 / Queue Registry 是从队列号串到 owner、DataSuite 和 workflow 的首选入口，登记缺失时要在结论里标明“只能查到 graph / 平台层”；（2）高频 op 的第一跳仍要回 graph，确认出现在哪张 YAML、前后连接哪些节点；（3）Redis / FSE / QT2I / Fallback 没有必要强行追 EGO / AFP，重点在 QueueParam / 离线产出 / Vespa rank_profile；（4）KNN 队列的完整路径才会稳定覆盖 AB + OhMyEmb + EGO + AFP + DataSuite，其他类型队列还需要继续补专门解决方案；（5）静态字段和 AB values 冲突时以 AB / 线上为准。
