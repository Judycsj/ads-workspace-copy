## 3.3 召回服务（Ads Recall）

Ads Recall 是 Shopee Paid Ads 的召回层，位于 ads-engine 或 prerank 与下游排序服务之间。它从 Vespa、Redis、ES、向量召回等多类路径获取广告候选，经过过滤、合并、去重、日志记录后返回最终候选集。

服务采用 Graph Engine 执行模式。每条召回路径都是 `graph-manager-conf/retrieval` DAG 中的一个 Operator，`paidads-recall` 会根据 `SPEX_SDU` 加载对应场景的 DAG。向量侧由 OhMyEmb 供给：OhMyEmb 计算 Embedding，写入 Redis，并通过 Indexer 同步到 Vespa。

| 模块 | 已实现行为 |
| --- | --- |
| 服务协议 | SPEX gRPC，包含 `search-retrieval` 和 `rcmd-retrieval` 两种部署形态。 |
| 图执行 | DAG 节点执行 KNN、Redis、Vespa 文本、ES、过滤、合并、打包等 Operator。 |
| 候选来源 | Vespa nearest-neighbor 召回、Redis 预计算 KV 召回、Vespa 文本召回、ES keyword 召回，以及场景专属 RPC 或策略召回。 |
| 过滤与合并 | `MergeRecallQueue`、`AdsInfoFilterOp`、`SnakeMergeFilterOp` 和场景过滤逻辑负责校验、合并、去重和截断。 |
| 运行时控制 | SPEX 动态配置、ABTestConfig 字段、降级级别、op cache 模式、Vespa 结果缓存、队列开关和队列 limit。 |
| 调试与可观测 | Kafka recall/query logs、`op_debug_info`、全链路去重 trace、Prometheus 漏斗指标和 Operator 延迟指标。 |

### 3.3.1 离线数据流和在线逻辑

Ads Recall 由离线队列准备、近线 Embedding 生产、在线 DAG 执行和运行时实验配置共同组成。离线链路准备 Redis KV 队列和向量索引；在线请求执行对应场景 DAG，并将多路召回候选合并为响应。

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 召回配置 | `graph-manager-conf/retrieval/*.yaml`、`GraphManagerVersion := recall_1.3.76` | 定义场景 DAG、节点、Operator 参数、输入输出和图版本。 |
| Embedding 供给 | `emb_service_trigger`、`emb_service_offline`、Redis、Indexer Kafka、Vespa | 为 KNN 召回生产 item/query/user/video/live Embedding。 |
| KV 供给 | 离线任务、cache syncer、Redis | 存储预计算 I2I/U2I/Q2I/U2U 和默认候选列表。 |
| 在线召回 | `paidads-recall`、Graph Engine、场景 handler | 执行召回 DAG 并向 ads-engine 或 prerank 返回候选。 |
| 实验与容灾 | SPEX config、ABTestConfig、`RetrievalDowngrade`、op cache、Vespa 结果缓存 | 控制队列开关、limit、Vespa 缓存模式和降级行为。 |

#### 3.3.1.1 离线数据流

离线数据准备主要分为两条链路。

向量召回由 OhMyEmb 准备 Embedding：

1. `emb_service_trigger` 从 Valar 读取全量和增量广告数据，从 Redis 扫描 Query/User 数据，并将 trigger 事件写入 item realtime、item batch、query/user realtime、query/user batch 等 Kafka topic。
2. `emb_service_offline` 消费 trigger，在需要时从 Valar 补全广告信息，执行 `offline_item`、`offline_query_user` 等 Graph Engine DAG，并通过模型和特征 Operator 计算 Embedding。
3. 离线服务将 Embedding 写入 Redis，key 形态为 `{country}:{table}:{field}:{key_value}`。典型 key 是 `SG:sa_q2i_knn_recall:embeddingv1:<ads_id>`，TTL 为 14 天并带最多 1 小时随机抖动。
4. 离线服务发送 Indexer Kafka 消息。Indexer 读取 Redis 并更新 `sa_q2i_knn_recall`、`dd_u2i_knn_recall`、`ymal_u2i_knn_recall`、`knn_qrwt`、`paidads_item`、`paidads_video`、`paidads_live`、`live_stream_ads` 等 Vespa table。

KV 召回由离线数据集预计算并导入 Redis。在线 Redis Operator 根据 seed 和队列配置读取这些列表，用于 I2I、U2I、Q2I、U2U、U2C、I2V、U2A 和默认队列等低成本召回路径。

对于图像 Embedding，Live 环境还支持一条独立链路：从 Kafka 消费图像特征并直接写入 Redis，不经过 DAG 计算链路。

OhMyEmb table/sinker 配置示例：

```yaml
table: sa_q2i_knn_recall
key:
  node: __TRIGGER__
  out: AdsID
fields:
  embeddingv1:
    data:
      node: sa_q2i_knn_recall@embeddingv1
      out: Embedding
    dim: 128
condition:
  type: ads
  enable_realtime: true
  enable_batch: true
enable_redis: "{{isLive}}"
enable_indexer: true
```

#### 3.3.1.2 在线逻辑

在线流量通过 SPEX gRPC 进入 `paidads-recall`。`server/retrieval/run.go` 根据 `SPEX_SDU` 选择服务形态和场景 handler。

| 部署形态 | SPEX SDU | 主要场景 | DAG 示例 |
| --- | --- | --- | --- |
| `search-retrieval` | `deep.paidads.recall.search` | Search Ads、图片搜索 | `search_recall.yaml`、`image_search_recall.yaml`。 |
| `rcmd-retrieval` | `paidads.discoveryretrieval`、`retrieval.videoads`、`retrieval.liveads`、`shopads.retrieval` | Discovery、YMAL、PP、Game、Video、Live、Shop | `recommend_dd.yaml`、`recommend_ymal.yaml`、`recommend_pp.yaml`、`recommend_game.yaml`、`video_ads_recall.yaml`、`live_ads_recall.yaml`、`shop_search_retrieval.yaml`。 |

实际线上 DAG 由 `graph-manager-conf/retrieval/*.yaml` 管理，`Makefile` 中 `GraphManagerVersion` 绑定具体版本。每个队列节点通常包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `queue_name` | 队列编号，用于标识队列在漏斗和日志中的身份 |
| `ab_param_key` | AB 参数键名，用于从 ABTestConfig 中读取队列开关和参数覆盖 |
| `model_param_key` | 模型参数键名，用于从 AB 配置中读取 model version、embedding 选择等运行时参数 |
| `vespa_name` | Vespa 索引名，结合 country 拼接为实际查询的 Vespa application（如 `sa_q2i_knn_recall_id0`） |
| `embedding_field` | Vespa embedding 字段名（如 `embeddingv1`、`embeddingv2`） |
| `rank_profile` | Vespa rank profile，与 `required_output` 一起决定查询时使用的排序表达式 |
| `required_output` | 子图名称，指定该队列依赖的上游 Embedding 子图输出 |
| `recall_limit` / `result_global_limit` | 单队列召回上限 |
| `downgrade_level` | 降级层级（L1/L2/L3/LM），统一降级触发时按此层级截断或关闭 |
| `placements` | 适用广告位列表 |
| `score_range` | 相似度分数有效区间 |
| `inputs` | 该节点依赖的上游节点 output 列表 |
| `outputs` | 该节点产出的 output 名称，下游 `MergeRecallResultOp` 需引用此 output |

**场景与 Op 映射：**

| Graph 文件 | KNN Op | Redis Op | 典型节点 |
| --- | --- | --- | --- |
| `search_recall.yaml` | `KnnQ2IOp` | `RedisQ2IOp` | `Q2I_KNN_611010104`、`Q2I_111030201` |
| `recommend_dd.yaml` | `KnnU2IOp`、`KnnU2UOp` | `RedisI2IOp`、`RedisU2IOp` | `U2I_KNN_623012108`、`U2I2I_622031201` |
| `recommend_ymal.yaml` / `recommend_pp.yaml` | 同 DD 主体 | 同 DD 主体 | 按场景复用推荐召回结构 |
| `recommend_game.yaml` | `KnnU2IOp`、`KnnU2UOp` | `RedisI2IOp`、`RedisU2IOp`、`RedisD2IOp` | `D2I_623932201` |
| `live_ads_recall.yaml` | `LiveKnnU2IOp`、`KnnU2LOp` | `RedisI2IOp`、`RedisU2AOp` | `U2I_KNN_653012101`、`Redis_U2A_653031202` |
| `video_ads_recall.yaml` | `KnnU2VOp`、`KnnU2I2V` | `RedisI2IOp`、`RedisI2VOp`、`RedisU2COp` | `U2V_MingTou_KNN_598770040`、`U2C_MingTou_70045` |
| `shop_search_retrieval.yaml` | `KnnQ2SOp`、`VespaBrandAds`、`VespaBrandMax` | — | `Q2S_KNN_677010101`、`FetchBrandMaxAdsOp`、`BrandmaxPostFilterOp` |

DAG 末端的 `MergeRecallResultOp` 会并行读取各队列 outputs，按 Label 拆分、队列内去重、应用 `DefaultLimit` 截断，输出 `QueueCollection`。新增队列时必须把新节点 output 加到 `MergeRecallResultOp.inputs`，否则不会进入最终返回。

通用请求流程：

1. 接收 ads-engine 或 prerank 发来的 SPEX gRPC 请求。
2. 通过 `config.GlobalConfig.RecallLimiter` 执行请求校验和限流。
3. 构建包含国家、入口、场景和 AB 参数的请求上下文。
4. 通过 Graph Engine 执行场景 DAG。
5. 并行或串行运行 KNN、Redis、Vespa 文本、ES 和场景专属 Operator。
6. 通过 `MergeRecallQueue` 合并各队列输出。
7. 通过 `AdsInfoFilterOp` 和场景业务过滤逻辑校验广告。
8. 通过 snake merge 去重和截断。
9. 打包结果，通过 `SendRecallLog` 发送召回日志，并返回 `RecallResponseV2`。

#### 3.3.1.3 系统通用逻辑

系统通用逻辑覆盖 Search、Discovery、Video、Live、Shop 等场景 DAG 共享的召回行为。这些能力不绑定某一种召回来源，而是为 KNN、KV、Vespa 文本、ES 和场景专属召回提供统一的执行、控制、过滤、缓存和响应打包框架。

##### 3.3.1.3.1 图编排与场景路由

`paidads-recall` 根据 `SPEX_SDU` 和场景上下文路由请求，并从 `graph-manager-conf/retrieval` 加载对应的 Graph Engine DAG。每个 DAG 由带有 args、inputs、outputs 的 Operator 组成，使多路召回可以并行或串行执行，并将队列输出交给后续 merge 和 filter 节点。

常见场景路由示例：

| 路由维度 | 示例 |
| --- | --- |
| 服务形态 | `search-retrieval`、`rcmd-retrieval` |
| SPEX SDU | `deep.paidads.recall.search`、`paidads.discoveryretrieval`、`retrieval.videoads`、`retrieval.liveads`、`shopads.retrieval` |
| DAG 配置 | `search_recall.yaml`、`recommend_dd.yaml`、`video_ads_recall.yaml`、`live_ads_recall.yaml`、`shop_search_retrieval.yaml` |

##### 3.3.1.3.2 运行时配置与降级

运行时配置通过 SPEX config 和 ABTestConfig 字段控制。通用队列参数包括 `queue_name`、`enable`、`ab_param_key`、`model_param_key`、`limit` 和 `downgrade_level`。AB 参数可以在不重新部署服务的情况下覆盖队列开关和 limit。

降级逻辑通过 retrieval downgrade 配置判断当前流量和服务状态下队列是否执行。当 `AdsEngineUseUnifiedDowngrade` 为 false 时，KNN Vespa 查询可以使用 `queryProfileForNoneDowngrade` 跳过 Vespa 侧降级逻辑，用于需要该行为的实验。

##### 3.3.1.3.3 候选过滤、合并与去重

召回队列返回候选 id 和来源信息，通用过滤与合并逻辑会在响应打包前校验候选。

| 功能 | 主要逻辑 |
| --- | --- |
| 候选合并 | `MergeRecallQueue` 合并多路召回队列输出，并保留队列和来源上下文。 |
| 广告校验 | `AdsInfoFilterOp` 和场景专属 filter 移除无效广告。 |
| 去重截断 | Snake merge 和去重逻辑移除重复候选，并按请求规模截断结果。 |
| Trace 传递 | 队列 tag 和 Operator metadata 会继续用于日志、debug payload 和观测。 |

##### 3.3.1.3.4 缓存与结果打包

通用缓存逻辑用于减少重复后端调用并稳定在线延迟。Operator cache 通过 `rw_mode` 控制，可取 `read_write`、`read_only`、`write_only` 和 `disable`。Vespa 结果缓存可以使用 Redis 做跨实例共享，也可以使用内存做实例内缓存。

合并和过滤完成后，服务将候选打包为 `RecallResponseV2`，附带下游排序所需的队列和来源信息，并通过 `SendRecallLog` 触发召回日志。

### 3.3.2 召回通道

Ads Recall 主要使用向量 KNN 召回和 KV 召回作为可复用召回通道。向量 KNN 召回依赖 OhMyEmb 生产的 Embedding，并从 Vespa 检索近邻候选；KV 召回从 Redis 读取预计算候选列表。

#### 3.3.2.1 向量 KNN 召回

向量 KNN 召回使用 seed Embedding 查询 Vespa nearest-neighbor 索引。在 `paidads-recall` 中，通用 `KnnX2YOp` 链路和场景专属 KNN Operator 会构造 Vespa ANN 请求、执行查询，并将返回 id 打包为召回候选。

##### 3.3.2.1.1 向量嵌入系统/OhMyEmb

OhMyEmb 是 Paid Ads 向量 KNN 召回使用的统一 Embedding 框架，负责计算和维护广告、商品、用户、搜索词、视频、直播等实体的 Embedding。它使用 Graph Engine 和 Graph Manager 的 `ohmyemb` service 执行 DAG，将离线 Embedding 写入 Redis，并通知 Indexer 同步到 Vespa。

| 服务 | 作用 |
| --- | --- |
| `emb_service_trigger` | 从 Valar 全量/增量广告数据和 Redis Query/User 扫描中生产 Kafka trigger。 |
| `emb_service_offline` | 消费 trigger，执行离线 DAG，写 Redis Embedding，并发送 Indexer Kafka 消息。 |
| `emb_service_online` | 提供 SPEX RPC `paidads.emb_service.get_embedding`，用于实时 Query/User Embedding 推理。 |

OhMyEmb 覆盖 Search Ads Q2I、DD U2I、YMAL U2I、视频明投/暗投、Live Ads、Union Item/Video/Live、Query Rewrite/Extend 和 User-to-User 场景。其图配置位于 `graph-manager-conf/ohmyemb/`，包括 `offline_item.yaml`、`offline_query_user.yaml`、`online_query_user.yaml` 和 `opdef.yaml`。

模型版本在 Graph Manager DAG 节点中通过 `model_name` 绑定；离线批次进度通过 Etcd 的 `ProcessingVersion` 和 `CompletedVersion` 跟踪，两者相等表示该批次写入完成。

| Operator | Seed | Target | 主要场景 |
| --- | --- | --- | --- |
| `KnnQ2IOp` | Query | Item | Search Ads Q2I 召回。 |
| `KnnU2IOp` | User | Item | Discovery、YMAL、PP、Game U2I 召回。 |
| `KnnU2UOp` | User | User | 相似用户召回，通常后接 user-to-item 扩展。 |
| `LiveKnnU2IOp` | User | Ad | 直播商品广告召回。 |
| `KnnU2LOp` | User | Live stream | 直播间召回。 |
| `KnnU2VOp` | User | Video | Video Ads U2V 召回。 |
| `KnnU2I2V` | User | Video through item | Video Ads user-to-item-to-video 召回。 |
| `KnnQ2SOp` | Query | Shop | Shop 搜索召回。 |

##### 3.3.2.1.2 离线数据流

KNN 离线链路为在线 nearest-neighbor 检索准备 Embedding 和 Vespa 索引。

1. `emb_service_trigger` 为 ads、query、user、video、live 等实体生产 trigger 消息。
2. `emb_service_offline` 消费 trigger，并执行国家过滤、lag 检查、trigger 拆分、pre-check、限速、ads-info 获取和 post-check。
3. Graph Engine 执行需要的离线 DAG 节点。当前模型 Operator 包括 `EgoPredictOp`、`SimpleMiniRankerOp`、`SimpleStandardURankerOp`、`FseFetchOp` 和 `MTextOp`。
4. Sinker 将 Embedding field 写入 Redis，并发送 Indexer Kafka 消息。
5. Indexer 更新 Vespa field，使 Embedding 可被在线召回查询。

Vespa table 示例：

| 场景 | Vespa Table | Key |
| --- | --- | --- |
| Search Ads Q2I | `sa_q2i_knn_recall` | `AdsID` |
| DD U2I | `dd_u2i_knn_recall` | `AdsID` |
| YMAL U2I | `ymal_u2i_knn_recall` | `AdsID` |
| Query rewrite/extend | `knn_qrwt` | `QueryMText` |
| User-to-user | `knn_u2u` | `UserID` |
| Union item | `paidads_item` | `ItemIDList` |
| Union video | `paidads_video` | `VideoID` |
| Union live | `paidads_live` | `AdsAccountID` |

BR、CO、CL、MX 等 US 国家可通过 `paidads.emb_service.redis_write` 将 Embedding 双写到 SG Redis，因为全量 Indexer 从 SG Redis 读取，而实时 Indexer 读取本地 Redis。

##### 3.3.2.1.3 在线召回

在线 KNN 召回有两条 Embedding 路径：

| 路径 | 行为 |
| --- | --- |
| 在线 Embedding 推理 | 当 Query/User Embedding 需要在请求时实时计算时，`paidads-recall` 调用 `paidads.emb_service.get_embedding`。`emb_service_online` 通过 `req_output_mapping` 解析 `dag_name` 和 `required_output`，执行所需子图，并直接返回 Embedding，不写 Redis 或 Indexer Kafka。 |
| Vespa nearest-neighbor 检索 | `KnnX2YOp` 或场景专属 KNN Operator 使用 seed embedding、`vespa_name`、`embedding_field`、`rank_profile` 和 `recall_limit` 查询 Vespa 并打包候选。 |

重要 KNN 配置字段：

| 配置字段 | 含义 |
| --- | --- |
| `queue_name` | 队列 id，用于监控、日志、降级判断和 merge 追踪。 |
| `ab_param_key` | ABTestConfig 字段，可覆盖动态队列参数。 |
| `model_param_key` | 模型参数选择器，用于 `vespa_name`、`rank_profile`、cluster 或 field 等设置。 |
| `vespa_name` | ANN 检索使用的 Vespa table 或 cluster。 |
| `embedding_field` | Vespa 中的 Embedding field，例如 `embeddingv1`、`embeddingv2`、`embeddingv3`。 |
| `rank_profile` | 与 Embedding field 配套的 Vespa rank profile。 |
| `required_output` | 获取 seed embedding 所需的 OhMyEmb output key 或 DAG 节点输出。 |
| `recall_limit` / `limit` | 每个 seed 或每个队列的候选数量上限。 |

KNN 队列配置示例：

```yaml
- name: U2I_KNN_623012108
  op: KnnU2IOp
  args:
    queue_name: 623012108
    enable: false
    ab_param_key: U2IKnn623012108Config
    model_param_key: knnRecallRcmdLTRModelCfg
    required_output: dd_knn_ltr_v1
    vespa_name: dd_u2i_knn_recall
    embedding_field: embeddingv2
    rank_profile: v2
    recall_limit: 500
```

**Vespa 索引管理口径：**

| 项 | 说明 |
| --- | --- |
| 索引命名 | Retrieval 侧按 `{vespa_name}_{country_lower}0` 访问 Vespa，例如 `sa_q2i_knn_recall`、`dd_u2i_knn_recall`、`ymal_u2i_knn_recall`、`live_stream_ads` 等 |
| 索引分类 | 广告侧 Vespa 索引按实体类型分为 4 大类：item（商品广告）、shop（店铺广告）、video（视频广告）、live（直播广告）。各类索引的 application/schema 元信息可通过 `/sp-vespa` skill 查 `project:PaidAds` 获取 |
| Schema / field | 由 Indexer / OhMyEmb 侧维护，KNN 字段通常来自 Embedding sinker 配置；召回 YAML 只引用 `vespa_name`、`embedding_field`、`rank_profile`、`required_output`。查看具体 schema 定义和字段列表可使用 [`/sra-vespa`](https://git.garena.com/shopee/search_recommend/ai-copilot/sra-toolkit/-/tree/main/skills/sra-vespa) skill 进行查询 |
| 写入链路 | OhMyEmb 或业务索引链路写 Redis / Indexer Kafka，Indexer 读取后 feed Vespa；paidads-recall 只读 Vespa，不负责写索引 |
| Rank profile | 在 YAML 或 `model_param_key` 中配置，和 `{required_output}||{rank_profile}` 一起决定 Vespa 查询和返回字段 |
| 容量与新鲜度 | 通过 Vespa 查询延迟、错误率、Indexer Kafka lag、Embedding cache hit rate、召回漏斗观察；容量规划由 Vespa/Indexer/OhMyEmb 共同决定 |

#### 3.3.2.2 KV 召回

KV 召回从 Redis 读取预计算候选列表，由通用 `RedisX2YOp` 链路和场景专属 Redis Operator 实现。相比 KNN，KV 召回把主要计算前置到离线侧，在线延迟通常更低。

| Operator | Seed | Result | 典型用途 |
| --- | --- | --- | --- |
| `RedisI2IOp` | Item | Item | 相关商品召回。 |
| `RedisU2IOp` | User | Item | 用户个性化商品召回。 |
| `RedisU2UOp` | User | User | 相似用户缓存召回。 |
| `RedisU2COp` | User | Category | 用户到类目扩展。 |
| `RedisQ2QOp` | Query | Query | Query 扩展。 |
| `RedisQ2IOp` | Query | Item | 搜索 query-to-item 缓存召回。 |
| `RedisD2IOp` | Default seed | Item | 默认或随机兜底召回。 |
| `RedisI2VOp` | Item | Video | 商品到视频召回。 |
| `RedisU2AOp` | User | Ad | 直播 user-to-ad 召回。 |

重要 Redis 队列配置字段：

| 配置字段 | 含义 |
| --- | --- |
| `queue_name` | 队列 id，用于日志、降级匹配和监控。 |
| `ab_param_key` | 用于运行时覆盖的 ABTestConfig 字段。 |
| `enable` | 运行时队列开关。 |
| `model` | Redis key 组成部分，标识离线模型或数据集。 |
| `source` | Redis key 组成部分，标识数据来源。 |
| `fetcher_version` | 选择旧 fetcher 或 v2 fetcher 行为。 |
| `compatible_old` | 在需要时兼容旧 Q2I 逻辑。 |
| `result_global_limit` / `limit` | 全局或按 seed 的候选数量上限。 |
| `score` | 缓存候选的分数过滤区间。 |

KV 队列配置示例：

```yaml
- name: Q2I_111030201
  op: RedisQ2IOp
  args:
    queue_name: 111030201
    enable: false
    ab_param_key: QueueParam111030201
    model: stgy_i2i
    source: AdsChange
    score: [0.1, 1]
    limit: 100
```

### 3.3.3 召回数据观测

召回数据观测分为离线分析日志和在线请求级调试信号。由于召回逻辑统一由 DAG 执行，这些信号可以围绕 Operator、队列输出、过滤、合并、去重和响应打包产生。

#### 3.3.3.1 离线观测

离线观测依赖 Kafka 日志和持久化召回数据。`pkg/log_producer/` 写 query log 和 recall log；`SendRecallLog` 在候选处理和响应打包后执行。下游消费者使用这些日志分析召回队列表现并诊断线上问题。

对于 Embedding 供给链路，OhMyEmb 离线观测会检查 `EmbPipelineStatus`、离线 Sinker QPS、Indexer Kafka 积压，以及目标 Vespa field 是否完成更新。这些信号用于区分模型输出变化、基础设施问题和索引写入问题。

典型离线字段包括：

```text
request_id=<request_id>
country=<country>
queue_tag=<queue_name>
operator=<operator_name>
ads_id=<ads_id>
stage=<recall|filter|merge|pack>
filter_reason=<reason>
```

常见 filter reason 包括广告 inactive、item id 无匹配广告、ads-info 过滤失败、反作弊过滤、相关性分数过低、手动广告缺少匹配关键词、eCPM 过低等。这些原因可以把召回行为和后续 relevance、prerank 过滤串起来。

| 过滤原因/Filter Reason | 阶段/Stage | 说明/Description |
| --- | --- | --- |
| INACTIVEITEM | Recall | inactive ads |
| ITEMNOADS | Recall | itemid 没有匹配到广告 / No matching ads found for the itemid |
| OFFLINEFILTERNOTPASS | Recall | ads info 信息过滤 / Filtered by ads info criteria |
| OVERDELIVERYANTIFRAUDFILTER | Recall | 反作弊策略 / Anti-fraud policy |
| LOWRELESCORE | Relevance | 相关性阈值过滤 / Filtered by relevance score threshold |
| NOPAIREDKEYWORD | Prerank | search manual mode 广告没有选中 bid keyword / Search manual mode ads missing bid keyword |
| LOWECPM | Prerank | 粗排保量策略拦截 / Filtered by coarse ranking volume control |

#### 3.3.3.2 在线观测

在线观测使用请求级 debug payload 和服务指标。

| 信号 | 作用 |
| --- | --- |
| `op_debug_info` | 开启 `EnableOpDebugInfo` 后，节点输入、输出和自定义 trace detail 会压缩后返回到 `Header.OpDebugInfo`。 |
| `FullLinkTrace.DedupMode` | 在 `RcmdAdsDedupOp` 中记录 `empty`、`filtered`、`skip` 等去重决策。 |
| `source_funnel` | 导出 `paidads_recall_rank_funnel_source_count` 等 Prometheus 漏斗指标。 |
| 队列漏斗指标 | 通过 `paidads_recall_rank_queue_funnel_cnt` 等指标记录队列维度漏斗计数。 |
| Operator 延迟指标 | 按 Operator 追踪执行耗时，标签包含 country、queue tag 等。 |
| Retrieval 大盘 | 观测 P99/P999 延迟、feature server 错误率、ads-info 数量、Vespa cache update error、panic 和 goroutine 异常。 |
| OhMyEmb 大盘 | 观测在线 Embedding QPS、延迟、错误率、离线 Sinker QPS、MiniRanker 错误率和 Indexer Embedding 缓存命中率。 |


### 3.3.4 召回排查与运维

**单请求"为什么没召回 item X"标准路径：**

1. 确认 item/ad 是否在索引中：查 AdsInfo / Vespa，先判断广告是否可见、是否 active、预算是否有效。
2. 确认候选是否被某路队列召回：打开 `op_debug_info` 或 recall log，看对应 `queue_name` 的 pre-filter count、post-filter count、picked count。
3. 如果队列没有召回，按队列类型查后端：KNN 看 `model_param_key`、`vespa_name`、`rank_profile`、embedding 字段；Redis 看 `{model}:{source}:{COUNTRY}:{seed}` key。
4. 如果已召回但最终未返回，查 `AdsInfoFilterOp`、`SnakeMergeFilterOp`、relevance/prerank/filter reason。
5. 如果只在某国家/入口异常，查 AB 参数、降级 level、`result_global_limit`、缓存配置和 GraphManagerVersion。

**高频 Op cheat sheet：**

| Op | 作用 | 常查参数 | 排查要点 |
| --- | --- | --- | --- |
| `KnnQ2IOp` / `KnnU2IOp` | Vespa KNN 向量召回 | `queue_name`、`ab_param_key`、`model_param_key`、`vespa_name`、`rank_profile`、`result_global_limit` | embedding 是否存在、rank profile 是否匹配、Vespa 查询耗时/空结果 |
| `RedisQ2IOp` / `RedisU2IOp` | Redis KV 召回 | `model`、`source`、`key`、`with_redis`、`rw_mode` | Redis key 是否命中、离线同步是否延迟、缓存 TTL 是否过期 |
| `SimpleStandardURankerOp` | 统一排序/粗排 | scorer/feature 参数、输入候选量 | scorer 错误、特征缺失、候选量过大导致耗时 |
| `SnakeMergeFilterOp` / `MergeRecallResultOp` | 队列合并、去重、截断 | inputs、`DefaultLimit`、队列 label | 新队列 output 是否接入、截断是否过早 |

**监控入口：**

| 大盘 | 链接 | 用途 |

| Retrieval L1 SRE | [Grafana](https://monitoring.infra.sz.shopee.io/grafana/d/HYPABS9Nk/retrieval-l1-sre?orgId=39) | QPS、延迟、错误率、panic、feature server error/latency |

| ohmyemb-offline-pipeline Grafana | — | 离线 Embedding pipeline、Redis 写入和 sinker 新鲜度 |
| Indexer Unified Embedding Cache Hit Rate | — | Indexer 侧 embedding cache 命中率和 Vespa 写入侧健康度 |

关键告警包括：Retrieval latency 按国家和 search/rcmd 1d/3d/7d diff > 30% 或延迟 > 130ms，Feature server error rate 1%，Graph Panic Count > 0，Goroutine 超过 30K。

**OhMyEmb 部署与扩缩容边界：**

| 组件 | 形态 | 说明 |
| --- | --- | --- |
| `emb_service_online` | SPEX 在线服务 | 请求时计算 Query/User Embedding，供 Recall 查询 Vespa |
| `emb_service_offline` | 离线/批处理服务 | 消费 Trigger，执行 DAG，写 Redis，并通过 Indexer Kafka 触发 Vespa 更新 |
| `deploy/` | SMC JSON | OhMyEmb 部署描述文件目录 |
| US 双写 | BR/CO/CL/MX 等 US 国家 | 本地 Redis + SG Redis 双写，保证 SG 全量 Indexer 可读到 embedding |

扩缩容判断看三类指标：在线推理 QPS/延迟/错误率、离线 pipeline sinker QPS 与积压、Indexer Kafka/Vespa 写入新鲜度。Recall 侧扩容只解决查询 QPS/延迟，不能解决 embedding 未产出或 Vespa 未写入的问题。

**发版流程：**

1. 功能代码合并到 `master`。
2. 如有 DAG 变更，更新 `Makefile` 的 `GraphManagerVersion`。
3. 使用 RESP Lab 验证召回结果和 `op_debug_info`。
4. 通过 SPEX 发布平台按 country / service 灰度。
5. 发布后观察 Retrieval L1 SRE 与 Ads Recall Funnel，确认 QPS、延迟、错误率、队列召回量正常。
6. **Rollback**：如出现异常需要回滚，参照 [`sra-release-sop`](https://git.garena.com/shopee/search_recommend/ai-copilot/sra-toolkit/-/blob/main/skills/sra-release-sop/SKILL.md) 中的回滚 SOP，并通过 [`/sra-release`](https://git.garena.com/shopee/search_recommend/ai-copilot/sra-toolkit/-/blob/main/skills/sra-release/SKILL.md) skill 执行回滚操作。

**Graph 配置热更新边界：**

DAG 配置不支持运行时热更新，GraphManagerVersion 变更后需要重新构建并发布服务。AB 参数、队列开关、模型参数和 `op_debug_config` 通过 SPEX Config Center 热更新，不需要重启。
