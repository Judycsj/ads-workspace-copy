## 3.3 Ads Recall Service

Ads Recall is the retrieval layer for Shopee Paid Ads. It sits between ads-engine or prerank and the downstream ranking services, retrieves candidate ads from Vespa, Redis, ES, and vector-recall paths, then filters, merges, deduplicates, logs, and returns the final candidate set.

The service is implemented as a Graph Engine workflow. Each recall path is an Operator in a DAG from `graph-manager-conf/retrieval`, while `paidads-recall` loads the proper DAG at runtime according to `SPEX_SDU`. The vector side is supplied by OhMyEmb, which computes embeddings, writes them to Redis, and syncs them to Vespa through Indexer.

| Area | Implemented Behavior |
| --- | --- |
| Service protocol | SPEX gRPC, with `search-retrieval` and `rcmd-retrieval` deployment modes. |
| Graph execution | DAG nodes execute KNN, Redis, Vespa text, ES, filtering, merge, and pack Operators. |
| Candidate sources | Vespa nearest-neighbor recall, Redis precomputed KV recall, Vespa text recall, ES keyword recall, and scene-specific RPC or strategy recall. |
| Filtering and merge | `MergeRecallQueue`, `AdsInfoFilterOp`, `SnakeMergeFilterOp`, and scene-specific filters validate, merge, deduplicate, and truncate results. |
| Runtime control | SPEX dynamic config, ABTestConfig fields, downgrade levels, op cache mode, Vespa result cache, queue switches, and queue limits. |
| Debug and observability | Kafka recall/query logs, `op_debug_info`, full-link dedup trace, Prometheus funnel metrics, and operator latency metrics. |

### 3.3.1 Offline Data Flow and Online Logic

Ads Recall combines offline queue preparation, nearline embedding production, online DAG execution, and runtime experiment config. Offline pipelines prepare Redis KV queues and vector indexes; online requests execute the selected scene DAG and merge multi-channel candidates into the response.

| Layer | Components | Responsibility |
| --- | --- | --- |
| Retrieval config | `graph-manager-conf/retrieval/*.yaml`, `GraphManagerVersion := recall_1.3.76` | Defines scene DAGs, nodes, Operator args, inputs, outputs, and graph version. |
| Embedding supply | `emb_service_trigger`, `emb_service_offline`, Redis, Indexer Kafka, Vespa | Produces item/query/user/video/live embeddings for KNN recall. |
| KV supply | Offline jobs, cache syncer, Redis | Stores precomputed I2I/U2I/Q2I/U2U and default candidate lists. |
| Online retrieval | `paidads-recall`, Graph Engine, scene handlers | Executes recall DAGs and returns candidates to ads-engine or prerank. |
| Experiment and resilience | SPEX config, ABTestConfig, `RetrievalDowngrade`, op cache, Vespa result cache | Controls queue enablement, limits, Vespa cache mode, and degradation behavior. |

#### 3.3.1.1 Offline Data Flow

Offline data preparation has two main tracks.

For vector recall, OhMyEmb prepares embeddings:

1. `emb_service_trigger` reads full and incremental ads data from Valar, scans Query/User data from Redis, and writes trigger events to Kafka topics such as item realtime, item batch, query/user realtime, and query/user batch.
2. `emb_service_offline` consumes triggers, fetches ads information from Valar when needed, runs Graph Engine DAGs such as `offline_item` and `offline_query_user`, and computes embeddings through model and feature Operators.
3. The offline service writes embeddings into Redis using the shape `{country}:{table}:{field}:{key_value}`. A typical key is `SG:sa_q2i_knn_recall:embeddingv1:<ads_id>`, with a 14-day TTL plus up to one hour of jitter.
4. The offline service sends Indexer Kafka messages. Indexer reads Redis and updates Vespa tables such as `sa_q2i_knn_recall`, `dd_u2i_knn_recall`, `ymal_u2i_knn_recall`, `knn_qrwt`, `paidads_item`, `paidads_video`, `paidads_live`, and `live_stream_ads`.

For KV recall, offline datasets are precomputed and loaded into Redis. Online Redis Operators read those lists by seed and queue config. This is used for lower-cost recall paths such as I2I, U2I, Q2I, U2U, U2C, I2V, U2A, and default queues.

For image embeddings, the live environment also supports an independent path that consumes image features from Kafka and writes them directly to Redis without running the DAG computation path.

Example OhMyEmb table/sinker config:

```yaml
table: sa_q2i_knn_recall
key:
  node: __TRIGGER__
  out: AdsID
fields:
  embeddingv1:
    data:
      node: sa_q2i_knn_recall@embeddingv1
      out: Embedding
    dim: 128
condition:
  type: ads
  enable_realtime: true
  enable_batch: true
enable_redis: "{{isLive}}"
enable_indexer: true
```

#### 3.3.1.2 Online Logic

Online traffic enters `paidads-recall` through SPEX gRPC. `server/retrieval/run.go` selects the service mode and scene handler from `SPEX_SDU`.

| Deployment Mode | SPEX SDU | Main Scenes | DAG Examples |
| --- | --- | --- | --- |
| `search-retrieval` | `deep.paidads.recall.search` | Search Ads, image search | `search_recall.yaml`, `image_search_recall.yaml`. |
| `rcmd-retrieval` | `paidads.discoveryretrieval`, `retrieval.videoads`, `retrieval.liveads`, `shopads.retrieval` | Discovery, YMAL, PP, Game, Video, Live, Shop | `recommend_dd.yaml`, `recommend_ymal.yaml`, `recommend_pp.yaml`, `recommend_game.yaml`, `video_ads_recall.yaml`, `live_ads_recall.yaml`, `shop_search_retrieval.yaml`. |

The common request flow is:

1. Receive a SPEX gRPC request from ads-engine or prerank.
2. Run request validation and rate limiting through `config.GlobalConfig.RecallLimiter`.
3. Build request context with country, entrance, scene, and AB parameters.
4. Execute the scene DAG through Graph Engine.
5. Run recall Operators in parallel or sequence, including KNN, Redis, Vespa text, ES, and scene-specific Operators.
6. Merge queue outputs through `MergeRecallQueue`.
7. Filter ads through `AdsInfoFilterOp` and scene-specific business filters.
8. Deduplicate and truncate through snake merge.
9. Pack results, send recall logs through `SendRecallLog`, and return `RecallResponseV2`.

#### 3.3.1.3 System Common Logic

System common logic covers the recall-wide behavior shared by Search, Discovery, Video, Live, Shop, and other scene DAGs. These functions are not tied to a single recall source; they provide the execution, control, filtering, caching, and response packaging framework used by KNN, KV, Vespa text, ES, and scene-specific recall paths.

##### 3.3.1.3.1 Graph Orchestration and Scene Routing

`paidads-recall` routes requests by `SPEX_SDU` and scene context, then loads the matching Graph Engine DAG from `graph-manager-conf/retrieval`. Each DAG is composed of Operators with declared args, inputs, and outputs. This lets multiple recall channels run in parallel or sequence and makes queue outputs available to downstream merge and filter nodes.

Common scene routing examples:

| Routing Dimension | Example |
| --- | --- |
| Service mode | `search-retrieval`, `rcmd-retrieval` |
| SPEX SDU | `deep.paidads.recall.search`, `paidads.discoveryretrieval`, `retrieval.videoads`, `retrieval.liveads`, `shopads.retrieval` |
| DAG config | `search_recall.yaml`, `recommend_dd.yaml`, `video_ads_recall.yaml`, `live_ads_recall.yaml`, `shop_search_retrieval.yaml` |

##### 3.3.1.3.2 Runtime Configuration and Degradation

Runtime config is controlled through SPEX config and ABTestConfig fields. Common queue parameters include `queue_name`, `enable`, `ab_param_key`, `model_param_key`, `limit`, and `downgrade_level`. AB parameters can override queue switches and limits at runtime without redeploying the service.

Degradation logic uses retrieval downgrade config to decide whether a queue should run under the current traffic and service state. When `AdsEngineUseUnifiedDowngrade` is false, KNN Vespa queries can use `queryProfileForNoneDowngrade` to skip Vespa-side downgrade logic for experiments that need that behavior.

##### 3.3.1.3.3 Candidate Filtering, Merge, and Deduplication

Recall queues return candidate ids and source metadata. Shared filtering and merge logic validates candidates before response packing.

| Function | Main Logic |
| --- | --- |
| Candidate merge | `MergeRecallQueue` combines outputs from multiple recall queues and preserves queue/source context. |
| Ads validation | `AdsInfoFilterOp` and scene-specific filters remove invalid ads before ranking. |
| Deduplication | Snake merge and dedup logic remove repeated candidates and truncate results to the requested size. |
| Trace propagation | Queue tags and Operator metadata are kept for logs, debug payloads, and observability. |

##### 3.3.1.3.4 Cache and Result Packaging

Common cache logic reduces repeated backend calls and stabilizes online latency. Operator cache uses `rw_mode` values such as `read_write`, `read_only`, `write_only`, and `disable`. Vespa result cache can use Redis for cross-instance sharing or memory for instance-local caching.

After merge and filtering, the service packs candidates into `RecallResponseV2`, attaches queue/source metadata needed by downstream ranking, and triggers recall logging through `SendRecallLog`.

### 3.3.2 Recall Channels

Ads Recall mainly uses vector KNN recall and KV recall as reusable recall channels. Vector KNN recall depends on embeddings produced by OhMyEmb and retrieves nearest candidates from Vespa; KV recall reads precomputed candidate lists from Redis.

#### 3.3.2.1 Vector KNN Recall

Vector KNN recall uses seed embeddings to query Vespa nearest-neighbor indexes. In `paidads-recall`, the generic `KnnX2YOp` path and scene-specific variants build Vespa ANN requests, execute them, and pack the returned ids into recall candidates.

##### 3.3.2.1.1 Embedding System / OhMyEmb

OhMyEmb is the unified embedding framework used by Paid Ads vector KNN recall. It calculates and maintains embeddings for ads, items, users, queries, videos, and live streams. It uses Graph Engine and Graph Manager service `ohmyemb` for DAG execution, writes offline embeddings to Redis, and notifies Indexer to sync them into Vespa.

| Service | Role |
| --- | --- |
| `emb_service_trigger` | Produces Kafka triggers from Valar full/incremental ads data and Redis Query/User scans. |
| `emb_service_offline` | Consumes triggers, runs offline DAGs, writes Redis embeddings, and sends Indexer Kafka messages. |
| `emb_service_online` | Serves SPEX RPC `paidads.emb_service.get_embedding` for real-time Query/User embedding inference. |

OhMyEmb covers Search Ads Q2I, DD U2I, YMAL U2I, video AnTou and MingTou, Live Ads, Union Item/Video/Live, Query Rewrite/Extend, and User-to-User scenes. Its graph configs live under `graph-manager-conf/ohmyemb/`, including `offline_item.yaml`, `offline_query_user.yaml`, `online_query_user.yaml`, and `opdef.yaml`.

Model versions are bound in Graph Manager DAG nodes through `model_name`; offline batch progress is tracked in Etcd through `ProcessingVersion` and `CompletedVersion`, where equality means the batch write has completed.

| Operator | Seed | Target | Main Scene |
| --- | --- | --- | --- |
| `KnnQ2IOp` | Query | Item | Search Ads Q2I recall. |
| `KnnU2IOp` | User | Item | Discovery, YMAL, PP, Game U2I recall. |
| `KnnU2UOp` | User | User | Similar-user recall before user-to-item expansion. |
| `LiveKnnU2IOp` | User | Ad | Live item-ad recall. |
| `KnnU2LOp` | User | Live stream | Live stream recall. |
| `KnnU2VOp` | User | Video | Video Ads U2V recall. |
| `KnnU2I2V` | User | Video through item | Video Ads user-to-item-to-video recall. |
| `KnnQ2SOp` | Query | Shop | Shop search recall. |

##### 3.3.2.1.2 Offline Data Flow

KNN offline flow prepares the embeddings and Vespa indexes used by online nearest-neighbor retrieval.

1. `emb_service_trigger` produces trigger messages for ads, query, user, video, and live entities.
2. `emb_service_offline` consumes triggers and performs country filtering, lag checks, trigger splitting, pre-checks, rate limiting, ads-info fetch, and post-checks.
3. Graph Engine executes the required offline DAG nodes. Current model Operators include `EgoPredictOp`, `SimpleMiniRankerOp`, `SimpleStandardURankerOp`, `FseFetchOp`, and `MTextOp`.
4. Sinker writes embedding fields into Redis and sends Indexer Kafka messages.
5. Indexer updates Vespa fields, making the embeddings queryable by online recall.

Vespa table examples include:

| Scene | Vespa Table | Key |
| --- | --- | --- |
| Search Ads Q2I | `sa_q2i_knn_recall` | `AdsID` |
| DD U2I | `dd_u2i_knn_recall` | `AdsID` |
| YMAL U2I | `ymal_u2i_knn_recall` | `AdsID` |
| Query rewrite/extend | `knn_qrwt` | `QueryMText` |
| User-to-user | `knn_u2u` | `UserID` |
| Union item | `paidads_item` | `ItemIDList` |
| Union video | `paidads_video` | `VideoID` |
| Union live | `paidads_live` | `AdsAccountID` |

US countries such as BR, CO, CL, and MX can double-write embeddings to SG Redis through `paidads.emb_service.redis_write`, because full Indexer jobs read from SG Redis while realtime Indexer jobs read local Redis.

##### 3.3.2.1.3 Online Recall

Online KNN recall has two embedding paths:

| Path | Behavior |
| --- | --- |
| Online embedding inference | `paidads-recall` calls `paidads.emb_service.get_embedding` when Query/User embeddings must be computed during the request. `emb_service_online` maps `dag_name` and `required_output` through `req_output_mapping`, executes the needed subgraph, and returns embeddings without writing Redis or Indexer Kafka. |
| Vespa nearest-neighbor retrieval | `KnnX2YOp` or scene-specific KNN Operators use the seed embedding, `vespa_name`, `embedding_field`, `rank_profile`, and `recall_limit` to query Vespa and pack candidates. |

Important KNN config fields:

| Config Field | Meaning |
| --- | --- |
| `queue_name` | Queue id used for monitoring, logs, downgrade checks, and merge tracking. |
| `ab_param_key` | ABTestConfig field that can override dynamic queue parameters. |
| `model_param_key` | Model parameter selector for values such as `vespa_name`, `rank_profile`, and cluster or field settings. |
| `vespa_name` | Vespa table or cluster used for ANN retrieval. |
| `embedding_field` | Embedding field in Vespa, for example `embeddingv1`, `embeddingv2`, or `embeddingv3`. |
| `rank_profile` | Vespa rank profile paired with the embedding field. |
| `required_output` | OhMyEmb output key or DAG node output needed to compute the seed embedding. |
| `recall_limit` / `limit` | Candidate limit per seed or per queue. |

Example KNN queue shape:

```yaml
- name: U2I_KNN_623012108
  op: KnnU2IOp
  args:
    queue_name: 623012108
    enable: false
    ab_param_key: U2IKnn623012108Config
    model_param_key: knnRecallRcmdLTRModelCfg
    required_output: dd_knn_ltr_v1
    vespa_name: dd_u2i_knn_recall
    embedding_field: embeddingv2
    rank_profile: v2
    recall_limit: 500
```

#### 3.3.2.2 KV Recall

KV recall reads precomputed candidate lists from Redis. It is implemented by the generic `RedisX2YOp` path and scene-specific Redis Operators. Compared with KNN, KV recall shifts most computation offline and usually has lower online latency.

| Operator | Seed | Result | Typical Use |
| --- | --- | --- | --- |
| `RedisI2IOp` | Item | Item | Related item recall. |
| `RedisU2IOp` | User | Item | User personalized item recall. |
| `RedisU2UOp` | User | User | Similar-user cache recall. |
| `RedisU2COp` | User | Category | User-to-category expansion. |
| `RedisQ2QOp` | Query | Query | Query expansion. |
| `RedisQ2IOp` | Query | Item | Search query-to-item cache recall. |
| `RedisD2IOp` | Default seed | Item | Default or random fallback recall. |
| `RedisI2VOp` | Item | Video | Item-to-video recall. |
| `RedisU2AOp` | User | Ad | Live user-to-ad recall. |

Important Redis queue config fields:

| Config Field | Meaning |
| --- | --- |
| `queue_name` | Queue id for logs, downgrade matching, and monitoring. |
| `ab_param_key` | ABTestConfig field used for runtime override. |
| `enable` | Runtime queue switch. |
| `model` | Redis key component that identifies the offline model or dataset. |
| `source` | Redis key component that identifies the data source. |
| `fetcher_version` | Selects old or v2 fetcher behavior. |
| `compatible_old` | Enables compatibility with old Q2I logic where needed. |
| `result_global_limit` / `limit` | Global or per-seed candidate count limit. |
| `score` | Score range filter for cached candidates. |

Example KV queue shape:

```yaml
- name: Q2I_111030201
  op: RedisQ2IOp
  args:
    queue_name: 111030201
    enable: false
    ab_param_key: QueueParam111030201
    model: stgy_i2i
    source: AdsChange
    score: [0.1, 1]
    limit: 100
```

### 3.3.3 Recall Data Observability

Recall observability is split between offline logs for analysis and online request-time signals for debugging. The same DAG execution model makes these signals available around Operators, queue outputs, filtering, merge, deduplication, and response packing.

#### 3.3.3.1 Offline Observability

Offline observability is based on Kafka logs and persisted recall data. `pkg/log_producer/` writes query logs and recall logs; `SendRecallLog` runs after candidate processing and response packing. Downstream consumers use these logs to analyze recall queue performance and diagnose production issues.

For embedding supply, OhMyEmb offline observability checks `EmbPipelineStatus`, offline Sinker QPS, Indexer Kafka lag, and whether the target Vespa fields have been updated. These signals distinguish model-output changes from infrastructure or indexing issues.

Typical offline fields include:

```text
request_id=<request_id>
country=<country>
queue_tag=<queue_name>
operator=<operator_name>
ads_id=<ads_id>
stage=<recall|filter|merge|pack>
filter_reason=<reason>
```

Common filter reasons include inactive ads, no ads for item id, ads-info filter failure, anti-fraud filtering, low relevance score, missing paired keyword, and low eCPM. These reasons connect recall behavior with later relevance and prerank filtering.

#### 3.3.3.2 Online Observability

Online observability uses request-time debug payloads and service metrics.

| Signal | Purpose |
| --- | --- |
| `op_debug_info` | When `EnableOpDebugInfo` is enabled, node inputs, outputs, and custom trace details are compressed and returned in `Header.OpDebugInfo`. |
| `FullLinkTrace.DedupMode` | Records dedup decisions such as `empty`, `filtered`, and `skip` in `RcmdAdsDedupOp`. |
| `source_funnel` | Exports Prometheus funnel metrics such as `paidads_recall_rank_funnel_source_count`. |
| Queue funnel metrics | Records queue-level funnel counts through metrics such as `paidads_recall_rank_queue_funnel_cnt`. |
| Operator latency metrics | Tracks execution time by Operator with labels such as country and queue tag. |
| Retrieval dashboards | Track P99/P999 latency, feature server error rate, ads-info volumes, Vespa cache update errors, and panic or goroutine anomalies. |
| OhMyEmb dashboards | Track online embedding QPS, latency, error rate, offline Sinker QPS, MiniRanker error rate, and Indexer embedding cache hit rate. |

Typical online debug shape:

```text
request_id=<request_id>
queue_tag=<queue_name>
node=<dag_node_name>
operator=<operator_name>
input_size=<n>
output_size=<n>
dedup_mode=<empty|filtered|skip>
```
