## 5.3 Tracking & Attribution

This section introduces the core concepts of the ads tracking system and order attribution models. For the engineering architecture of data services (Tracking service, Kafka pipelines), see [§3.6 Ads Data](../03.ads-engine/06.ads-data.md).

### 5.3.1 Tracking System Overview

The Ads Tracking system is responsible for receiving ad events reported by the frontend/SDK, performing validation, enrichment, and deduplication, then distributing them to downstream consumers.

**Event Hierarchy Model**: Tracking (request-level) contains secondary entities — items (Product Ads), shops (Shop Ads), livestreams (Live Ads), videos (Video Ads), banners (Display/Brand Ads).

**Core Event Types (Operation)**:

| Operation | Value | Description |
|-----------|-------|-------------|
| IMPRESSION | 1 | Ad impression |
| CLICK | 2 | Ad click |
| PRODUCT_CLICK | 14 | Product click |
| VIDEO_VIEW | 21 | Video view |
| ADD_TO_CART | 5 | Add to cart |

**Key Data Fields**:
- **json_data**: Serialized `AdsData` Protobuf carrying ad metadata (ads_id, campaign_id, pricing_type, pCTR, pCR, ecpm, recall_type, etc.)
- **deduction_info**: Encrypted billing information passed from the Ads BE through Org BE to FE, then sent back to Tracking
- **entrance**: Traffic entrance (e.g., search=1, daily_discover=3); the entrance in json_data takes priority over the frontend-reported value
- **placement**: Ad placement, derived from entrance via mapping

**Deduplication Mechanisms**:
- **Checksum Deduplication**: xxhash of the POST body, Redis SETNX, 12h TTL. Marks duplicates but does not discard events.
- **Business-Level Deduplication**: Different Redis keys and TTLs per scenario (standard 10min, Live Antou 1min). Sets `DuplicateLabel` for downstream decision-making.

**Anti-Fraud**: IP rate limiting (1000/h), user+ad rate limiting (5/d), user+placement rate limiting (30/d), DFP risk assessment (Click only), fraudulent user cache.

### 5.3.2 TMS Merger

TMS (Tracking Management System) is the company-level tracking system. Ads tracking is being merged with TMS to eliminate duplicate reporting from both sides.

**Merger Architecture**:
1. Frontend/App reports events uniformly through TMS SDK (no longer distinguishing organic traffic from ads)
2. TMS Tracking distribution: ad events are tagged with `real_time_type = ADS` and routed through the Priority Channel (UBTA Kafka) for real-time processing
3. `paidads-tracking` (TMS Service) consumes UBTA and converts TMS format into **Fake Ads Tracking** (compatible with legacy Protobuf), minimizing downstream migration costs
4. Downstream consumers (Deduction, Report-NG, OA) consume the same format as before

**Core Design Principle**: The frontend does not understand ad business logic; all mappings (Operation, Entrance, Placement) are completed on the Tracking server side.

### 5.3.3 Order Attribution Overview

Order Attribution (OA) determines which ad interaction an order should be attributed to. Implemented in `paidads-report-ng`.

**Two Independent Attribution Pipelines**:
- **Main OA**: Covers all ad types. Priority: Click > Impression > OCPM No-Click.
- **Agent OA**: Live Ads only (streamer/agent scenarios), Click attribution only.

The same order can be attributed in both pipelines simultaneously (double-counting is by design).

### 5.3.4 Attribution Models

#### Click Attribution

| Attribution Type | Redis Key | Attribution Window | Description |
|-----------------|-----------|-------------------|-------------|
| **Direct** | `item:{user}->{item}` | 7 days | User clicked the specific promoted item, then ordered that item |
| **Broad** | `shop:{user}->{shop}` | 7 days | User clicked an ad, then ordered another item from the same shop (triggered when Direct misses) |
| **Agent** | `item:` + `ls_agent_item:` | 24 hours | Live Ads agent scenario, takes the most recent valid agent livestream ad click |

**Write Rules**: Product/Search/ROI2/Boost/Targeting/Video/Live Ads always write the item key; Shop Ads only write the item key when the user clicks the product area; Brand/Display/Banner do not write the item key.

#### Impression Attribution

Triggered after Click attribution misses. 24-hour window. Requires country-level feature flag + experiment + exemption check. Supports Product Ads and Live Ads.

#### No-Click / No-Imp Attribution (OCPM)

Triggered after both Click and Impression attribution miss. Queries Valar for active ROI2/OCPM ad candidates. Requires dual-layer feature flags.

**Exemption Conditions**: No clicks in 7 days, GMV ratio >= 50%, budget exhausted, under-recovery. Exemption does not change the experiment label.
