## 5.4 Billing & Deduction

This section introduces the core concepts of the ads billing and deduction system, including top-up, deduction flow, revenue definitions, and the auto-rebate mechanism.

### 5.4.1 Billing Modes

| Mode | Full Name | Trigger Event | Description |
|------|-----------|---------------|-------------|
| **CPC** | Cost Per Click | Click | Billed per click, most commonly used |
| **CPM** | Cost Per Mille | Impression (batch) | Billed per thousand impressions, aggregated via Batcher (30s timeout, max 50 per batch) |
| **OCPM** | Optimized CPM | Impression (optimized) | Optimized CPM, shop-level batch processing |
| **CPS** | Cost Per Sale | Conversion | Billed per sale, TMS pipeline only |
| **ECPC** | Enhanced CPC | Click (enhanced) | Enhanced CPC, bid cap at 4x |

### 5.4.2 Deduction Flow Overview

Deduction consists of two phases:

**Online Pre-Deduction** (`paidads-deduction`):
1. Consume Tracking events
2. Anti-fraud filtering → basic validation → single-item check → price extraction
3. Redis SETNX deduplication (standard CPC/CPM: 1h TTL; OCPM: 24h TTL)
4. Model status check (whether ad/campaign/account is valid)
5. Price cap check (4x seller bid)
6. Campaign daily budget check → account balance pre-check
7. Send deduction event to Kafka

**Offline Deduction** (`paidads-offline-deduction`):
1. Consume deduction events
2. Translog deduplication (pre-transaction query + MySQL unique key constraint dual-layer guarantee)
3. Three-level budget cap check: account + credits, campaign daily budget, placement allocation
4. DB transaction execution (SELECT FOR UPDATE → credits/account/campaign_daily update → translog insert)
5. Downstream output: translog, financial events, re-indexing

### 5.4.3 Top-up & Account

Advertisers inject funds into their ad account through top-up. Account balance is divided into:
- **Cash Balance**: Funds actually topped up by the advertiser
- **Free Credit**: Promotional credits issued by the platform (e.g., credits injected via auto-rebate)

Different types of balance are consumed according to rules during deduction.

### 5.4.4 Revenue Concepts

| Concept | Definition |
|---------|------------|
| **Gross Revenue** | Total ad spend by advertisers (including tax and all deductions) |
| **Net Revenue** | Gross revenue minus rebates, expired amounts, etc. |
| **expenditure_amt** | Ad spend (pre-tax, excluding Display/Expiry) |
| **Net Take Rate** | net_ads_revenue / buyer_checkout_gmv |

### 5.4.5 Auto Rebate

Auto Rebate is a ROAS/ROI protection mechanism: when a Campaign's actual ROI falls below the protection threshold, the system compensates the advertiser by injecting Free Credits.

**Three-Layer Architecture**:
1. **Rule Layer** (DE offline computation): Rebate cycle, order threshold, ROI protection threshold, calculation formula
2. **Service Layer** (`auto-rebate`): State machine managing the rebate lifecycle, creating rebate orders, calling Top-up to inject credits
3. **Data Warehouse Layer**: Stores expected/final rebate, top-up details, and translog for analysis and reconciliation

**Key Concepts**:
- **Expected Rebate**: Theoretical rebate amount = spend - protected ADVV
- **Final Rebate**: Actual rebate amount after manual review and risk control
- **ADVV**: Advertiser Value = broad_gmv × target_cir. Divided by 0.9 for Rapid Boost/Campaign Surge scenarios
- **Order Threshold**: ROI2/MPD >= 5 orders, GMS >= 10 orders
- **Rebate Cap**: `min(expected_rebate, spend × rebate_amt_cap)`

**State Machine**: invalid → calculating → need_manual_review / no_rebate_needed / pending_rebate → order_created → rebate_done
